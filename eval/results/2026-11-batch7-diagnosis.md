## Method

- After the scored run (committed first, as `477a44e`), analyzed each checkout in `eval/.repos/` at its pinned commit with the built `analyze()` (the scratch `eval/dist/m92c-diag.mjs`), and listed the services, routes, unresolved nodes (reason, expression, detail), `http` edges with their sites, and warnings.
- Read the code at each missed site and at the helper, base, or client it goes through, and compared it with the analyzer's documented "not handled" lists (`packages/analyzer/src/http/wrappers.ts`, `url.ts`) and the ADRs.
- Reproduced every cause but AK's deploy config and the JornAI label in minimal repos, each beside the nearest form that is read (the scratch `eval/dist/m122c-b7-three-repro.mjs`, `neowatch-repro.mjs`, `neowatch-repro2.mjs`, and `m122c-repro.mjs`). AM was also checked on a copy of AuthSphere with the SDK folder named as a workspace.
- Counted each miss under exactly one cause with a script over the scored report; the FN column sums to 305 and the FP column to 4.

## Precision (4 FP)

- **AQ, 2 FP (and 2 FN).** Both edges are the right routes, drawn one call out from the labels (below).
- **The label left out, 1 FP.** JornAI's `create` sends `apiPost<{ … }>("/api/users", form)` at `AdminPanel.tsx:337`; `src/app/api/users/route.ts:35` exports `POST`, and `apiPost` is labeled at its callers everywhere else in the file (328, 357, 373). The labeler skipped this one, perhaps because its type argument spreads the call over five lines. The edge is right. The label is left as committed, since the batch is scored once (as batch 6's RentTools.io slip was); with it, precision would be 99.6% (840 of 843) and recall 73.4% (840 of 1,145).
- **AY, 1 FP, the only wrong edge.** neowatch's `test/verify-design.mjs:516` runs `fetch('/api/catalog/home')` inside `page.evaluate(...)`, so the browser sends it from a page whose origin the script gets only from the command line (its two other requests are `null` for that reason, M12.2b2). The analyzer reads a root-relative URL as the page's own origin and matches it across services at `heuristic` (a proxy is assumed, `match.ts`), not knowing that a `page.evaluate` body runs in another page. No ADR mentions `page.evaluate`.

All 256 `exact` and 583 `heuristic` true positives are otherwise right; batch 7 has no `pattern` prediction.

## Calling side

- **AI, a `let` base read through a guarded getter (123 FN).** zero-cost-crm's `testing/functional/api/helpers.ts` declares `let baseUrl = '';` (line 6), sets it in `startApi()` to `` `http://127.0.0.1:${(server!.address() as AddressInfo).port}` `` (line 21, the app on `listen(0)`), resets it in `stopApi()` (line 32), and reads it through `getBaseUrl() { if (!baseUrl) throw new Error(…); return baseUrl; }` (lines 9–11). 119 requests go through `api(path)` → `` fetch(`${getBaseUrl()}${path}`) `` (the wrapper is read; the callers' paths are found), and 4 call `` fetch(`${getBaseUrl()}/api/…`) `` directly. Three things each block it alone, as the minimal repos show: ADR-0304 reads a module `let` with no initializer and exactly one write, and this one has an initializer and a second write; and the string-builder rule (M5C.7d, `url.ts`'s `builderBody`) reads only a function whose body is a single `return` of a template, string, or `+`, so the `throw` guard stops it, and so would `return baseUrl` alone (a bare identifier isn't a builder's return). ADR-0304's exact shape (`let baseUrl;`, read directly) matches in the same repro. The guard is why the empty initial value can't be what a request sends.
- **AJ, a method destructured from the options parameter (98 FN).** Every neowatch test suite has its own `req`, of the shape `const req = async (path, { method = 'GET', token, body, … } = {}) => { … fetch(BASE + path, { method, headers, … }) }` (`test/session-test.mjs:31,35`, `account-test.mjs:40,47`, and the same in the other suites). The URL is read (`BASE` is the `localhost:8787` fallback, and the paths are the callers'), but the method isn't: `wrappers.ts`'s `parameterOf` takes only a declared parameter, and `method` here is a binding element of one, so `methodValue` gives `null` and each site is `AMBIGUOUS` ("the method isn't read, and routes for DELETE, GET match {env:BASE}/api/auth/me"), even for calls passing no options, where the `'GET'` default applies. The file's header lists `{ method }` from a parameter as handled and names a destructured prop only for React components; for plain functions this is an unhandled form, not a decided refusal. The URL side already binds an object pattern's properties. Split by suite: session 39, account 25, catalog 11, integration 8, hardening 7, img 4, proxy 3, contract 1.
- **AK, a literal public host (31 FN).** Blog-Website-MERN's `client/src/config/defaults.js:1` is `export const BACKEND_HOST_URL = "https://blog-website-mern-navy.vercel.app"`, and every service sends `` axios.get(`${BACKEND_HOST_URL}/admin/getAllUsers`, config) `` and the like (admin 4, auth 8, blog 11, category 4, profile 4). The labels follow the host into the repo because `server/vercel.json` routes `"/(.*)"` to `server.js`, whose routes match every path sent there (ADR-0209). The analyzer doesn't read `vercel.json`, and a literal remote host is never this repo, so each site is an `external_call` to that host. ADR-0209 foresaw it: such targets are "likely misses shown under `external host`". By design, as U's public-host side was in batch 6.
- **AL, a multi-statement URL builder (23 FN).** neowatch's `test/proxy-test.mjs:65-72` has `function link(url, opts = {}, exp = …) { let u = \`/api/proxy?url=${enc(url)}\`; if (opts.ua) u += …; … return \`${u}&exp=…\`; }`, called as `req(link(up('…'), { lan: 1 }))` and through `const base = link(…)`. String builders (M5C.7d) must be a single `return`; `link` has six statements and returns a local `let`, so every URL is `DYNAMIC_URL` ("every path segment is only known at runtime"). A one-`return` `link()` matches `GET /api/proxy` in the repro. A deliberate scope limit.
- **AM, an SDK folder no workspace pattern names (7 FN).** AuthSphere's root `package.json` lists `"workspaces": ["frontend", "backend", "packages/*"]`, but the SDK is `packages/` itself, with its own `packages/package.json` (`@authspherejs/sdk`), so `packages/*` matches nothing. Under ADR-0163's M5C.7e amendment, a folder with its own `package.json` that no pattern names is another project, left out of the root service; the analyzer warns `WORKSPACE_NO_MATCH` and `FILES_OUTSIDE_SERVICE` ("20 source files under packages/ … are not analyzed") and draws nothing at the SDK's 7 labeled sites. By design. Analyzed anyway (a copy with the workspace named `packages`), all 12 SDK requests become `DYNAMIC_URL`: the base comes from `getConfig()`, a frozen copy of a module `let` set by `initAuth(options)` with a conditional default (`if (!options.baseUrl) options.baseUrl = DEFAULT_BASE_URL`), so reading the folder alone would turn these misses into unresolved nodes, not matches.
- **AN, a component fetching its prop through SWR (4 FN).** maintenance-management-system's admin pages render `<DataTable url="/api/locations">` (and `/api/types`, `/api/users`, `/api/workers`), labeled at each element (EVALUATION.md §1). Inside, `DataTable.tsx:45-54` keeps the prop in `useState(url)` state reset by an effect, and fetches through a fetcher declared inside the component (`const fetcher = (url) => fetch(url, …)`). A nested named fetcher is listed as not handled (`wrappers.ts`), state isn't a value the normalizer follows, and a component passing its prop to SWR's positional key isn't followed either (ADR-0312 follows objects: hook options and element attributes). Each blocks it alone in the repros; a component that `fetch`es its prop directly, and a module-level fetcher, both match `exact`.
- **AO, a spread-and-init SWR fetcher (3 FN).** `ReportsTable.tsx:142`, `MyReports.tsx:13`, and `useUncompletedReports.ts:15` call `useSWR(key, (...args) => fetch(...args, { cache: "no-store" }))`. ADR-0194 reads the bare `(...args) => fetch(...args)`, and `wrappers.ts` lists a spread rest parameter with other arguments around it as not handled, so the `fetch` is `DYNAMIC_URL` and the `useSWR` calls, where the labels sit, get nothing. `(url) => fetch(url, { cache })` matches `exact` in the repro. Documented.
- **AP, a catch-all (3 FN).** `catalog-test.mjs:173` (`anon('/chaine/abc')`) and `contract-test.mjs:87,90` request SPA pages that only the server's fallback `app.get('*')` (`server/src/index.js:456`) answers, labeled `GET /*splat`. ADR-0033's amendments (M5C.7c, M9.1a3b) leave a catch-all of every path out of the ranking, literal paths included, so each is `NO_MATCHING_ROUTE` ("only a catch-all of every path matches … (GET /*), so it doesn't pick a route"). By design.
- **AQ, a fixed-path helper with a method parameter (2 FN, 2 FP).** DecisionOS's `share-panel.tsx:58-61` is `function request(method: "POST" | "DELETE") { … fetch(\`/api/decisions/${decisionId}/share\`, { method }) }`, called as `request("DELETE")` (line 144) and `request("POST")` (line 158). ADR-0164 lets a method parameter make a wrapper, so the analyzer draws `DELETE` and `POST` `exact` at the two callers. EVALUATION.md §1 labels a call "whose URL is fixed there (even inside a helper)" at that call, and moves a label to the callers only for "a helper that takes the path as a parameter", so both labels sit at line 61 (M12.2b4 gave the site one label per method). Both edges are right and one level apart from the labels: the analyzer's rule and the label rule disagree on a parameter that fixes only the method, as they did on AG's path after a fixed segment.
- **AR, a method passed on to a wrapper (2 FN).** DecisionOS's `tag-picker.tsx:58` sends `sendJson("/api/decisions/tags", method, …)` inside `mutate(method: "POST" | "DELETE")`, called with `"POST"` (line 82) and `"DELETE"` (line 111). `sendJson` is inlined one level (`wrappers.ts`), so the method is `mutate`'s parameter, which ADR-0308 keeps unknown, and the site is `AMBIGUOUS` ("the method isn't read, and routes for DELETE, POST match"). `mutate("POST")`'s literal passed straight to `sendJson` matches in the repro. A relative of W: a method chosen by the caller.
- **AS, the method as a property of the options (2 FN).** neowatch's `hardening-test.mjs:160` has `const call = (p, opt = {}) => fetch(own + p, { method: opt.method || 'GET', … })`, used at lines 170 and 175. A config parameter read through properties is listed as not handled (`wrappers.ts`), so both are `AMBIGUOUS`. Documented.
- **AT, a base from a returned object (2 FN).** neowatch's `test/run.mjs:101` has `warmHealth(base)`, whose `getJson(\`${base}/api/catalog/channels?…\`)` (line 104) and `fetch(\`${base}/api/catalog/check\`, { method: 'POST' … })` (line 108) fix their paths; it's called as `warmHealth(srv.base)` (line 212), `srv` being `startServer()`'s returned object. The leading `base` makes `warmHealth` a wrapper (ADR-0164), so the requests move to line 212, where a property of an async function's result isn't read: one `DYNAMIC_URL` there, an unlabeled line, and nothing at 104 and 108. Reading the value wouldn't be enough: EVALUATION.md §1 labels the call that supplies the path (inside `warmHealth`), while the analyzer places it at the call supplying the leading parameter, so a readable base would draw the right routes at line 212 (an FN and an FP each). The repro shows both layers.
- **AU, a fetcher chosen with `??` (2 FN).** agentic-scheduling's `src/components/calendar/progressiveSchedule.ts:34` is `const fetcher = opts.fetcher ?? ((url, sig) => fetch(url, { signal: sig }))`, called at lines 46 and 69 with `/api/schedule` paths. A local helper must be a function value (`wrappers.ts`), and this const is a `??` expression, so the `fetch` is `DYNAMIC_URL` and the two calls get nothing. The plain arrow matches `exact` in the repro. Documented.
- **AV, an env base read through the repo's helper (1 FN).** agentic-scheduling's monitor cron sends `` `${base}/api/availability?…` `` through `timedFetch(url)` inside `checkAvailability(base)` (`src/app/api/cron/monitor/route.ts:78`), called at line 251 with `PUBLIC_BASE_URL = optionalEnv("PUBLIC_BASE_URL") ??
