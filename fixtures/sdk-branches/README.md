# sdk-branches

Tests: SDK clients built on several branches (M9.7g, review findings H1, H2, H4). In `switch.js`, `LocalOrCloud`'s field is written twice in its constructor, once with a localhost base and once with OpenAI's default, so its request is unresolved (`DYNAMIC_URL`, different bases on different branches) rather than drawn to the first write's base; `Lazy`'s `this.ai = this.ai || new OpenAI(…)` refers to itself, so its one client goes to `api.groq.com`; `clientFor`'s `opts.client || new OpenAI(…)` may return any client the caller passes, so `embed` is unresolved too. In `fields.ts`, `Switchable`'s initializer builds a default client and `useGroq` replaces it, so its request is unresolved; `router`'s `cache.router ?? new OpenAI(…)` reads a cache on the global object, which holds the same client, so `route` reaches `openrouter.ai`; `assistant` is an Anthropic client on one branch and an OpenAI client on the other, so its request is unresolved; and `azure`'s env base is set in `.env.example` to a placeholder (`https://YOUR_RESOURCE.openai.azure.com/…`), so no outside API is drawn for it.

M9.7j (review findings J1, J3) adds three more. `Pluggable` builds its client with no options, but `setClient` may swap in one with any base, so its request is unresolved; `sharedModels` reads `window.openai`, which nothing in `switch.js` writes, so another script may have put any client there and its request is unresolved too; and `repoFor`'s `given ?? new Octokit({ auth })` pairs a caller's client with one built only with a token, so it's unresolved rather than drawn to `api.github.com`.

M9.7l (review findings K1, K2) adds three more. In `switch.js`, `assistantModels` reads `globalThis.openai`, whose only write in the file stores a client `setAssistant`'s caller injects, so it's no cache and the request is unresolved; `modelsOf`'s `self` is a parameter, not the global object, so `self.openai` may hold any client and its request is unresolved too. In `fields.ts`, `issuesFor` joins a caller's client, the App's, and one built with a token (`opts.gh ?? app.octokit ?? new Kit({ auth })`); the caller's may have any base, so it's unresolved whatever order the three come in.

M9.7m (review findings L1, L2) adds `lazy.ts` and `setup.ts`. `getAI`'s `g.lazyAI ??= new OpenAI()` reads what was at the path before, and nothing but that line writes it, so `lazyModels` goes to `api.openai.com`; `getClient`'s `client ??= new OpenAI()` reads the module variable, which `setClient` may set to any client, so `clientModels` is unresolved. `proxied` is cached on the global object in `lazy.ts`, but `setup.ts` stores a client with the proxy's base at the same path, so `proxiedModels` is unresolved too: a global path's writes are read in every file of the service.

M9.7n (review findings M1, M2) adds `warm.ts`. `warm` writes `getCached()`'s result back to `cached`, which `setCached` may also set to any client, so both `warm`'s and `cachedModels`' requests are unresolved, whichever is traced first (before M9.7n, tracing `warm` first cached `getCached` as the default client). `sharedAI` is a global `var`, so `share`'s bare-name write stores a caller's client at `globalThis.sharedAI`, and `sharedModels`' `??=` read is unresolved rather than drawn to `api.openai.com`.
