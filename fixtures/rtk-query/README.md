# rtk-query

Tests: RTK Query endpoints as requests (ADR-0196). `store/api.ts`'s `createApi` uses `fetchBaseQuery({ baseUrl: "/api/" })`, so each endpoint's `query` is a `fetch` RTK makes: `listTasks` and `getTask` are `GET`s, `addTask` a `POST`, and `finishTask` (a `query` method) a `PATCH`, each drawn from `tasksApi` at its `builder.query(…)` call. `countTasks` has a `queryFn`, no request. `store/labels.ts` injects `listLabels` into the same API, so it takes `tasksApi`'s base; `/labels` has no route, so it is unmatched. `hooks/stats.ts` holds two TanStack Query hooks: a `queryFn` calling `fetch` with its own URL resolves, and one reading the URL from `queryKey` stays unresolved (not followed). The page calls the generated hooks, which aren't linked to the endpoints. `store/session.ts` follows RTK's documented re-authorization example: its `baseQuery` is a function passing its arguments on unchanged to a `fetchBaseQuery` result, so it counts as that `fetchBaseQuery` (M5C.2) and its two endpoints (built with a destructured builder, `({ query, mutation })`) reach `GET` and `DELETE /api/session` (`pages/api/session/index.ts`). The wrapper's own `rawBaseQuery("session/refresh", …)` call is a request too, from `baseQueryWithReauth`, to `pages/api/session/refresh.ts`; its two forwarding calls make none of their own.
