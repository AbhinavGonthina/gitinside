# Architecture decision records

One entry per significant decision: context, options, decision, consequences. New ADRs are appended with the next number. An ADR is never edited after the fact except to mark it **Superseded by ADR-NNNN**.

Product-level decisions trace to `../gitinside-planning/DISCOVERY.md` (`D<topic>.<n>`) and `../gitinside-planning/SPEC.md`.

## ADR-0001: Website first, GitHub App second, both in v1
- **Context:** the paste-a-URL website is the front door; the PR bot drives retention. Abhinav wants both in v1 (D1.1).
- **Options:**
  - Website only in v1.
  - Both in v1, website built first.
  - PR bot first.
- **Decision:** both are in v1. Build order is the website flow (M1–M5), then diff (M6–M7), then sign-in and the GitHub App (M8).
- **Consequences:**
  - The PR bot reuses the analyzer, diff, and viewer instead of shipping a Mermaid-only bot early.
  - Private repos arrive late (M8).

## ADR-0002: One stack, done well
- **Context:** supporting every language is startup-scale. Accuracy numbers matter more than breadth (D1.4, D2.1).
- **Options:**
  - Core TS set.
  - Full KICKOFF TS set (+TypeORM, k8s, Terraform).
  - TS + Python.
- **Decision:** v1 supports TypeScript/JavaScript only.
  - React/Next.js frontends.
  - Express and Next.js API route backends.
  - Prisma.
  - docker-compose and `.env`.
  - Monorepos via npm/yarn/pnpm workspaces and Turborepo/Nx (D2.3).
  - Detectors sit behind a plugin interface.
- **Consequences:**
  - TypeORM, Kubernetes, Terraform, tRPC, GraphQL, and other languages are v1.1+.
  - The detector interface must not assume TS internals at its boundary.

## ADR-0003: Structure is deterministic; no LLM in v1
- **Context:** if an LLM decides structure, diagrams change between runs and can't be trusted (ORIGINAL_ANALYSIS). Abhinav chose no AI in v1 (D3.3), and the budget is $0 (D8.2).
- **Options:**
  - LLM summaries only.
  - Summaries plus "Explain this".
  - No LLM.
- **Decision:** no LLM anywhere in v1. Nodes, edges, labels, and groups come from parsing and heuristics: names, folders, framework conventions, and dependencies. Same commit ⇒ byte-identical `architecture.json`.
- **Consequences:**
  - The determinism test is mandatory.
  - Inspector summaries are templated from graph facts.
  - The pitch "everything shown comes from code" is literally true.
  - AI features (v1.1) need a budget decision first (D9.1).

## ADR-0004: Real static analysis with source links
- **Context:** competitors (GitDiagram, Eraser) have a model read files and draw a diagram (D6.5).
- **Decision:** every node and edge carries a source location (file, line, column) and links to GitHub at that line. Cross-service edges come from resolving actual call sites.
- **Consequences:** the schema requires `source` on every node and edge kind except synthetic group nodes, which aggregate their children's locations.

## ADR-0005: Hierarchical, C4-style drill-down
- **Context:** large graphs become hairballs, and readability matters more than completeness.
- **Decision:**
  - Hierarchy: System → Services → Modules → Files → Symbols.
  - The top level never shows more than one node per service, datastore, and external system.
  - Children appear only when their parent is expanded.
- **Consequences:**
  - Every node has exactly one `parentId`, except the system root.
  - Edges are stored between leaves and aggregated upward at render time.

## ADR-0006: Broken-edge detection is the flagship check
- **Context:** the most valuable PR signal is "this PR removes or changes something another part still uses."
- **Decision:** the diff marks an edge `broken` when its target is removed or changed incompatibly in head while the source still references it. Covered cases:
  - Route removed or method/path changed.
  - Symbol removed or renamed without updating callers.
  - Prisma model field removed while still read.
- **Consequences:** node identity must be stable across commits (ADR-0019), and the diff needs a property-test suite.

## ADR-0007: Untrusted repos are parsed, never executed
- **Context:** anyone can submit any public repo.
- **Decision:**
  - Never install dependencies, run scripts, or evaluate code.
  - Analysis runs in a hardened container: non-root, read-only filesystem except a temp dir, network only to GitHub.
  - Each job is a child process with memory, CPU, and wall-clock limits.
  - Limits: 20k source files, 5 minutes (D2.2, D5.8). Symlinks and path traversal are rejected at extraction.
- **Consequences:** no type information from `node_modules`, so external library types resolve to `unknown` (documented per detector). Security tests are required (`docs/SECURITY.md`).

## ADR-0008: Measurement is part of the product
- **Context:** resume impact and credibility depend on real numbers (D1.4).
- **Decision:** ship the accuracy eval (5 labeled repos, precision/recall), PR backtesting (~8 repos), incremental-analysis speedup, and render/analysis benchmarks. Results are committed and reported exactly as measured.
- **Consequences:** M3 comes right after the resolver (ADR-0016). Labels are independently drafted and spot-checked by Abhinav (D10.3).

## ADR-0009: Access model
- **Context:** public use must be frictionless; private repos must be safe (D7.1–D7.4).
- **Decision:**
  - Public repos: no sign-in, cached by commit SHA, shareable links.
  - Private repos: an optional GitHub sign-in plus a GitHub App installed on chosen repos. Permissions:
    - Contents: read. Metadata: read.
    - Pull requests: read & write (comment only).
    - Checks: read & write (Check Run only).
  - Private views re-check access, cached for at most 60 seconds per user+repo. Private data never enters the public cache, and uninstall deletes it immediately.
- **Consequences:**
  - Public copy says "read-only access to your code", not "read-only".
  - Access checks need a small cache table.
  - The uninstall webhook handler is security-critical and tested.

## ADR-0010: TypeScript compiler API for parsing and resolution
- **Context:** cross-service matching needs real name resolution (imports, path aliases, axios instances) (D5.1).
- **Options:**
  - TS compiler API.
  - tree-sitter only (we'd write resolution ourselves).
  - Both.
- **Decision:** use the TypeScript compiler API (`typescript` package, `ts.createProgram` with `noResolve` off but no `node_modules` on disk) for parsing, binding, and symbol resolution.
- **Consequences:**
  - Memory grows with repo size, which drives the 20k-file limit and per-package programs for monorepos.
  - A tree-sitter plugin path stays open for other languages.

## ADR-0013: Postgres + Drizzle for metadata, R2 for snapshots
- **Context:** graph snapshots can be tens of MB; metadata is small and relational (D5.5, D5.7).
- **Decision:**
  - Postgres (Neon) via Drizzle ORM for users, repos, analyses, jobs, PR records, and the access-check cache.
  - Gzipped `architecture.json` snapshots in Cloudflare R2, keyed `public/<owner>/<repo>/<sha>.json.gz` or `private/<installationId>/<repoId>/<sha>.json.gz`. **Amended by ADR-0062:** keys end `<sha>/<analyzerVersion>.json.gz`, one object per `analyses` row.
- **Consequences:** our own repo doesn't use Prisma, so the Prisma detector is exercised through fixtures and eval repos.

## ADR-0014: BullMQ + Redis job queue
- **Context:** analysis takes up to 5 minutes and must run on the isolated worker, not in a web request. We need queuing, retries, stalled-job recovery, concurrency caps, dedupe, and progress (D5.6).
- **Options:**
  - pg-boss on Postgres.
  - BullMQ + Redis.
- **Decision:** BullMQ on Redis, co-located with the worker on the Oracle VM.
  - Redis listens only on the Docker network.
  - Job ID is `<owner>/<repo>@<sha>` (dedupe).
  - `attempts: 3` with exponential backoff; concurrency 2.
- **Consequences:**
  - The web app enqueues through a small authenticated enqueue endpoint on the worker host (Redis is never exposed publicly).
  - Abhinav learns BullMQ.

## ADR-0019: Stable node identity from qualified names
- **Context:** diffs need the same node to have the same ID across commits.
- **Decision:** node ID = `<kind>:<service>/<qualified path>`. For example:
  - `symbol:api/src/routes/orders.ts#createOrder`
  - `route:api/POST /api/orders`
  - `model:api/Order`

  File moves and renames are detected in the diff by content similarity and reported as `renamed`, not as remove + add.
- **Consequences:** IDs are human-readable and deterministic. Renames need a similarity threshold, tuned against fixtures in M6.

## ADR-0020: Inventory skips with warnings; only the file limit is fatal
- **Context:** the inventory (M1.3) decides which files the pipeline may read. "Fail visibly" says nothing may disappear silently, but one odd file shouldn't fail a whole analysis.
- **Decision** (`packages/analyzer/src/inventory.ts`):
  - A fixed list of directory names (`node_modules`, `.git`, `dist`, `build`, `.next`, `coverage`, `vendor`, …) is skipped at any depth with no warning, because skipping them is expected.
  - Everything else that gets skipped produces a graph warning: symlinks are never followed (`SKIPPED_SYMLINK`), files over 2 MB (`SKIPPED_LARGE`), directories deeper than 64 levels (`SKIPPED_DEPTH`), and generated files, meaning `*.min.js`, or in a source file's first 1 KB an `@generated` marker or "generated" and "do not edit" on one line (`SKIPPED_GENERATED`). "Do not edit" alone was dropped after the M1 review, because hand-written comments use it too.
  - More than 20,000 kept source files throws `AnalysisError` `LIMIT_FILES` with the exact count. Generated and oversized files don't count.
  - `.gitignore` is not read. GitHub tarballs only contain tracked files, so it only matters for local CLI runs.
- **Consequences:** results are deterministic and every skip can be explained in the UI. A local run may walk a gitignored folder that isn't on the list. A generated file with no marker is analyzed like hand-written code.

## ADR-0021: Services come from workspace folders, keyed by folder name
- **Context:** service keys appear in every node ID (ADR-0019), so they must be short, readable, unique, and stable across commits and machines (D2.3).
- **Decision** (`packages/analyzer/src/workspace.ts`):
  - Workspace packages are the union of root `package.json` `workspaces`, `pnpm-workspace.yaml`, and `lerna.json` patterns (Lerna's default `packages/*` if none are listed), plus every `project.json` folder when `nx.json` exists. `turbo.json` only marks the tool. Globs use a small built-in matcher, not a dependency.
  - The service key is the **folder name** (`apps/api` → `api`), not the package name, so renaming a package doesn't change every ID. Colliding names and the reserved pseudo-services `infra`/`ext` fall back to the directory with `/` → `-` (`apps-web`), then a numeric suffix, assigned in sorted order.
  - With no workspace packages, the repo is one root service keyed by its unscoped package name, or `app`. The repo's directory name is never used, because it differs between machines.
  - In a workspace repo the root package is not a service. Files outside every package belong to no service (M1.6 decides how to show them).
  - `framework` comes from `dependencies`/`peerDependencies`/`optionalDependencies` (`next` > `express` > `react`), and cycle warnings use the same runtime fields. Dev dependencies are ignored for both.
  - Invalid config, patterns matching nothing, duplicate package names, and dependency cycles are warnings, never errors.
- **Consequences:** IDs survive package renames but change when a folder moves (the diff's rename detection handles that, M6). `pnpm-workspace.yaml` is parsed with the `yaml` package, which M2.7 needs for docker-compose anyway.

## ADR-0022: One TS program per service over an inventory-only compiler host
- **Context:** cross-file resolution (imports, `paths` aliases) needs a `ts.Program` per service (D5.1), but the repo is untrusted (T1), has no `node_modules`, and may have broken or partial tsconfigs.
- **Decision** (`packages/analyzer/src/program.ts`):
  - A custom `CompilerHost` answers `fileExists`/`readFile`/`directoryExists` from the inventory only, plus TypeScript's own bundled `lib.*.d.ts`. Skipped, symlinked, and `node_modules` files are invisible, so package imports stay unresolved until M1.8 maps workspace packages.
  - Root files are every TS/JS source file the service owns (`serviceForFile`), not the tsconfig's `include`, so tests and scripts are analyzed and the graph doesn't depend on build config. The tsconfig only supplies compiler options.
  - Config lookup: `tsconfig.json`, then `jsconfig.json`, in the service folder; `extends` chains work within the repo. Missing config → `TSCONFIG_MISSING`; unparseable config or errors such as an npm-package `extends` → `TSCONFIG_INVALID`. Neither is fatal.
  - Unset options are filled from synthesized defaults (ES2022, ESNext + Bundler resolution, `jsx: preserve`); a `module` set without `moduleResolution` gets Bundler (ES kinds) or Node10, never Classic. `allowJs`, `noEmit`, `skipLibCheck`, `types: []`, and no composite/incremental/declaration always win.
  - Syntax errors become one `SYNTAX_ERROR` warning per file (first error's line:column plus a count); TS's error recovery still yields an AST. Diagnostic text has the absolute repo root stripped so warnings are identical on every machine.
  - Parsed lib files are cached per process; they come from our install and never change.
- **Consequences:** analysis never touches anything outside the repo except TS's libs. Project `references` and `include`/`exclude` are ignored, so a solution-style tsconfig contributes only its own options. Lib parsing costs ~0.5 s once per process.

## ADR-0023: Symbols are top-level declarations; exports are detected syntactically
- **Context:** symbol nodes (M1.7) are the leaves that `calls`, `handles`, and `renders` edges attach to, so they must include every function a route or page could point at, without flooding the graph with every local constant.
- **Decision** (`packages/analyzer/src/symbols.ts`):
  - Only top-level statements are read. Functions (skipping overload signatures), classes, and function- or arrow-valued `const`/`let`/`var` are always symbols. Any other variable is a symbol only when exported.
  - Methods are class methods with a body (or `abstract`) plus function-valued class properties (`handle = () => {}`). Their ID is `Class.method`, their parent is the class symbol, and they inherit the class's `exported` flag. Constructors and get/set accessors are skipped.
  - Exports are read from syntax, not the type checker: the `export` modifier, local `export { … }` lists, `export default` / `export =`, and the CommonJS forms `module.exports = x | { … }`, `exports.x = …`, `module.exports.x = …`. Exporting an identifier marks the local declaration. An inline exported value becomes a symbol under its export name, or `default` when it has none.
  - Ambient (`declare`) declarations and `.d.ts` files yield no symbols. On a name collision within a file, the first declaration wins.
  - `source` spans the declaration, starting after any JSDoc.
- **Consequences:** the result depends only on the file's own text, so it is cheap to cache per content hash (M6.7) and easy to explain. Express controllers written as `module.exports = { list: async (req, res) => … }` get named symbols for M1.10. Nested functions, `exports["x"]`, and `Object.assign(module.exports, …)` produce no symbols. Calls made inside them are attributed to the enclosing top-level symbol in M1.9.

## ADR-0024: Import edges via TS resolution, workspace manifests, and visible failures
- **Context:** `imports` edges (M1.8) are the first edges in the graph and the base for broken-connection detection (ADR-0006). There is no `node_modules`, so TypeScript alone can't resolve `@acme/shared` in a monorepo, and "fail visibly" rules out silently dropping imports that should resolve.
- **Decision** (`packages/analyzer/src/imports.ts`):
  - Specifiers come from import/export-from declarations (type-only included, since they are real file dependencies), `import x = require()`, and literal `require("x")` / `import("x")` calls anywhere in the file. Asset specifiers (`.css`, `.svg`, `.json`, …) are ignored.
  - TypeScript's `resolveModuleName` runs first, with the service's compiler options over the inventory-only host. A hit is `exact`.
  - A bare specifier naming a workspace package (longest name wins) is resolved from that package's `package.json`: `exports` (string, conditions, or exact subpath key), then `source`/`types`/`typings`/`module`/`main`, then the subpath itself, each `exact`. If those all point at missing files (usually a skipped `dist/`), `src/index` or `src/<subpath>` and then `index` are `heuristic`. `index` is `exact` when the manifest names no entry, because that's Node's default.
  - A specifier that must be local (relative, absolute, `@/`, `~/`, `#`, a non-`*` `paths` key, or a workspace package) but doesn't resolve becomes an `unresolved` node with reason `UNKNOWN_SYMBOL`, parented to the importing service, ID `unresolved:<service>/<file>:<line>:<column>`. Other bare specifiers are third-party packages and get no edge yet (M2.6 handles SDKs).
  - A target in the repo but outside every service is an `IMPORT_OUTSIDE_SERVICE` warning, not an edge.
- **Consequences:** imports of skipped files (generated, oversized) show up as unresolved, which is honest. `exports` wildcards (`./*`) and `typesVersions` aren't followed. `UNKNOWN_SYMBOL` is reused rather than adding a schema reason, so the schema stays at 1.0.0. Unresolved IDs carry the column, so two imports on one line can't collide.

## ADR-0025: Call edges via the type checker, with workspace imports bridged by hand
- **Context:** `calls` edges (M1.9) feed trace mode and broken-connection detection, so they must point at real declarations. TypeScript's checker resolves calls precisely within a program, but there is no `node_modules`, so it can't follow `import { f } from "@acme/shared"` into another workspace package, which is exactly where architecture lives in a monorepo.
- **Decision** (`packages/analyzer/src/calls.ts`):
  - The caller is the innermost extracted symbol (ADR-0023) whose declaration contains the call. Calls in nested functions and callbacks belong to the enclosing top-level symbol. Top-level calls have no caller and produce no edge.
  - The callee name (`f`, the `m` of `a.m`, `a["m"]`, or the class of `new C()`) is resolved with `getSymbolAtLocation`, following aliases, re-exports, `{ list }` / `{ list: impl }` properties, and `const a = b`, up to 8 hops. A declaration maps to a symbol node by repo path, node kind, and text span, so a file loaded into another service's program still matches.
  - When an alias points at a module TypeScript couldn't resolve, the import is resolved with the M1.8 resolver (now shared as `createModuleResolver`) and the name is looked up among the target module's exports with the target service's checker, so re-export chains work. The edge takes the import's confidence (`heuristic` for `src/index` fallbacks); everything else is `exact`.
  - Unresolved callees produce no edge or `unresolved` node: third-party and built-in calls are the overwhelming majority, and showing them would bury the diagram. Local imports that fail are already visible as unresolved `imports` edges. Recursion (self-edges) is skipped.
- **Consequences:** precision is high because nothing is guessed. Recall misses untyped values (methods on instances of classes from another workspace package, parameters called as callbacks), computed element access, and `require` of workspace packages. Call sites record the callee name's position.

## ADR-0026: Express routes from tracked router objects, composed over a mount graph
- **Context:** route nodes (M1.10) are what M2's matcher links frontend calls to, so their full paths must be right. Express builds paths at runtime (`app.use("/api", r)` + `r.get("/users/:id")`), routers travel across files and through functions, and there are no `express` types (no `node_modules`), so the checker can't tell an Express `get` from `Map.get`.
- **Decision** (`packages/analyzer/src/express.ts`):
  - **Router objects** are found syntactically: calls to `express()`, `express.Router()`, or `Router()` where the name is bound to `express` by a top-level import or `require`, plus parameters typed `Express`/`Application`/`Router` from `express`. Only calls on an expression that resolves to one of these count as routes or mounts. Resolution uses the checker to follow variables, imports, `export default`, CommonJS `module.exports`/`require`, object properties, class properties, chained calls (`router.get()` returns the router), and factory functions that return a router.
  - **Parameter binding:** a call `f(app)` where `app` resolves to a router makes `f`'s parameter an alias of it (a mount at `""`), repeated until no new parameter appears (at most 8 rounds). This covers `module.exports = (app) => { app.get(…) }` without types.
  - **Composition:** mounts form a graph; a depth-first walk from every unmounted app or router joins prefixes (one `/` between segments, no trailing `/`). A router mounted twice yields its routes twice. Cycles are cut; routers mounted only inside a cycle are walked from the first one seen.
  - **IDs:** `route:<service>/<METHOD> <path>`, where the service is the root app's (the deployment that serves it), and the parent is the file that registers the route. Duplicate registrations merge; the earliest source wins.
  - **Failures stay visible:** a non-static route path or mount prefix makes each affected route an `unresolved` node (`DYNAMIC_ROUTE`, expression like `GET process.env.PREFIX + /users`), parented to the service, with no edge. A router never mounted on an app gets an `EXPRESS_UNMOUNTED_ROUTER` warning and keeps router-relative paths.
  - **Handlers:** every handler argument (including middleware and arrays) that resolves to a symbol node via the M1.9 resolver (now `createSymbolResolver`, shared) gets a `handles` edge.
- **Consequences:** routes are only found on objects provably created by Express, so precision is high; a local `http.get(path, cb)` never becomes a route. Inline arrow handlers and wrapped handlers (`asyncHandler(fn)`) get no `handles` edge, which breaks the route → logic chain for those apps; M2 may revisit. Routers imported from other workspace packages, routers in collections or loops, and constructor-assigned properties without initializers are missed, which shows up as an `EXPRESS_UNMOUNTED_ROUTER` warning when the router side is visible.

## ADR-0027: Next.js routes and pages from the file system, exports from the checker
- **Context:** Next.js apps (M1.11) declare routes by where files sit, not by calls, so paths are always static. What varies is how a route file exports its handlers (`export function GET`, `export const { GET, POST } = handlers`, `export { h as GET }`, re-exports), which router folder is live, and what the pages router's API handlers accept.
- **Decision** (`packages/analyzer/src/next.ts`):
  - Only services that declare `next` as a dependency are scanned, so an unrelated `pages/` folder never becomes routes. Router folders are `app/` and `pages/`, or `src/app/` and `src/pages/` when neither root folder holds a source file (Next's rule). Only the default page extensions count; `next.config` is never read.
  - **Paths:** `[id]` ⇒ `:id`, `[...x]` and `[[...x]]` ⇒ `*x`, `(group)` and `@slot` dropped, `index` maps to its folder. App router `_private` folders and intercepting routes (`(.)x`, `(..)x`, `(...)x`) produce nothing.
  - **Route handlers:** the method names come from `checker.getExportsOfModule`, so every export form (including re-exports and `export *` from local files) counts. Each exported method becomes `route:<service>/<METHOD> <path>` with a `handles` edge to the symbol the export resolves to (the shared resolver, ADR-0025). A `route.ts` with no method export gets a `NEXT_ROUTE_NO_METHODS` warning rather than vanishing.
  - **Pages router API:** method `ALL`, unless the default-export function compares its request's `method` with string literals (`===`, `!==`, `switch`, `[...].includes`, also through `const { method } = req`); then one route per method named. A `!==` guard counts, because `if (req.method !== "POST") return 405` means the route is POST. When other methods may still fall through to real code (no negative guard, `switch` `default`, `405`, or `Allow` header, and the checks aren't in the handler's last statement without a final `else`), `ALL` is emitted too, so the fall-through in `if (GET) return list(); return create();` stays visible as `ALL` (revised after the M1 fresh-eyes review). Type-only exports (`export type GET`) are not routes.
  - **Pages:** `page:<service>/<path>` (frontend layer) with a `renders` edge to the default export.
  - **Collisions:** two files mapping to one ID keep the first by path with a `NEXT_DUPLICATE_ROUTE` warning. When a custom Express server registers the same route, the Express node wins and both `handles` edges are kept.
- **Consequences:** no `unresolved` nodes are needed, since file-system paths are always static. `basePath`, `pageExtensions`, `i18n`, rewrites, and middleware are invisible until v1.1; a repo using `basePath` gets wrong paths with no warning, which M3's eval should catch. Optional catch-alls lose the "also matches the parent" detail. Wrapped API handlers (`export default withAuth(h)`) stay `ALL`.

## ADR-0028: Prisma models from a line parser, client usage traced to `new PrismaClient()`
- **Context:** Prisma (M1.12) is the data layer of v1. The schema is its own language, and the client's types are generated into `node_modules`, which we never have. So the checker can't tell `prisma.user.findMany()` from any other `a.b.c()` call by type, and Prisma's own parser ships as an engine binary or WASM, which we won't load to read untrusted input.
- **Decision** (`packages/analyzer/src/prisma.ts`):
  - **Schema:** a small line-based parser reads `model`, `view`, and `datasource` blocks from every `.prisma` file (so multi-file schemas work), ignoring `//` comments outside strings. Unreadable lines become a `PRISMA_SYNTAX` warning; the rest of the file is still used. Models are `model:<service>/<Name>`, parented to their schema file, so they sit with the other code of their folder when drilling down.
  - **Datastores:** a literal `provider` becomes `datastore:infra/<service>/<schema file>#<datasource>` with a normalized engine (`postgresql` ⇒ `postgres`), plus `stores` edges from that file's models (or the whole service's when its multi-file schema has one datasource). The ID includes the service and file, because two services both on Postgres may well be two databases; merging them would be a guess. M2.7 links these to compose services.
  - **Client tracing:** a receiver is a client when the checker follows it (variables, imports including workspace packages via a new `importTarget` hook on the shared resolver, default and CommonJS exports, class properties, `??`, ternaries, `$extends`, factories) to `new PrismaClient()`, a class extending it, or a declaration typed `PrismaClient`/`TransactionClient`; `$transaction` callback parameters count too. These edges are `exact`. An untraced receiver named `db`, `database`, `client`, `tx`, `trx`, or `*prisma*` whose accessor and op both match counts as `heuristic`, because tRPC-style `ctx.db` is common and untyped without `node_modules`.
  - **Model lookup:** the schema of the service that created the client, then the calling service's, then the only service that has the model. Several candidates make an `AMBIGUOUS` unresolved node; a traced client naming no known model makes `UNKNOWN_SYMBOL`. Raw queries (`$queryRaw`, `$executeRaw`, …) make `RAW_QUERY` unresolved nodes. All three keep `reads`/`writes` edges to the unresolved node, so nothing is dropped.
  - **Edge source:** the innermost symbol, or the Express route when the call is in an inline handler. The Express detector now returns `inlineHandlers` (handler function ⇒ route IDs, one wrapper call deep) for this.
  - **Field-level usage:** `GraphEdge` gains an optional `fields: string[]`, the model fields named in top-level `select`/`include`/`where`/`data`/… keys, filtered to real field names and sorted. The schema stays at 1.0.0: the key is optional and additive, and no graph has been published yet.
- **Consequences:** precision stays high because the exact tier requires a provable client. Recall misses delegates in variables, destructured clients with unusual names, generic repository wrappers, and nested writes (`data: { posts: { create } }` lists `posts` on the parent but draws no edge to `Post`). `@@map` table names are ignored. The heuristic tier is a measured risk: M3's eval reports it separately by confidence.

## ADR-0029: One assembly step merges pass outputs; writes validate the serialized text
- **Context:** by M1.12, `analyze()` concatenated each pass's nodes and edges by hand and filtered Next.js items that Express already produced. Every new detector (M2's HTTP, compose, queues, SDKs) can emit an ID another pass also emits, and each would need its own ad hoc filter. A collision would then either crash `parseGraph` with a raw Zod error or be silently dropped.
- **Decision** (`packages/analyzer/src/assemble.ts`):
  - `assembleGraph` takes the passes as ordered `GraphPart`s; the order is the precedence. The first node per ID wins. A later node with the same ID but different content is dropped with a `DUPLICATE_NODE` warning naming both passes (fail visibly); an identical one merges silently.
  - Edges with one ID merge: sites and `fields` are unioned, and the strongest confidence is kept (exact > pattern > heuristic), since a pass that proved the edge outranks one that guessed it. `unresolved` can't compete, because it's fixed by the target node.
  - Exact duplicate warnings are removed. The in-memory graph keeps pipeline order; `stringifyGraph` alone applies the canonical order on write.
  - A schema failure becomes `AnalysisError` `INVALID_GRAPH` listing the first 5 issues with their paths. It always means an analyzer bug.
  - `serializeGraph` runs `stringifyGraph`, parses the text back, and validates it, catching values JSON can't carry (`NaN` ⇒ `null`). The CLI writes `--out` through a temp file and a rename, so a failed run never truncates an existing graph.
- **Consequences:** detectors stay independent; precedence lives in one list in `analyze()`. Validating twice costs a few milliseconds per graph, negligible next to parsing.

## ADR-0030: HTTP call sites are collected as records with "unknown" kept distinct from "absent"
- **Context:** M2's resolver is split into collect (M2.1), normalize (M2.2), wrappers (M2.3), match (M2.4), and unresolved output (M2.5). The ROADMAP requires that no collected call site is silently dropped. Without `node_modules`, axios is an unresolvable import, so the checker can't type `api.get()`; and request configs are often built at runtime.
- **Decision** (`packages/analyzer/src/http.ts`):
  - `collectHttpCalls` returns sorted `HttpCallSite` records (client, program, call, site, owners, method, URL, base URL, confidence) and emits no graph output yet. Later stages consume the records.
  - **`null` means "set, but not statically readable"; `undefined` means "not set".** A `fetch` without `init.method` is `GET`; one whose `init` is an unknown variable or contains a spread before `method` has method `null`. A config property after the last spread is read; one that a spread could supply is `null`. M2.5 turns every `null` into an unresolved edge with a reason rather than a guess.
  - **axios is recognized from its import, not its types:** the default or namespace import of `"axios"`, `require("axios")` (in JS files TypeScript models it as an alias, so the alias's own declaration is checked before following it), and instances from `.create(config)` traced like the Prisma client (variables, imports incl. workspace packages, exports, operators, factories, object properties). A declaration typed `AxiosInstance` is an instance with an unknown base URL.
  - **`axios(x)`** is the URL form only when `x` is string syntax or string-typed; otherwise it's the config form, so an untyped `x` gives an unknown URL and method instead of treating a config object as a URL.
  - **Shorthand calls** (`api.get(url, cfg)`) with an unreadable `cfg` keep the instance's base URL: overriding `baseURL` per call is rare, and marking every such call unknown would hide the common case. This is listed under "not handled".
  - Only the global `fetch` (or one from `node-fetch`, `undici`, …) counts. A repo function named `fetch` is a wrapper, left to M2.3.
  - Axios results are memoized per checker symbol (in-progress symbols map to `null`, which also stops cycles). On cal.com the pass collects 217 sites in 2.7 s after the `calls` pass has warmed the checkers.
- **Consequences:** M2.2 receives expressions together with the program whose checker understands them, so a base URL defined in another workspace package resolves its imported consts in that package. Recall misses other clients (`ky`, `got`, `ofetch`), destructured instance methods, instances assigned in constructors without a type, and `defaults.baseURL` mutations.

## ADR-0031: URLs normalize in two layers, parts then pattern, and a leading hole is `DYNAMIC_URL`
- **Context:** M2.2 turns each call site's URL and `baseURL` expressions into something the route matcher (M2.4) can align with route paths. The same evaluation must later run with wrapper parameters bound (M2.3), and ROADMAP M2 asks for a property test of normalizer idempotence.
- **Decision** (`packages/analyzer/src/url.ts`, shared tracing in `values.ts`):
  - **Two layers.** `parts()` evaluates an expression to a flat list of `text`, `hole`, `env`, and `origin` parts using the checker (consts through imports and workspace packages, const objects incl. nested ones, string enums, single-literal types, env reads, `location.origin`, `new URL`). `toUrlPattern()` is pure: it reads the parts as a base (`path`, `page`, literal `host`, or `env`) plus segments of text and holes. The pure layer is what the fast-check properties test; `patternParts()` is its inverse, so idempotence is `toUrlPattern(patternParts(p)) = p`.
  - **A URL starting with a hole is `DYNAMIC_URL`,** and so is a non-host URL whose segments are all holes, or a host with a hole before the port. There is nothing to match such a URL on, and treating `${base}/users` as `/users` would be a guess. The result carries a fixed English `detail` for the UI.
  - **Env vars are bases only at the start.** `env ?? "http://localhost"` and `env || …` read as the env var, since the env var is the deployed value; the matcher (M2.4) decides from the name whether it means "same deployment" (heuristic).
  - **axios joining copies axios** (`combineURLs`/`isAbsoluteURL`): an absolute URL ignores `baseURL`, an empty base is no base, otherwise one `/` joins them. **`new URL(u, base)`** uses Node's WHATWG parser only when both are literals; a root-relative `u` keeps the base's origin (literal, env, or page origin); anything else is a hole, because the base's path is unknown.
  - **Query strings and fragments** are cut at the first literal `?`/`#`; empty segments are dropped; scheme and host are lowercased, the path isn't.
  - **Confidence:** a resolved URL is `exact` unless a value came through a heuristic workspace import, in which case it takes that import's confidence.
  - `constString`, `constObject`, `objectProperty`, and `resolveDeclaration` moved from `http.ts` into `values.ts` so the collector and the normalizer read values the same way. `http.ts` behavior is unchanged (its tests pass untouched).
- **Consequences:** a wrapper body like `fetch(BASE + path)` normalizes to `/api{}` today; M2.3 will bind `path` to the caller's argument and re-run `parts()`. On cal.com 130 of 217 sites resolve (41 root-relative, 74 literal host, 15 env base) and 87 are `DYNAMIC_URL` (82 start with a runtime value, 4 have a runtime host, 1 has an unreadable URL), almost all URLs held in variables or parameters or built by function calls (e.g. `WEBAPP_URL = ensureProtocol(process.env.…) || …`). Normalizing all 217 takes 69 ms.

## ADR-0032: Wrappers inline one level by re-normalizing with bound parameters; each wrapper call is its own request
- **Context:** M2.3. Real clients route requests through helpers (`fetcher(endpoint, init)`, `api.get(path)`), so the `fetch` inside the helper reads a parameter and is `DYNAMIC_URL` or `/api{}` on its own, and its method is often hidden behind `{ method: "GET", ...init }`. The URL that matters is at each call to the helper. DESIGN.md §7.1 asks for one level of inlining and `WRAPPER_DEPTH` beyond.
- **Decision** (`packages/analyzer/src/wrappers.ts`, plus small hooks in `url.ts` and `http.ts`):
  - **A wrapper is a symbol (M1.7) whose function directly contains a call site that reads one of its parameters** in the URL, `baseURL`, or method. Nested closures and functions that aren't symbols are not wrappers: their sites stay as they are.
  - **Callers are found with the shared symbol resolver** (M1.9), so imports, renamed and default imports, namespaces, class instances, and workspace packages work the same as call edges. Only calls spelled like a wrapper's name or made through an import alias are resolved, to keep the scan cheap.
  - **Inlining re-runs the M2.2 normalizer with bindings** (parameter declaration ⇒ caller argument, else the parameter's default). The argument is evaluated in the caller's scope with the bindings switched off, so recursion terminates. Unbound parameters are holes marked `param`.
  - **`WRAPPER_DEPTH`:** while inlining, a URL or `baseURL` that still starts with a `param` hole came from the caller's own parameter, so only a second level could resolve it. A `param` hole later in the URL (`get(\`/users/${id}\`)`) is an ordinary hole.
  - **Each wrapper call becomes its own `HttpRequest`**, located at and owned by the caller, with `via` pointing at the wrapper call and `call` at the inner site. The inner site yields no request of its own when it has callers; a wrapper with no visible callers keeps its own request. So every collected site is represented at least once (ROADMAP's "no call site dropped").
  - **Methods:** `HttpCallSite.methodSource` records where an unreadable method came from (a `method` value, an unlocatable config, or the spreads in a config literal with the `method` before them). Inlining reads it with the bindings: the last spread that sets `method` wins, and a missing argument spreads nothing, so `fetcher("/rooms")` is `GET` and `fetcher("/rooms", { method: "POST" })` is `POST`.
  - **Confidence** is the weakest of the call site's, the URL's, and the wrapper call's resolution.
- **Consequences:** on cal.com, 27 of 217 sites are wrapper bodies; inlining turns them into 79 requests (269 in total, 0 sites dropped). Resolved requests rise from 130 to 157, and inlined methods that were unknown now read `GET`/`POST`/`PATCH`/`DELETE`. Inlining takes 1.3 s, mostly resolving candidate calls. A forwarded parameter in the middle or at the end (`fetcher(endpoint, …)` ⇒ `https://api.daily.co/v1{}`) stays a hole rather than `WRAPPER_DEPTH`: telling a forwarded sub-path from a path parameter would be a guess, so the matcher (M2.4) sees the hole. Destructured parameters, `arguments`, reassigned parameters, URLs held entirely in a config parameter, and invisible (callback) callers are not handled; the file comment lists them.

## ADR-0033: Routes match on base, method, and path levels; ties break on path, then method; ambiguity floors at heuristic
- **Context:** M2.4. DESIGN.md §7.4 defines segment rules and three confidence levels, but leaves open how the base and method combine with the path, what happens to an unreadable method, what "downgrade one level" means for a heuristic match, and where an edge from top-level code starts.
- **Decision** (`packages/analyzer/src/match.ts`):
  - **Three independent levels, weakest wins.** Base: root-relative is `exact` within the caller's service and `heuristic` across services (it assumes a proxy or rewrite); page-relative is `heuristic`; an env var is `heuristic` only when named `API_URL`/`BASE_URL`/`*_API_URL`/`*_BASE_URL`; a loopback host is `heuristic` against every service; any other literal host is an external API and never a route. Method: equal, `ALL`, or `HEAD` → `GET` is `exact`; an unreadable method matches every method at `heuristic`. Path: the §7.4 segment rules, plus optional params (absent is `exact`) and partly literal segments (`user-{}`), which may spell a literal or fill a param at `pattern`. A pure hole never matches a literal. The result is then no stronger than the request's own confidence.
  - **Tie-breaks before ambiguity.** At the best overall level, the best path level wins: under an env base every match is `heuristic`, and without this `/api/users/me` would tie with `/api/users/:id`. Then a route with the request's method beats an `ALL` route (the pages router's fall-through `ALL` is the same handler). Remaining ties are real ambiguity. There's no further "more specific route" rule: Express picks by registration order, which isn't visible across files, so `/v1/acme/items` against `/v1/:org/items` and `/v1/:org/:kind` links both.
  - **Ambiguity downgrades one level but not below `heuristic`.** `unresolved` would require an `unresolved` target node (integrity rule 5), and the candidates are real routes. The edge records `reason: "AMBIGUOUS"`; when the same (owner, route) edge also has an unambiguous site, the strongest confidence wins and the reason is dropped.
  - **Path alignment is dynamic programming** over (call segment, route segment), so wildcards and optional params cost O(n·m), never backtracking. Partly literal segments use greedy leftmost glob matching, not a RegExp.
  - **Route index:** method, then first literal segment, with a catch-all bucket for routes starting with a param or wildcard. A call whose first segment is a pure hole only scans the catch-all bucket.
  - **Edge source:** each owner symbol or inline-handler route; top-level code uses its file node. A request in a file outside every service with no owner gets no edge yet (M2.5).
  - **Outcomes, not just edges.** `match()` returns `routes`, `external` (literal host), or `unresolved` (`DYNAMIC_URL`, `WRAPPER_DEPTH`, `NO_MATCHING_ROUTE` with a detail). M2.4 draws edges only for `routes`; M2.5 turns the rest into unresolved and external nodes.
  - `weaker()` in `values.ts` now ranks all four levels (it previously assumed only `exact`/`heuristic`, which was all its callers passed).
- **Consequences:** on cal.com, the `http` stage emits 38 edges from 41 sites (22 exact, 7 pattern, 9 heuristic, 0 ambiguous) in 3.8 s, almost all of it collection and inlining. Until M2.5, requests that match no route are absent from the graph. M3's eval should measure whether the cross-service `heuristic` for root-relative URLs and the env-name pattern are too strict or too loose.

## ADR-0034: Unmatched requests become unresolved nodes at the call site; literal hosts become external nodes
- **Context:** M2.5. After M2.4, requests that matched no route were dropped from the graph, which breaks "fail visibly" and ROADMAP M2's "no call site dropped". DESIGN.md §7.4 says what to create, but not which edge kind points at an external, where an inlined request's node sits, how hosts are keyed, or where the matcher's readable detail goes.
- **Decision** (`buildHttpEdges` in `packages/analyzer/src/match.ts`):
  - **Unresolved:** one `unresolved` node per request site (`unresolved:<service>/<file>:<line>:<column>`, under the service), at the wrapper call when inlined, since that is where a reader can act. `reason` is the matcher's (`DYNAMIC_URL`, `WRAPPER_DEPTH`, `NO_MATCHING_ROUTE`); `expression` is the call's source text (whitespace collapsed, cut at 120 characters, the helper now shared with Prisma in `values.ts`); `label` is `METHOD url` when the URL was read, else `METHOD <url source>`. Each owner (or the file node, for top-level code) gets an `http` edge to it at `unresolved`. Several requests at one site share its node; the first request's reason wins.
  - **New optional `detail` field on `unresolved` nodes** (schema): the matcher's sentence ("the URL starts with a value only known at runtime"). The reason code alone doesn't tell a user what to fix. It's additive and optional; `SCHEMA_VERSION` stays `1.0.0` because no graph has been published or consumed yet.
  - **External:** a literal non-loopback host becomes `external:ext/<host>` under the system (layer `external`), with an `external_call` edge (not `http`, which GRAPH_SCHEMA reserves for routes and unresolved targets). Confidence is `exact`, or the request's own weaker confidence (a workspace-imported axios instance). Hosts are lowercased (M2.2), credentials (`user:pass@`) are dropped in `toUrlPattern` so they never reach the graph, and a scheme's default port is dropped so `:443` doesn't split a node. No edge label: one edge merges many endpoints of one host.
  - **Edge merging:** an edge keeps a `reason` only when every merged site gave it (this generalizes M2.4's `AMBIGUOUS` rule).
  - `EXTERNAL_HOST` stays in the reason enum but is unused: a literal external host is a resolved `external` node, not an unresolved one.
- **Consequences:** on cal.com all 269 requests reach the graph: 38 route edges (unchanged), 135 unresolved nodes (112 `DYNAMIC_URL`, 23 `NO_MATCHING_ROUTE`, every one with an edge), and 79 `external_call` edges to 26 external hosts. Most `DYNAMIC_URL`s are `${WEBAPP_URL}/…` where `WEBAPP_URL` is a function result. 16 `NO_MATCHING_ROUTE`s target cal.com's v2 API (15 under `NEXT_PUBLIC_CALCOM_API_URL`, plus `/api/v2/slots/available`), whose NestJS routes v1 doesn't detect. Every request now reaches the graph (a request with no owner and no file node keeps its unresolved node with no edge, which can't happen for files inside a service). M2.6 adds SDK calls to the same `external` nodes, so its IDs and labels must use `externalHost()`.

## ADR-0035: SDK calls are traced to allowlisted client packages and keyed by the API's host
- **Context:** M2.6. ROADMAP lists an allowlist (stripe, `@aws-sdk/*`, resend, openai, twilio, `@sendgrid/*`, …) but not what counts as a call, which host an SDK maps to, or how an SDK node relates to the `external` nodes `fetch` calls already create (ADR-0034). Without `node_modules`, the checker knows nothing about an SDK's types, so `stripe.customers.create` has no symbol.
- **Decision** (`packages/analyzer/src/sdk.ts`, new `sdk` stage after `http`):
  - **One node per API host, shared with `fetch`.** Each package maps to its documented default endpoint (`stripe` ⇒ `api.stripe.com`), and nodes come from `externalNode()` in `match.ts`, so an SDK call and a literal-host `fetch` to one API produce byte-identical nodes that assembly merges silently, and edges from one symbol merge into one `external_call` edge. Edges are unlabeled, like `fetch` ones: a label would show or vanish depending on which pass produced the edge first.
  - **Families:** every `@aws-sdk/client-<name>` is accepted; listed clients use their real endpoint prefix (`ses` ⇒ `email.amazonaws.com`) at `exact`, others use `<name>.amazonaws.com` at `heuristic`, since that host is inferred from a package name. Every `@googleapis/<api>` maps to `www.googleapis.com`.
  - **Values are traced like axios instances** (ADR-0030): imports, `require`, variables, exports, workspace packages (at the import's confidence), and factories, including factories exported from workspace packages. An SDK value records its export path (`default`, `*`, `S3Client`, `calendar_v3.Calendar`) until it becomes a client, so `new X()` only counts when `X` is a client export: the default, a listed class, a `*Client` name, or a package pattern.
  - **A request is a method call on an SDK module value or client**, matched by the shortest SDK prefix of the callee. Calls on results aren't followed (one site per chain), calls that build a client (`google.calendar({ auth })`) aren't requests, and each package lists methods that run locally (Stripe `webhooks`, SendGrid `setApiKey`, AWS `destroy`).
  - **Types count only for client names**, so `out: GetObjectCommandOutput` is data, not a client, and `c: Stripe` is.
- **Consequences:** precision over recall: destructured clients, untyped `this.x = new Stripe()`, and directly called named exports are missed and listed under "not handled". Local helpers outside the `local` lists still draw an edge; this over-reports a dependency the code really has, never invents one. SDKs whose host is per-account (Supabase, Algolia, Salesforce), SMTP, and telemetry are off the list, so they get no edge, as with any third-party package (ADR-0024).

## ADR-0036: Compose services are the datastores; env URLs only link to them, and their values never leave the parser
- **Context:** M2.7. ADR-0028 gave each Prisma datasource its own datastore node and deferred the link to compose. ADR-0005 says the top level shows one node per datastore, so a Prisma `postgres` and a compose `postgres` that are the same database must not be two nodes. `.env` files hold real credentials, and SECURITY.md T5 allows reading key names and URL schemes/hosts only.
- **Decision** (`packages/analyzer/src/infra.ts`, new `infra` stage after `prisma`):
  - **Compose services with a known image are the nodes.** `datastore:infra/<dir>/<service>` (root: `datastore:infra/<service>`, as GRAPH_SCHEMA's example), or `queue:` for brokers, labeled with the service name. Files in one folder are one Compose project, so override files merge their host names and published ports into one node. Images match on the path without registry, `library/`, tag, or digest. Parsing uses `yaml` with merge keys on and at most 100 alias expansions; parse errors are reported by line with our own message, because yaml's can quote the file.
  - **Env files are parsed into keys and `{ scheme, host, port }` only.** Credentials, paths, and queries are dropped inside `parseEnv`; hosts are only compared against compose names, never written. Multi-line quoted values are skipped whole so their contents can't be read as keys.
  - **A Prisma datasource becomes a compose node** when its `url = env("KEY")` value (from env files in the schema's folder or above) names the service's host (`exact`), or a loopback host and a port the service publishes (`heuristic`). With no URL value at all, a lone compose service of that engine is linked (`heuristic`). Several candidates keep the Prisma node and warn `INFRA_AMBIGUOUS_DATASTORE`; a URL pointing elsewhere keeps it silently. `relinkStores` drops the linked Prisma node and retargets its `stores` edges, so the node count drops by one per link.
  - **Env-only datastores:** a URL key with an engine scheme that no datasource reads (`url`, `directUrl`, `shadowDatabaseUrl`) and no compose service serves becomes `datastore:infra/env#<KEY>`, labeled with the engine. The `#` keeps it apart from compose IDs, which can't contain one.
  - **`*_API_KEY` keys produce nothing.** A key is not a connection; SDK calls already draw the edge (ADR-0035). DESIGN.md's infra list is updated to match.
- **Consequences:** on cal.com, the 102 models of `packages/prisma` now store into `datastore:infra/packages/prisma/postgres` (`heuristic`: `.env.example` says `localhost:5450`, the compose file publishes `5450:5432`), and the separate Prisma datastore is gone. 6 compose datastores appear, including `postgres_is_ready`, a health-check container running the `postgres` image: an image says what a container runs, not whether it holds data. M3's eval should check whether skipping services with an overridden `command`/`entrypoint` is worth it. A literal Prisma `url`, `prisma.config.ts`, and compose `extends`/`include` are not handled.

## ADR-0037: Queues are identified by name; producers and workers meet at `queue:infra/redis#<name>`
- **Context:** M2.8. ROADMAP asks for BullMQ and known queue clients (`new Queue(name)`, `queue.add`, `new Worker(name)`) ⇒ `publishes`/`consumes`. A producer and its worker usually live in different services and hold different objects: what they share is the queue name (and a Redis server). GRAPH_SCHEMA already showed `queue:infra/redis#receipts`. A name built at runtime has no unresolved reason that fits (`DYNAMIC_URL` is about URLs).
- **Decision** (`packages/analyzer/src/queues.ts`, new `queues` stage after `sdk`):
  - **Libraries:** `bullmq` (`Queue`, `Worker`, `FlowProducer`), `bull`, `bee-queue`. All three are Redis-backed, so the engine is `redis` and the node is `queue:infra/redis#<name>`, labeled with the name, sourced at the first site that names it. The `#` keeps it apart from compose queue IDs. One name is one node whatever the library, `prefix`, or connection: telling those apart needs runtime config.
  - **Instances are traced like SDK clients** (ADR-0035), including workspace packages at the import's confidence and factory functions. A factory's parameters are bound to each call's arguments (or defaults), so `getQueue("email").add()` publishes to `email`.
  - **Edges:** `publishes` from the code that calls `add`/`addBulk`/`upsertJobScheduler` (Bull `add`/`addBulk`, Bee-Queue `createJob`), and each `queueName` in a BullMQ flow. `consumes` from the processor function's symbol when it resolves, else the code that creates the worker (`new Worker`, Bull/Bee `process`). Both are edges from code to the queue, as GRAPH_SCHEMA has them, so trace mode (M4b.6) must follow `consumes` edges in reverse to get from a queue to its workers.
  - **Worker factories.** When a `new Worker(name, …)` reads its name from its function's parameter, that function is a factory: a second walk traces only calls whose callee has the factory's name, binds them, and drops the factory's own unresolved edge once it has a call. Nested factories are found in later rounds. Tracing every call in the repo as a possible factory cost 2.8 s on cal.com with nothing to find; the name filter brings the stage to 0.8 s. The stage also skips repos where no source file quotes a library name.
  - **New unresolved reason `DYNAMIC_NAME`** (schema enum, additive, so `SCHEMA_VERSION` stays `1.0.0` as with `detail` in ADR-0034). The unresolved node sits at the name expression, or at the call when the queue came from a type annotation (`private queue: Queue`), with a detail saying which.
- **Consequences:** cal.com has no edges: its only queue code is NestJS `@Processor`/`@InjectQueue`, which v1 doesn't detect (no NestJS, like its routes in ADR-0034). Queue nodes aren't linked to a compose Redis node; there is no edge kind for "queue lives in datastore", and adding one belongs with the viewer work. Publishing wrappers (`enqueue(name, data)`), queues kept in maps, and renamed factory imports are listed under "not handled"; the last two show up as unresolved or missing, never as a wrong queue.

## ADR-0038: Unresolved requests show their source with string contents masked
- **Context:** M2.9's `fake-secrets` fixture found a leak. An unresolved HTTP node's `expression` (and, for wrapper calls, its label) was the whole call's source text, so `fetch(target, { headers: { Authorization: "Bearer …" } })` copied a hardcoded token into the graph, and a key in the query of a runtime URL (`` `${base}/items?api_key=…` ``) reached the label too. SECURITY.md T5 covers hardcoded keys, and graphs of public repos are served from a CDN.
- **Decision** (`redactedText()` in `packages/analyzer/src/values.ts`, used by `buildHttpEdges`):
  - **Text shown for an unresolved request keeps the code's shape but not its strings.** Every string and template literal's contents become `…`, except inside the URL: the `fetch`/axios URL and per-call `baseURL` expressions, or for an inlined wrapper call the arguments bound to parameters its URL reads (new `WrapperCall.url`). Inside the URL, literal text is kept up to and including the first `?`; everything after it is masked, so the path stays readable and the query doesn't.
  - **Kept as written:** identifiers, operators, empty strings, quoted property names (`"x-api-key":`), and `method` values. None of them carries a value a user typed as a secret.
  - **Not applied** to Prisma `RAW_QUERY` expressions (the SQL is what the user needs to see) or queue `DYNAMIC_NAME` expressions (the name expression itself). Both show only the unresolved expression, not neighbouring arguments.
  - **Alternatives rejected:** masking only strings that look like keys (a guess, and token formats vary); dropping `expression` (the user then can't tell which call it was).
- **Consequences:** no golden changed (no earlier fixture had a string outside a URL in an unresolved call). The secret-leak test checks the serialized `fake-secrets` graph for every planted value, from env files, compose, literal URL credentials, headers, a query string, and a wrapper argument. A hardcoded secret *inside the path* of an unresolved URL is still shown; that's a path segment, not a credential slot, and reads as one in code review.

## ADR-0039: M2 review fixes: budgets on repo-controlled evaluation, wider masking, no empty names
- **Context:** M2.11's fresh-eyes review ran hostile scratch repos against the built analyzer. Nine lines of consts that each repeat the last ten times took 70 s in the URL normalizer and put a 10-million-character label in the graph. Seven factories that each return ten calls of the next took 110 s in axios tracing (same shape in SDK tracing). `fetch("https:///x")`, `new Queue("")`, or a compose service named `""` produced an empty label or host, so validation threw and the whole analysis failed. `redactedText` kept `${base}&token=…` and `sign("/x", "key")` strings because they sat inside the URL before any `?`. Typed-queue `DYNAMIC_NAME` nodes copied the whole call, payload included.
- **Decision:**
  - **Budgets, not just depth limits.** `MAX_HOPS` bounds depth, not branching. The normalizer now counts expressions per `parts()` call (`MAX_STEPS` = 10,000) and caps literal text at `MAX_TEXT` = 2,048 characters. Either one produces an `overflow` hole, and the URL becomes `DYNAMIC_URL` with the detail "the URL is too large or too complex to read statically". Axios and SDK factory results are memoized per function, like queues' `byFactory` already was. Long labels and `NO_MATCHING_ROUTE` details go through `clip()`.
  - **No empty names reach the graph.** An empty host (also `user@` only, or only a port) is `DYNAMIC_URL` ("the URL has an empty host"). An empty queue name is `DYNAMIC_NAME` with its own detail. A compose service with an empty key is skipped with `COMPOSE_INVALID`.
  - **Masking:** inside a URL, literal text is kept up to the first `?`, `&`, `=`, or `#`. Strings passed to a call inside the URL are masked; only `new URL(…)` counts as building the URL. Queue `DYNAMIC_NAME` nodes use `redactedText` and keep only a name expression's own strings, never a whole call's or flow object's.
  - **Correctness fixes:** a called worker factory drops only its own `consumes` events; its publishes stay, as `DYNAMIC_NAME` when the name is the parameter. A config object only gives a `method` when it is `const` and never written (`x.a = …`, `delete`, `Object.assign`) in its file. A datasource with a literal `url` is never linked to a compose service by engine alone. An env value whose quote never closes is read as one line, so the keys after it still count.
  - **Kept as is:** an unbound wrapper parameter hole aligned to a `:param` route stays `exact`, per DESIGN.md §7.4's rule that a hole matches a param. A forwarded sub-path (`"/api/" + path`) and a path parameter look the same, and ADR-0032 already lists nested closures as not handled. M3's eval measures how often this misleads.
- **Consequences:** no golden changed, and cal.com's counts are unchanged. The review's repros are now tests: each stays under 20 s (in practice under 0.5 s).

## ADR-0040: Eval ground truth: labeled scope, call sites defined by the code, strict validation
- **Context:** M3.1 finalizes EVALUATION.md's label format before any repo is labeled. The draft left three things open that change the numbers: which call sites a label file promises to cover (so an unlabeled prediction is either "not scored" or "wrong"), where a call through a helper counts as made, and how a route is spelled so label and prediction compare as strings. The labeler must answer all three without looking at analyzer output (D10.3).
- **Decision** (`eval/src/format.ts`, the `@gitinside/eval` package):
  - **`scope` is required.** It lists the folders whose call sites are all labeled. Outside it nothing is scored; inside it, a route predicted at an unlabeled site counts as a false positive and is listed. This is the conservative choice: a labeling miss can only lower precision, and the list makes it visible so it gets fixed with a note.
  - **A call site is where the code fixes the URL's route:** the `fetch`/axios call when its URL is known there, else each call of the helper that supplies the path, however deep. That is a fact about the code, so the labeler can apply it blind. Where the analyzer stops early (`WRAPPER_DEPTH` after one level, ADR-0032), the label sits further out and the miss counts as a false negative, as it should.
  - **Routes use the analyzer's spelling** (`"POST /api/users/:id"`, `*slug`, `ALL`), and a target names the file that registers the route. Scoring ignores parameter names, so naming a param differently is not an error.
  - **Hand-written files are validated strictly:** unknown keys, unsorted or duplicate call sites, call sites outside the scope, non-canonical paths, and Next.js `[id]` syntax in routes are all rejected, and `repos.json` only takes permissive licenses and the five shapes. `validate` cross-checks file names and SHAs against `repos.json`.
  - **Alternatives rejected:** labeling the innermost `fetch` line (then a wrapper's one site would stand for many different routes); treating unlabeled predictions as unscored (a missed label would silently drop a wrong prediction); free-form routes (scoring would need fuzzy matching).
- **Consequences:** `eval/repos.json` starts empty and M3.2 fills it. A repo too large to label fully can be scored on a declared subset, and the report must state the scope.

## ADR-0041: Eval labels: one label per route reached at a call site with alternative URLs
- **Context:** labeling wanderlust (M3.4) found two calls whose URL is one of two literal paths: `axios.get(base + endpoint)` where `endpoint` is either `/api/posts/featured` or a template over `/api/posts/categories/`, and `axios.delete(base + url)` with `url` reassigned to an admin route in a branch. Each call really reaches two routes, but ADR-0040 allowed one label per call site. The graph already allows it: one `http` edge per `(from, to)`, each listing the site (GRAPH_SCHEMA.md).
- **Decision:** a call site may carry several labels, one per route reached, when the code fixes the alternatives statically. Labels are unique and sorted by call site, then target (`null` first, then route, file, line), enforced by `compareLabels` in `eval/src/format.ts`. Scoring treats each label as its own expected edge.
- **Alternatives rejected:** picking one route (the other is a real edge the eval would never ask for); `target: null` (claims the call reaches nothing in the repo, which is false); a `targets` array (a second shape for scoring to handle, and per-target notes get awkward).
- **Consequences:** WealthWise and foodie labels are unchanged (no such sites). `validate` now reports labels and call sites separately. A site the analyzer resolves to only one of its routes gets one TP and one FN, which is the honest count.

## ADR-0042: Eval scoring: what a prediction is, external hosts as abstentions, missing sites listed
- **Context:** M3.5 implements EVALUATION.md's scoring. The rules left open what counts as a prediction (the graph has `http` edges to routes and to `unresolved` nodes, but a literal-host `fetch` becomes an `external_call` edge, ADR-0034), how to compare route lines, and how to keep per-confidence numbers from double-counting recall. These must be fixed before the first scoring run (M3.6), so they can't be tuned to the result.
- **Decision** (`eval/src/score.ts`):
  - **Predictions are per edge site.** `http` → `route` predicts that route; `http` → `unresolved` and `external_call` → `external` both predict "no route in the repo". A `null` label with only such predictions at its site is a correct abstention. Other edge kinds are ignored.
  - **Route lines aren't compared.** The analyzer anchors a route at the method call (`router.get` column), labels at the registering statement; registering file + method + path (parameter names dropped) already identify a route uniquely within a file.
  - **False positives carry a kind** (`wrong-route`, `route-for-null-label`, `unlabeled-site`), and false negatives list what was predicted instead, so the report explains every miss.
  - **A label with no prediction at all is "missing"**, listed separately (it is also a false negative when it has a real target). It should never happen given "no call site dropped" (ADR-0034), so the list makes any break visible.
  - **Per-level recall uses all positive labels as the denominator**, so exact + pattern + heuristic recall add up to the overall recall; a level's own precision is TP / (TP + FP) at that level. Empty denominators are `null` ("n/a").
  - **Duplicates count once:** the same route predicted twice for one label (two sites on a line the label gives no column for) is one TP.
  - **Alternatives rejected:** comparing route lines (fails on harmless anchoring differences); counting external predictions for `null` labels as FPs or ignoring them (the analyzer correctly said "not in this repo"); per-level recall over labels "attempted" at that level (undefined for FNs, which have no confidence).
- **Consequences:** the scorer refuses a graph for another repo or commit (`ScoreError`). M3.6 adds the runner (analyze each pinned checkout, score, write the report).

## ADR-0043: Eval reports: byte-for-byte reproduction with a recorded run record
- **Context:** M3.6. EVALUATION.md asks that `pnpm eval` reproduce a committed report byte-for-byte, and also that the report state its date and machine. Those two can't both hold on another machine or day unless the report separates what depends on the run from what depends on the inputs. The analyzer's version string (`0.1.0`) also doesn't change with every analyzer commit, so it can't by itself say which code produced a report.
- **Decision** (`eval/src/run.ts`, `eval/src/report.ts`):
  - **The report is a pure function** of the pinned inputs plus a **Run** record (date, GitInside commit, machine). Scores, lists, and wording are all derived from the inputs, sorted, and printed with fixed formatting (`toFixed(1)` plus the raw fraction).
  - **`pnpm eval --check [report]`** reads the Run record back, refuses if the analyzer, schema, eval code (including labels and `repos.json`), or `pnpm-lock.yaml` differ from the recorded commit (committed or uncommitted), regenerates, and compares bytes. So "reproduced" means: the same code, at the recorded commit, gives the same report, on any machine.
  - **Dirty runs are marked** (`+ uncommitted changes`) and can't be checked. The workflow is: commit code, run the eval, commit the report.
  - **Checkouts** are shallow fetches of the exact SHA into `eval/.repos/<owner>__<name>`, with LFS smudging and `core.autocrlf` off so files have the same bytes on every OS; `eval/results/**` is pinned to LF for the same reason. The repos are only read.
  - **Missing labels with a real target** are listed once, under false negatives ("nothing predicted at the site"); the Missing list repeats only `null`-labeled dropped sites.
  - An on-demand **Eval** GitHub Actions workflow (`workflow_dispatch`) runs `--check`.
- **Alternatives rejected:** leaving the date and machine out of the report (EVALUATION.md requires them); comparing everything except the Run section (then a report could claim a commit it wasn't produced from); a JSON sidecar that the Markdown is re-rendered from (proves only the renderer, not the analysis).
- **Consequences:** a new report is needed whenever the analyzer, schema, labels, or lockfile change, which matches the rule that analyzer commits after M3 state their eval delta.

## ADR-0044: Owner label review sample: stratified per repo, seeded by date
- **Context:** M3.7. D10.3 has Abhinav review a random 20% of the drafted labels, chosen by a seeded shuffle with the issue's date as the seed (EVALUATION.md §1). Left open: the sampling unit, whether to sample across all repos at once, and which generator, so the list can be regenerated anywhere.
- **Decision** (`eval/src/sample.ts`, CLI `review-sample`):
  - **The unit is a call site,** with every label at it, since a multi-route site (ADR-0041) is one judgment about one piece of code.
  - **Stratified per repo:** ⌈20%⌉ of each repo's call sites, each repo shuffled with its own seed `<date>/<owner>/<name>`. A pooled draw of 29 of 142 could skip taxonomy (8 sites) entirely; stratifying costs one extra site (30) and checks every labeler pass.
  - **Generator:** FNV-1a 32-bit hash of the seed string into mulberry32, Fisher–Yates. Integer-only arithmetic, so the same on every platform and Node version; no dependency.
- **Alternatives rejected:** one pooled shuffle (can miss a repo); `Math.random` or a time seed (not reproducible); sampling labels instead of sites (splits one judgment in two).
- **Consequences:** the list in the review issue can be checked by anyone with the committed labels and the issue's date. Corrections go into the label files with a `notes` entry and `reviewedBy`, then a new report is generated.

## ADR-0045: M3 fresh-eyes review fixes to the eval harness
- **Context:** the M3.8 review (a context-free subagent, `m2..HEAD`) found no high-severity issues and confirmed the committed report reproduces. It found one real bug and eight latent gaps, five confirmed by running.
- **Decision:**
  - **`--check <path>` resolves against `INIT_CWD`** (where `pnpm` was run), not the eval package. The report's own "Reproduce" command failed with ENOENT before.
  - **Checkouts are reset and cleaned** (`reset --hard`, `clean -ffdx`) on every run, and checked out with `core.symlinks=false` on every OS. Stray or ignored files (a reader's `node_modules`, a `.env`) could otherwise reach the analysis, and Linux and Windows would disagree on symlinks.
  - **Wrong duplicates count once, like right ones:** when the label names only the line, the same wrong route at two columns is one FP, not two.
  - **Labels scoring can't tell apart are rejected** by `format.ts`: two routes at one site with the same `routeKey`, or `null` mixed with a route at one site (the `null` label was never scored). No committed label file had either.
  - **Report wording is derived** from the number of repos, `labeler`, and `reviewedBy`, instead of being fixed text.
  - **The Eval workflow** gets `permissions: contents: read` and `persist-credentials: false`.
  - **Newest report** is chosen by date, then version numerically (`0.10.0` after `0.9.0`).
- **Not changed:** a same-day rerun replaces that day's report rather than refusing. Git history keeps the old one, the Run record names the code, and the "re-run `pnpm eval` after any input change" rule (ADR-0043) would otherwise need a new name scheme. The review's other suggestion, summarizing review disagreements in the report, waits until the review exists (planning #1).
- **Consequences:** the report was regenerated. Its numbers are unchanged; only the Run commit and the derived wording can differ.

## ADR-0046: Viewer package scaffold: React 19, Vite library mode, Storybook 8, theme on one attribute
- **Context:** M4a.1 needs `packages/viewer` (ROADMAP M4a) for `apps/web` (Next.js, M5) and Storybook, with visual tests in dark and light later (M4a.8).
- **Decision:**
  - **React 19** as a peer dependency, so the Next.js app supplies the single copy (Next 15 ships React 19). React Flow (ADR-0011) is added when the graph canvas arrives (M4b).
  - **Vite library mode** builds one ES module bundle with React external; `tsc --emitDeclarationOnly` writes the types into the same `dist/`. The package exports `dist/` like `@gitinside/schema`, so turbo's `^build` ordering works unchanged.
  - **Vite 5.4.21**, the version Vitest 2.1.8 already resolves. Two Vite copies made `plugins` fail typecheck under `exactOptionalPropertyTypes`.
  - **Storybook 8.6** (`react-vite`, `addon-essentials`, telemetry off). A preview decorator wraps every story in `ViewerRoot` with a `theme` global (toolbar, and `&globals=theme:light` in URLs for visual tests). CI builds Storybook on every push (TESTING.md).
  - **Theme = `data-theme` on `ViewerRoot`.** Tokens (M4a.2) will be CSS variables keyed on `[data-theme]`, so switching themes changes one attribute and re-renders nothing below it.
  - **Tests** use Vitest + jsdom + Testing Library; coverage threshold 70% (TESTING.md, "others").

## ADR-0047: Design tokens in TS and CSS, checked against each other; Geist via external Fontsource imports
- **Context:** M4a.2 turns DESIGN_SYSTEM.md §4 into tokens for both themes, with self-hosted Geist. Components style with CSS, but canvas code (layout timing, SVG/PNG export, minimap) needs the same values in JS. The light theme had no values yet, only "tuned for AA".
- **Decision:**
  - **Two sources, one test.** `src/tokens.ts` (`themeTokens`, `scaleTokens`, `durations`, `cssVar`) and `src/styles/tokens.css` hold the same values; `tokens.test.ts` parses the stylesheet and fails on any drift. Hex values are lowercase because Prettier lowercases them in CSS.
  - **Scoping:** shared scales on `.gi-root`, colors on `.gi-root[data-theme="dark"|"light"]`, so nested roots override and the host page is never restyled. `:focus-visible` gets the 2px accent ring; `prefers-reduced-motion` zeroes every duration.
  - **Contrast is a test, not a review step.** In both themes, `text` and `text-muted` are ≥ 4.5:1 and the accent, layer, trace, and diff colors are ≥ 3:1 on the canvas and every surface (`contrast.ts`, exported for M4a.3's logo fallback). Light values keep each dark hue and lower its lightness until it clears the bar.
  - **New tokens beyond the brief:** `surface-raised` for elevation 2–3 (screenshots showed shadows alone don't separate levels on the dark canvas; it is white in light), `scrim` for the palette backdrop, `shadow-2`/`shadow-3`, line heights, and per-role radii.
  - **Fonts:** `@fontsource-variable/geist` and `geist-mono` (OFL 1.1) as dependencies, imported from `src/fonts.ts` and kept **external** in the library build. Vite's library mode inlines every asset, which made `style.css` 201 kB of base64 woff2 subsets; external imports let the app's bundler emit the files on its own origin and the browser load only the unicode-range subsets a page uses (Latin only in the screenshots). Tokens ship as `@gitinside/viewer/styles.css`.
  - **No `sideEffects` field.** A `["*.css", …]` list made Storybook's build drop both stylesheets; the default (everything has side effects) costs nothing at this size.
- **Alternatives rejected:** generating the CSS from TS at build time (an extra build step for ~40 values the test already guards); Google Fonts or the `geist` npm package's `next/font` loader (third-party fetch, or Next-only); subsetting fonts by hand.
- **Consequences:** `apps/web` (M5) must import `@gitinside/viewer/styles.css` and let its bundler resolve the Fontsource CSS. `trace` and `diff-changed` are both amber; they never share a screen today (diff mode vs trace), which the design gate should confirm.

## ADR-0048: Icons from the node's own fields; logos bundled from Simple Icons; contrast picks the fill
- **Context:** M4a.3 needs real technology logos and a custom glyph family (DESIGN_SYSTEM.md §3). Simple Icons 16.36 no longer ships several brands the analyzer can name (OpenAI, AWS, Microsoft SQL Server, Twilio, Slack, SendGrid, Postmark), and many brand colors are near-black or pale, so they disappear on one theme's tile.
- **Decision:**
  - **Lookup is from the node's own field only:** `service.framework`, `datastore`/`queue` `engine`, `external.host`. Hosts match a registrable suffix at a label boundary, longest suffix first. Anything unmapped gets its kind's glyph; nothing is inferred from paths or package names. `iconFor()` is pure and total over `GraphNode`.
  - **`simple-icons` is pinned and bundled.** brands.ts imports ~56 named icons and keeps only slug, title, hex, and path; Rollup tree-shakes the rest (the library's `index.js` is 66 kB, 28 kB gzipped). `@gitinside/schema` is a types-only dependency and stays external.
  - **Fill by contrast, per theme:** the brand color if it is ≥ 3:1 (WCAG 1.4.11) on the tile's `surface-1`, else `--text`. Both fills go on the element as custom properties and `icons.css` picks one by `data-theme`, keeping ADR-0046's "theme switch re-renders nothing".
  - **The tile never changes fill.** Checking a hover fill too (`surface-2`) turned Redis, GitLab, Spotify, and Supabase monochrome in light; node states will restyle the node around the tile instead (M4a.4).
  - **Glyphs:** 14 stroke-only glyphs on a 24px grid (1.5px, round caps/joins, no per-element paint, enforced by tests), including two fallbacks beyond the brief: `datastore` (cylinder) and `variable` (braces). Unresolved is a dotted ring with a question mark, echoing the dotted unresolved edge style.
  - **Layer ring:** the tile hairline mixes 60% of the layer color into `--border` (`color-mix`). Full-strength rings were louder than the logos in screenshots. Layer is also named in the legend and inspector, so the ring is never the only signal.
- **Alternatives rejected:** keeping `simple-icons` external (apps/web would depend on its bundler tree-shaking a 5 MB module); copying SVG files into the repo (loses version pinning and license tracking); drawing our own approximations of missing brands (trademark risk, and a wrong logo is a guess); a per-brand hand-picked dark/light color table (drifts from the tokens; the contrast rule is testable).
- **Consequences:** a logo that Simple Icons removes in a future version breaks the import at build time, never silently. Some brands are monochrome in one theme (e.g. React in light). The design gate should confirm that tradeoff. The library build's sourcemap embeds the whole simple-icons source (5 MB `index.js.map` in `dist/`, not shipped to browsers).

## ADR-0049: One DiagramNode component, three container tiers, states as combinable data attributes
- **Context:** M4a.4 needs node visuals for every kind in every state (default, hover, selected, dimmed, traced, diff added/changed/removed). States co-occur in the explorer (a selected node on a trace, a selected node that changed), and M4b's canvas (React Flow) will own positioning and events.
- **Decision:**
  - **One component, `DiagramNode`, picks the container from the kind** (`nodeTier`): services and modules are frames, datastores/queues/externals are icon-first, everything else is a card. Words come from pure helpers in `nodes/describe.ts` (`nodeLabel`, `nodeSubtitle`, `kindName`, `REASON_TEXT`, `nodeAccessibleName`), all from the node's own fields.
  - **A closed frame draws a stacked edge** (two box-shadows) meaning "there is more inside, break it down". An open frame is translucent (`color-mix` of the layer into `transparent`), so nested frames deepen the tint.
  - **States are data attributes** (`data-hover`, `data-selected`, `data-emphasis`, `data-diff`), styled in `nodes.css`, so they combine without prop explosions and a theme switch re-renders nothing. Border precedence is selected (accent) > traced (trace) > diff > hover; hover rules wrap tier qualifiers in `:where()` to keep the same specificity as the state rules after them. Traced adds a soft trace-colored glow that survives selection.
  - **Diff state is a worded tag on the node's top edge** ("Added", "Changed", "Removed"), not an inline badge: the first screenshots showed inline diff badges squeezing card names to "crea…" and clipping the route's method chip, and growing icon-first nodes. Color is never the only signal: the tag has the word, removed is also dashed, ghosted, and struck through, and the accessible name says "Added in this change".
  - **Unresolved nodes are dotted cards** on the canvas color, matching the dotted unresolved edge, with the reason in words (`detail` if the analyzer gave one).
  - **Inherited layer:** modules, files, and symbols have no layer in the graph, so the caller passes the service's layer; the node's own layer wins.
  - **Dimmed is 20% opacity** (UX.md trace mode), raised to 50% on hover so a dimmed node can still be read before clicking it.
- **Alternatives rejected:** one component per kind (11 near-identical components; tier is the real axis); a single `state` enum prop (can't express selected + traced); per-state class names (same thing with less readable selectors); recoloring the icon tile for states (ADR-0048: the tile's fill is what logo contrast was checked against).
- **Consequences:** `nodes.css` must keep taking every color from tokens (a test rejects literals) and every transition from duration tokens (so reduced motion is instant). M4b wraps `DiagramNode` in React Flow nodes and passes `tabIndex`/handlers through. Long route paths truncate with an ellipsis in narrow cards; the full label is in the `title` and the accessible name.

## ADR-0050: Edges drawn from route points with our own geometry; labels as HTML pills; flow via CSS motion path
- **Context:** M4a.5 needs edges for every confidence level and state (hover, selected, traced, dimmed, diff, broken), with labels, arrowheads, and flow particles (DESIGN_SYSTEM.md §3, UX.md). M4b will route edges with ELK and render them inside React Flow, which isn't a dependency yet (ADR-0046).
- **Decision:**
  - **`DiagramEdge` takes route points** (ELK's start, bend, and end points), not a ready-made path. Pure `edgeGeometry()` builds the line with rounded bends (radius 10, shrunk on short jogs), ends it at the arrowhead's base so the stroke never pokes through the tip, and returns the arrowhead, an open chevron, the pattern dot, the label point (half the length), and the full flow path. Coordinates are rounded to 0.01px, so the same points always give the same SVG text. Our own arrowheads replace SVG `<marker>`s, whose color can't follow the stroke on every browser (`context-stroke` support is patchy).
  - **Line style is confidence:** solid (exact), solid with a dot 7px off the source (pattern), dashed 6/4 (heuristic), dotted round caps (unresolved, with an open chevron arrowhead). Broken overrides the line with a pulsing red dash, because UX.md specifies that look.
  - **Color is the source's layer**, mixed 70% into `--text-muted` at rest and full on hover. A test computes that mix for every layer and theme and holds it to 3:1 on the canvas and both surfaces (WCAG 1.4.11; edges are essential graphics).
  - **Selected and traced get a halo** (the hit-area stroke tinted 22% / 16%), not only a color: screenshots showed a selected frontend edge was indistinguishable from hover in light, where the frontend blue sits next to the accent.
  - **Labels are a separate HTML pill (`EdgeLabel`)**, positioned by the caller at the geometry's `mid`, the way React Flow draws labels above its SVG layer. They say only what the analyzer knows: `POST /api/orders · HTTP` (method chip + mono path), `reads id, total`, the reason in words when unresolved, "22 calls" when aggregated, a leading "Added/Changed/Removed" in diff mode, and the broken text when broken. No guessed protocol: `external_call` reads "calls API", never "HTTPS". The pill is `aria-hidden`; the edge's accessible name carries the same words plus both ends and the confidence.
  - **Flow particles** are two circles per edge animated along the path with CSS `offset-path` (one lap per three trace hops, staggered), with a canvas-colored ring so they show on a line of the same color. Reduced motion hides them and stops the broken pulse; the duration tokens already go to 0ms.
- **Alternatives rejected:** taking an SVG path string (we couldn't compute the arrow direction, label point, or pattern dot without parsing it); SVG `<marker>` arrowheads; SMIL `<animateMotion>` (ignores CSS, so reduced motion couldn't turn it off); labels inside SVG `<text>` (no mono/sans mix, chips, or ellipsis); a stroke color separate from the layer (the brief makes layer the edge flow color).

## ADR-0057: `packages/db`: Drizzle schema with integrity in the database, committed SQL migrations, PGlite locally and Postgres in CI
- **Context:** M5.3. Both `apps/web` (Vercel) and `apps/worker` (VM) read and write the DESIGN.md §10 tables, production is Neon (ADR-0055), and Docker's daemon doesn't run on the development machine.
- **Decision:**

## ADR-0058: `apps/worker` starts with a tar extractor we parse ourselves
- **Context:** M5.4a. The worker unpacks GitHub tarballs of untrusted repos (SECURITY.md T2, T3). Tar libraries have a history of path-traversal and link-following bugs (node-tar's 2021–2024 CVEs), and their safety depends on options and filters set correctly by the caller. The format itself is small: 512-byte headers, ustar `prefix`, pax `x`/`g` records, GNU `L` long names.
- **Decision:**
  - **`extractTarball(source, dest)` parses the tar stream itself** (`apps/worker/src/extract.ts`, no dependency) behind `node:zlib` gunzip, and does every filesystem write: `mkdir` for folders and `open(…, "wx", 0o644)` (create-exclusive, so no overwrite) for files, after resolving each path and checking it stays under `dest`.
  - **What fails the job vs. what is skipped.** Paths git can't record (absolute, `..`, NUL) fail with `TAR_UNSAFE_PATH`: they only appear in crafted archives. Symlinks, hard links, devices, FIFOs, unknown types, and names the worker can't represent safely (backslash, control characters, segments over 255 bytes, paths over 4,096) are **skipped and listed** in the result, because real repos have symlinks. Since no link is ever created, a later entry under a skipped link's name becomes an ordinary folder inside `dest`.
  - **Limits:** 500 MiB counted on the decompressed stream (including anything after the end marker, so a gzip bomb stops while streaming; a header declaring more fails before reading), 100,000 entries (pax/GNU records not counted), metadata records ≤ 1 MiB. Codes `LIMIT_SIZE`, `LIMIT_ENTRIES`.
  - **Strict integrity:** header checksums, the end-of-archive marker (a cut-off download fails instead of yielding half a repo), one top folder (GitHub's `owner-repo-sha7/`, stripped), no duplicate or conflicting entries; anything else is `TAR_INVALID`, as is bad gzip.
  - **Files over 2 MB are written in full.** The analyzer's inventory then skips them with the same `SKIPPED_LARGE` warning a local checkout gets, and workspace detection can still read anything it reads directly. The 500 MiB cap bounds the disk use.
  - **Tests** build hostile archives byte by byte with a test-only tar writer (`tar.testkit.ts`), and extract a real `git archive` tarball (pax global header, like GitHub's) to compare against the committed blobs.
- **Alternatives rejected:** `tar` (node-tar), whose `filter`/`strict`/`preservePaths` options must all be set right and which creates links by default; `tar-stream` (safe to drive by hand, but buffers whole pax headers and adds a dependency for ~150 lines); skipping large files at extraction (the analyzer couldn't warn about them, so worker and CLI graphs would differ).
- **Consequences:** skipped entries aren't in the graph's warnings yet; M5.4d/M5.5 put the list in `analyses.stats`. GNU sparse files and multi-volume archives are unsupported (GitHub doesn't produce them). On failure `dest` is partly written; the job runner deletes the job directory either way (SECURITY.md §3).

## ADR-0059: Analysis runs in a child process sandboxed by Node's permission model, an empty env, and a network guard
- **Context:** M5.4b. Each job analyzes untrusted text in a process that must not outlive 5 minutes or 3 GB (SECURITY.md T3), read the worker's secrets, start processes (T1), or use the network (T4). The analyzer is synchronous TypeScript-compiler work for most of a run, so an in-process timer can't stop it. Node 22 (the CI and production runtime) has a stable permission model for the filesystem, child processes, worker threads, and addons, but not for the network (that arrives in Node 25).
- **Decision:**
  - **`runAnalysis(job, options)`** (`apps/worker/src/runner.ts`) spawns `node child.js` (`process.execPath`, `spawn`, not `fork`, so no IPC channel and no inherited `execArgv`) and never throws for the child's behavior; it returns `{ ok, stats }` or `{ ok: false, code, message, stderrTail }`.
  - **Limits:** `--max-old-space-size=3072`; a wall-clock timer that sends `SIGKILL` at 5 minutes (also when an `AbortSignal` fires, for worker shutdown). CPU share is the container's job (M5.10); the queue runs 2 jobs at most.
  - **Permission model:** `--permission` with `--allow-fs-read` for the installed app root (code, analyzer, TypeScript's libs; it must hold no secrets) and the job's `src`, `--allow-fs-write` for exactly the output file. Paths are passed through `realpath` first. Child processes, worker threads, addons, and WASI are refused by default.
  - **Environment:** `{}`, so no secret, `NODE_OPTIONS`, or proxy variable reaches the child (on Windows libuv adds its fixed list of system variables).
  - **Network:** `netguard.ts`, preloaded with `--import`, replaces socket, TLS, UDP, listen, `http(s)`, `dns`, `fetch`, `WebSocket`, and `EventSource` entry points with non-writable functions that fail with `ERR_NETWORK_DISABLED` (ESM named imports re-synced). It's defense in depth against our own bugs; the boundary against an attacker is the container's egress allowlist (M5.10).
  - **Protocol** (`protocol.ts`): the job goes in as one JSON argument; the child writes the graph to `out` and prints one JSON report line (stats with per-stage timings, or an `AnalysisError` code). The parent validates it like input and requires exit 0, stdout ≤ 64 KiB, and a graph file of the reported size.
  - **Codes:** the analyzer's own (`LIMIT_FILES`, `INVALID_GRAPH`) pass through; `LIMIT_TIME` (killed at the limit), `LIMIT_MEMORY` (V8's heap-limit message on stderr), `CANCELLED`, and `ANALYZER_CRASHED` for anything else. User-facing messages are fixed text or the analyzer's own; the stderr tail (8 KiB) is for logs only.
  - **Tests** run the compiled child (a Vitest global setup builds `dist/`): the real analyzer on a copied fixture must write the golden bytes, and a probe script run in the same sandbox checks the kill on a busy loop, the heap cap, cancellation, malformed reports, every blocked network API (a local server sees no connection), denied reads outside the roots, denied writes besides `out`, denied `spawnSync` and `Worker`, and the empty environment.
- **Alternatives rejected:** `worker_threads` with `resourceLimits` (shares the process, its env, and its file access; a hung thread is harder to kill cleanly); `fork` (IPC channel and inherited flags for no benefit); OS sandboxes (`unshare -n`, seccomp per child) that need privileges the non-root container doesn't have; relying on the container alone (one bug would expose the worker's own secrets and files to the analysis).
- **Consequences:** the app root's read access means no secrets may live under it (production keeps them in `/etc/gitinside/worker.env`). If the worker process itself dies, its child isn't killed by us; in production the container's restart takes it down. `netguard.ts` runs only in child processes, so it shows 0% in the in-process coverage report; the probe test is its coverage.

## ADR-0060: The enqueue API: plain `node:http`, an HMAC over timestamp + method + path + body, two secrets, derived job IDs
- **Context:** M5.4c. The web app (Vercel) must queue jobs on the VM without Redis ever being public (ADR-0007, SECURITY.md T8: HMAC over body + timestamp, ±5 min; §4: secrets rotate without downtime). Three routes: `POST /enqueue`, `GET /jobs/:id`, and a health check (DESIGN.md §11, §13).
- **Decision:**
  - **`node:http`, no framework** (`apps/worker/src/api.ts`). Three routes don't need Express, and every dependency on the one public port is attack surface (T12). Server timeouts: headers 10 s, whole request 15 s, keep-alive 5 s. Tests drive the handler with Supertest.
  - **Signature** (`hmac.ts`): `X-GitInside-Timestamp: <unix seconds>` and `X-GitInside-Signature: v1=<hex HMAC-SHA256>` over `v1\n<ts>\n<METHOD>\n<path?query>\n<raw body>`. Binding the method and path (not only the body, as T8 first said) stops a captured `GET /jobs/A` signature being used for `/jobs/B`. Compared with `timingSafeEqual` against every accepted secret, no early exit. The version prefix leaves room for a scheme change.
  - **Order:** `/health` is open; for everything else the body is read (≤ 16 KiB, a declared larger `content-length` refused unread, a chunked one counted as it streams) and the signature checked **before** JSON parsing or routing, so an unsigned caller gets `401` everywhere and learns no paths. Refusal reasons (`MISSING_SIGNATURE`, `BAD_TIMESTAMP`, `STALE_TIMESTAMP`, `BAD_SIGNATURE`) are returned: they reveal nothing secret and make clock skew debuggable.
  - **Rotation:** the worker accepts `ENQUEUE_HMAC_SECRET` and, during a rollover, `ENQUEUE_HMAC_SECRET_PREVIOUS` (each ≥ 32 characters; the worker refuses to start otherwise, naming the variable, never the value). Rollover: put the new secret in the worker as current and the old one as previous, restart; change Vercel's value and redeploy; remove previous.
  - **Job IDs are derived, not given:** `<kind>-<first 32 hex of SHA-256>` over kind, lowercased owner and repo, SHA, base SHA, and the analyzer version. One commit is one job however often it's asked for (T9 dedupe), a new analyzer version re-analyzes, and an ID can't be enumerated. `installationId` is left out: it changes who may fetch the commit, not the analysis. `202 { id, created }`; `created: false` means the job already exists.
  - **Validation by hand** like `protocol.ts` (no zod in the worker): GitHub's owner/repo rules (the same as `apps/web/lib/repoUrl.ts`), 40 lowercase hex SHAs, `baseSha` iff `diff`, positive integer `installationId`, unknown keys refused; error messages name a field, never echo its value.
  - **The queue is an interface** (`JobQueue`: `add`, `get`, `ping`); M5.4d backs it with BullMQ. `GET /jobs/:id` copies only the documented status fields. A failing queue is `503 QUEUE_UNAVAILABLE`; `/health` waits 2 s for `ping` and says only `ok`/`unavailable`.
  - **The signer is importable on its own** (`@gitinside/worker/hmac`, only `node:crypto`), so M5.6's `/api/analyze` signs with exactly the code the worker verifies.
- **Alternatives rejected:** Express or Fastify (dependencies for three routes); signing the body only (signatures replayable across paths, and GETs have no body); a nonce store against replays inside the window (a replayed enqueue is the same derived ID, so it's a no-op, and a replayed GET reads a status the caller already saw); mTLS (Caddy and Vercel's fetch would both need client-cert plumbing); random job IDs from the caller (no dedupe without another lookup).
- **Consequences:** the web app and VM clocks must agree within 5 minutes (both use NTP). Caddy must pass the request target unchanged, or signatures fail. SECURITY.md T8 now describes the method + path binding.

## ADR-0061: The BullMQ worker: one pipeline function, coded failures that say whether to retry, Redis tests on CI only
- **Context:** M5.4d ties M5.4a–c together: take a job from Redis, fetch the commit's tarball from GitHub, extract it, run the sandboxed child, hand the graph on, and delete the job folder. ADR-0014 fixed BullMQ, `attempts: 3` with backoff, concurrency 2; DESIGN.md §12 says a worker crash re-queues the job (max 3 attempts). BullMQ 6 (current since July 2026) no longer bundles ioredis, and Docker doesn't run on the development machine, so there's no local Redis.
- **Decision:**
  - **`processJob(context, deps)`** (`apps/worker/src/job.ts`) is the whole pipeline and knows nothing about BullMQ: download and extract (one 2-minute budget; the tarball streams from `fetch` into `extractTarball`, never buffered on disk), run (runner.ts's own 5 minutes), `publish` (injected; M5.5 writes R2 + Postgres), then `rm` the folder in `finally`. Folders are `<jobsRoot>/<id>-<random>`, so a stalled attempt still running somewhere never shares one with its retry; `sweepJobsRoot` clears leftovers at startup (a SIGKILL skips `finally`). Stages `download → extract → analyze → upload` are reported as BullMQ progress.
  - **Failures are `JobFailure { code, retriable, detail }`** (`failure.ts`). The message is only the code, so that is all BullMQ stores (`failedReason`, shown as `errorCode`); `detail` (stderr tails, hosts) goes to logs. Retriable: `DOWNLOAD_FAILED` (network, 408, 5xx), `DOWNLOAD_TIMEOUT`, `GITHUB_RATE_LIMITED`, `CANCELLED`, `PUBLISH_FAILED`, `WORKER_ERROR` (anything unexpected). Everything else (`REPO_NOT_FOUND`, `TAR_*`, `LIMIT_*`, `ANALYZER_CRASHED`, …) is thrown as BullMQ's `UnrecoverableError`, so a deterministic failure costs one run, not three.
  - **Downloads** (`github.ts`) follow redirects by hand: inside the API (a renamed repo) with the token, at most 3 hops; to `https://codeload.github.com` **without** the token; anywhere else refused unfetched (`DOWNLOAD_REFUSED`). 404 ⇒ `REPO_NOT_FOUND`, 451 ⇒ `REPO_UNAVAILABLE`, 403/429 with a rate-limit header ⇒ `GITHUB_RATE_LIMITED`.
  - **Queue** (`queue.ts`): one queue `analysis`; job options `attempts: 3`, exponential backoff from 15 s, finished jobs kept 24 h for status lookups. Worker: concurrency 2, `maxStalledCount: 2` (with the first run, at most 3 starts; past that `JOB_STALLED`), default 30 s locks (the analysis runs in a child, so the event loop is free to renew them). Adding an existing ID is a no-op, except a job that **failed retriably** (GitHub down for all 3 attempts), which is retried with its counters reset; otherwise a transient outage would block that commit for a day. Waiting jobs get their position from the wait list, oldest first. API calls into the queue time out after 5 s (`503`) instead of waiting on a dead Redis. `stopWorker` aborts running jobs through BullMQ's processor signal (they fail `CANCELLED` and run again after the restart).
  - **Stored data is validated again** with `parseJobRequest` before a job runs, and the job ID must be a plain folder name.
  - **Dependencies:** `bullmq` 6.4.2 and `ioredis` 5.11.1 (BullMQ 6's default client, now an optional peer), exact pins; not the newest BullMQ (released the same day).
  - **Tests:** the pipeline against a fake GitHub (two local HTTP servers; the real child on a fixture tarball, every failure path, folder cleanup) and the processor's error mapping run everywhere. BullMQ itself (dedupe, positions, stages, permanent vs. retried failures, re-adding a retriably failed job, concurrency 2, stalled-job recovery by a second worker, cancel on shutdown, the signed API end to end) runs only with `TEST_REDIS_URL`: CI's `redis:7.4-alpine` service. A guard test fails on CI if the variable is missing, and `turbo.json` now passes `CI`, `TEST_DATABASE_URL`, and `TEST_REDIS_URL` through to tasks (Turbo 2's strict env mode filters unlisted variables).
- **Alternatives rejected:** BullMQ's Postgres backend (new in 6; ADR-0014 chose Redis, and Neon's free compute would pay for the polling); `ioredis-mock` (no Lua, which BullMQ runs everywhere); following redirects with `fetch`'s default (it would send the token to whatever host the redirect names); retrying every failure (a repo over 20k files would run three times); buffering the tarball to disk first (twice the disk, and no earlier failure).
- **Consequences:** the worker's entry point (env ⇒ Redis, `jobsRoot`, sweep, worker + enqueue server, JSON logs, SIGTERM ⇒ `stopWorker`) arrives with M5.5, when `publish` has somewhere to put the graph. Diff jobs fail `UNSUPPORTED_JOB` until M6. Unauthenticated tarball downloads share GitHub's 60/hour per-IP limit until a token is configured (M8's app token). The BullMQ tests' coverage counts only on CI.

## ADR-0062: Snapshot store: our own SigV4 signer, keys per analyzer version, gzip level 9
- **Context:** M5.5a. The worker must put each finished graph in R2 (ADR-0013) before M5.5b records it in Postgres. R2 speaks S3's API, authenticated with AWS Signature Version 4. ADR-0013's keys (`…/<sha>.json.gz`) have no analyzer version, but `analyses` is unique per (repo, sha, analyzer version), and public snapshots are meant to be cached by a CDN.
- **Decision:**
  - **Our own SigV4** (`apps/worker/src/sigv4.ts`, ~100 lines on `node:crypto`): canonical request, string to sign, derived key, `Authorization` header. Tested against the three worked examples in AWS's documentation (IAM `ListUsers`, S3 GET Object, S3 PUT Object with a `$` in the key); all three matched on the first run. Each path segment is percent-encoded once (S3 doesn't double-encode); a header given twice in different case is refused.
  - **Store** (`storage.ts`): `createObjectStore(config).put(key, body, headers)`, path-style `<endpoint>/<bucket>/<key>`, region `auto`. The body's SHA-256 is signed as `x-amz-content-sha256`, so a body changed in transit is refused by R2. `Host` is signed as `url.host` and left for `fetch` to send. 60 s per request. Failures are `StorageError { status?, s3Code? }`: only S3's `<Code>` is kept from an error body, and no message carries credentials (the job turns it into the retriable `PUBLISH_FAILED`).
  - **Keys** (amends ADR-0013): `public/<owner>/<repo>/<sha>/<analyzerVersion>.json.gz` with owner and repo lowercased (GitHub ignores case, like `jobIdFor`), and `private/<installationId>/<repoId>/<sha>/<analyzerVersion>.json.gz`. Every part is validated before it becomes a key, and the store refuses any key with empty, `.`, or `..` segments or characters outside `[A-Za-z0-9._/-]`. One object per `analyses` row, so a new analyzer version never overwrites an object a cache may still hold, and retention (M5.12) deletes exactly the rows it evicts.
  - **Objects:** `architecture.json` gzipped at level 9 (async, as the enqueue API shares the event loop), `Content-Type: application/json`, `Content-Encoding: gzip`; public `Cache-Control: public, max-age=31536000, immutable` (a key's content never changes), private `private, no-store` (SECURITY.md T6).
  - **Config:** `storeConfigFromEnv` reads `R2_ACCOUNT_ID` (32 lowercase hex, which also stops it from redirecting the endpoint), `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET` (ADR-0055); errors name the variable, never its value.
  - **Tests:** a fake S3 server (`s3.testkit.ts`) recomputes each signature from the headers the request says it signed and checks the body hash, as R2 does; wrong secret, tampered body, non-XML errors, no response, timeout, and unsafe keys are each tested.
- **Alternatives rejected:** `@aws-sdk/client-s3` (dozens of transitive packages for one PUT, SECURITY.md T12); `aws4fetch` (small, but a dependency for code we can test against AWS's own examples); presigned URLs (the worker holds the key anyway); the unversioned ADR-0013 key (a re-analysis by a newer analyzer would overwrite an "immutable" object); gzip level 6 (graphs are text, and storage, not CPU, is the scarce free quota).
- **Consequences:** no GET/DELETE yet: M5.12 (retention), M5.8 (serving), and M8.5 (uninstall) add them on the same signer. The worker's egress allowlist (M5.10) needs `<account>.r2.cloudflarestorage.com`.

## ADR-0063: Postgres writes: the worker records each attempt, GitHub supplies the repo facts, `publish` = R2 then Postgres
- **Context:** M5.5b. The worker must leave a `repos` row and an `analyses` row (DESIGN.md §10) whose status follows the job. A repo row needs GitHub's ID, current name, visibility, and default branch, none of which the enqueue request carries. The schema enforces the status ⇔ columns rule, and `repos` has two unique keys (GitHub's ID, and owner/name ignoring case).
- **Decision:**
  - **Lifecycle functions live in `@gitinside/db`** (`analyses.ts`), shared with the web app (M5.6): `upsertRepo`, `startAnalysis` (insert or restart as `running`), `requeueAnalysis` (`running` ⇒ `queued`), `completeAnalysis`, `failAnalysis`, `failInterruptedAnalyses`. Times come from the database's `now()`. **A `done` row is never changed again** (`startAnalysis` returns it as is, `failAnalysis`/`requeueAnalysis` skip it), so a redundant job can't hide a cached result; `completeAnalysis` accepts any other status, since the snapshot now exists.
  - **Repo facts come from GitHub at the start of each attempt** (`fetchRepoFacts`, `GET /repos/{owner}/{repo}`, API-only redirects with the token, the answer validated field by field). **A private repo on a job without an installation fails `REPO_NOT_PUBLIC`** before anything is downloaded or written: the worker's token may be able to read it, but it must never reach the public cache (SECURITY.md T6). GitHub's spelling (after a rename or a case change) names the row and the public snapshot key.
  - **A stale holder of a name** (a repo renamed or deleted on GitHub, whose name a new repo took) is renamed `~<its GitHub ID>` inside the upsert's transaction instead of deleted, so its analyses survive until it is seen again; no GitHub name contains `~`.
  - **`processJob` gets an optional `JobRecorder`** (`start` before the download, inside the download budget; `failed(record, code, final)` after a failed attempt). `final` = the failure isn't retriable, or the processor says it's the last attempt (`attemptsMade + 1 >= opts.attempts`); a non-`JobFailure` counts as the processor's retriable `WORKER_ERROR`. If recording a failure fails too, it's logged (`record_failed`) and the job's own failure is what the queue sees. A failing start is the retriable `RECORD_FAILED`.
  - **`publish` = R2, then Postgres** (`createAnalysisRecorder(...).publish`): upload the gzipped snapshot under the public or private key, then `completeAnalysis` with stats (files, nodes, edges, unresolved, warnings, graph and stored sizes, analyzer stage times, and worker `jobMs` for download, analyze, upload). A `done` row therefore always has its object; if the database write fails, the retry uploads the same immutable key again.
  - **`files`** joins the child's stats (the graph's `file` nodes), as DESIGN.md §10 lists it.
  - **Tests:** the lifecycle on PGlite (or CI's Postgres) in `packages/db`; the worker's recorder end to end through `processJob` with a migrated database, the fake S3, and the fake GitHub. The db package's test database helper is now a built entry, `@gitinside/db/testing`.
- **Alternatives rejected:** the web app writing the repo row and passing its facts in the job (the enqueue API would grow fields, and the worker would trust a visibility it can check itself); deleting a stale name holder (loses analyses of a renamed repo); marking `failed` on every failed attempt (the progress page would flash "failed" before a retry succeeds); writing Postgres before R2 (a `done` row could point at a missing object).
- **Consequences:** one extra GitHub API call per attempt (inside the same rate limit as the tarball). A job that stalls out (`JOB_STALLED`, no processor runs) leaves its row `running`; the entry point (M5.5d) calls `failInterruptedAnalyses` with its own start time after the sweep. `installations` rows and `repos.installation_id` are linked by M8.3. Concurrent jobs for a rename-swapped pair of repos could deadlock the two upserts; Postgres aborts one and it's retried.

## ADR-0064: Progress events: analyzer stages streamed as stdout lines, stored as the job's BullMQ progress, worded by a shared module
- **Context:** M5.5c. UX.md's progress page shows real stages with counts ("Parsing 1,204 files", "Linking 87 calls to routes"). The analyzer runs in a sandboxed child with no network and an empty environment, and its only channel back is stdout, which used to carry exactly one report line. The analyzer's `onStage` fires only after a stage ends, with a duration.
- **Decision:**
  - **The analyzer gains `onProgress({ stage, count? })`,** called as each stage starts. Counts are given only where the analyzer knows them before doing the work: `programs` carries the source files it parses, and `http` reports a second time with the requests it links once it has collected them. Progress never enters the graph (goldens and determinism tests unchanged).
  - **The child prints one `{"progress":{"step","count"?}}` line per event, then the report as the last line.** The runner parses stdout line by line as it arrives (lines split across chunks are joined), validates each (known step, non-negative integer count) and hands it to `RunOptions.onProgress`. A line after the report, two reports, a report without its newline, or more than 64 KiB in total is `ANALYZER_CRASHED`, as before.
  - **The worker stores the latest step as the job's BullMQ progress,** `{ stage: "analyze", progress, step, count? }`. The analyzer's 15 steps share 30–90 evenly (`inventory` 30 … `assemble` 86). Step updates are **best effort**: `processJob` issues each at once (so they reach Redis in order, before `upload`) without awaiting it, and a failure is logged `progress_failed` instead of failing an analysis that is otherwise fine. Stage updates keep awaiting, as before.
  - **`GET /jobs/:id` gains `step?` and `count?`;** `statusFromJob` copies only validated fields, so nothing else stored with the progress reaches a caller.
  - **`progress.ts` holds the vocabulary** (job stages, a copy of the analyzer's stage list kept equal by a test, `stepProgress`, `describeProgress`, locale-free `formatCount`) with no dependencies, exported as `@gitinside/worker/progress` for the progress page (M5.7), so the words live in one place and the website doesn't load BullMQ or the analyzer.
- **Alternatives rejected:** a second pipe or IPC channel for progress (more sandbox surface; `--permission` and `stdio` stay as they were); counts for every stage (the analyzer would have to pre-scan, e.g. call sites, just to report them); progress text written by the worker (the website couldn't reword or localize it, and free text in Redis is harder to validate than a step name and a number); awaiting each step update or failing the job on it (a Redis blip mid-analysis would throw away a good result).
- **Consequences:** the progress page shows the latest step only; it's polled or streamed by M5.7. The analyzer's public options grew, so the eval report is re-recorded. A new analyzer stage needs adding to `ANALYZER_STEPS` and its words, or the progress test fails.

## ADR-0065: The worker's entry point: one process for the worker and the enqueue API, config checked up front, sweep before work, ordered shutdown
- **Context:** M5.5d. M5.4–M5.5c built every piece of the worker (queue, pipeline, recorder, store, enqueue API) but nothing starts them. ADR-0061 and ADR-0063 left the entry point the startup sweep of job folders and of rows left `running`, JSON logs (DESIGN.md §13), and SIGTERM ⇒ `stopWorker`. The container (M5.10) runs one command and is restarted by Docker when it exits.
- **Decision:**
  - **One process** (`apps/worker/src/bin.ts` ⇒ `runMain` in `main.ts`, `pnpm --filter @gitinside/worker start`) runs the BullMQ worker and the enqueue API on the same queue. They share Redis and the analyzer version; the analysis itself happens in child processes, so the API's event loop stays free.
  - **Config** (`config.ts`, `workerConfigFromEnv`): `REDIS_URL` (`redis:`/`rediss:`), `DATABASE_URL` (`postgres:`/`postgresql:`), the `R2_*` variables, `ENQUEUE_HMAC_SECRET` (+ `_PREVIOUS`), and optional `JOBS_ROOT` (absolute, default `/tmp/jobs`), `HOST` (default `127.0.0.1`; the container sets `0.0.0.0` behind Caddy), `PORT` (default 8080), `GITHUB_TOKEN`. Every problem is reported at once (`config_invalid` with one line per variable, exit 1), naming the variable, never its value. Names in `apps/worker/.env.example`.
  - **Startup order:** open Postgres; delete leftover job folders; `failInterruptedAnalyses(db, <this process's start time>)`; connect to Redis and `ping` it (5 s), so a wrong URL fails at boot instead of on the first job; start the worker; listen. A failure at any step closes what was opened, in reverse, and exits 1. The sweep comes before the worker takes jobs, so it never deletes a live job's folder.
  - **Shutdown** on SIGTERM (Docker) or SIGINT: stop accepting connections and close idle ones, `stopWorker` (running jobs are cancelled with the retriable `CANCELLED`), close the queue, close the database. Every step runs even if one fails; any failure, or taking over 20 s, exits 1, a clean stop exits 0. A second signal is ignored; `stop()` is idempotent.
  - **Logs** (`log.ts`, `createJsonLog`): one JSON line per event on stdout, `time` first, then `event` and its fields (codes, IDs, counts, timings). Errors become their message; an unserializable event becomes `log_unserializable` instead of throwing. Rotation is the Docker log driver's job (M5.10). No URL or secret is logged: `worker_starting` says only whether a GitHub token is set.
  - **Tests:** config parsing and every refusal; the log format; `runMain` with a fake process (bad config, failed start, signal ⇒ exit 0, failed or slow stop ⇒ exit 1, second signal ignored); the built `bin.js` with an empty environment; startup against PGlite with an unreachable Redis (folders swept and the row failed before the Redis check, the database closed after it, nothing secret logged). With `TEST_REDIS_URL` (CI): a signed job through the real process to the fake S3 and Postgres, two `stop()`s, and a taken port closing the worker it had started.
- **Alternatives rejected:** separate processes for the API and the worker (two containers sharing one small VM for no isolation gain: neither parses repos); a logging library such as pino (a dependency for one `JSON.stringify` per line, SECURITY.md T12); waiting for Redis with retries at startup (Docker's restart policy already retries, and a crash loop is visible in `docker ps`); the database's clock for the interrupted-rows cutoff (no job runs before the sweep, so the local clock only has to be right to within the restart time).
- **Consequences:** M5.10's image runs `node dist/bin.js` with `HOST=0.0.0.0`, a stop grace period over 20 s, and the log driver's rotation. The worker's main process loads the analyzer only for its version string (TypeScript stays loaded, ~tens of MB); `main.ts` isn't re-exported from the package root so importers don't pay for it. An uncaught exception still crashes the process (Node prints the stack to stderr), and Docker restarts it; the next start's sweep cleans up.

## ADR-0066: `/api/analyze`: GitHub's latest commit, cache by commit and analyzer version, charge only new analyses, rows recorded by the web app
- **Context:** M5.6. The website needs one endpoint that turns a pasted URL into "here's the diagram" or "here's your job" (DESIGN.md §11), while staying inside SPEC §3's rate limit (5 new analyses per hour per IP signed out; viewing unlimited) and SECURITY.md T9 (abuse, dedupe by repo@sha). The worker's enqueue API (ADR-0060) already dedupes by a job ID derived from the commit and analyzer version; `rate_limits` (ADR-0057) is a fixed-window table keyed by an opaque string.
- **Decision:**
  - **Flow** (`apps/web/lib/analyze.ts`, `requestAnalysis`): parse with `parseRepoUrl` ⇒ resolve on GitHub ⇒ `findAnalysis` ⇒ `done` is returned as `200 { status: "done", owner, repo, sha }`; otherwise enqueue and return `202 { status: "queued", jobId, owner, repo, sha }`. Owner and repo in answers are GitHub's spelling.
  - **Resolving** (`lib/github.ts`): `GET /repos/{owner}/{repo}` for the ID, spelling, visibility, and default branch, then `GET /repos/{owner}/{repo}/commits/HEAD` with `Accept: application/vnd.github.sha` (the bare SHA, one small response). Same-origin API redirects (a renamed repo) are followed, at most 3; nothing else is. **A private repo is answered exactly like a missing one** (`REPO_NOT_FOUND`), so an optional `GITHUB_TOKEN` that can see private repos never reveals one. Empty repo (409) ⇒ `REPO_EMPTY`; GitHub's rate limit ⇒ `GITHUB_RATE_LIMITED` (503).
  - **Cache key = GitHub repo ID + SHA + analyzer version.** The version comes from a new dependency-free entry, `@gitinside/analyzer/version`, so the web app doesn't load the TypeScript compiler. Looking up by GitHub's ID means a renamed repo keeps its cache.
  - **Who pays:** a commit already `queued`/`running` is "in flight" and gets its job back free (the enqueue call is idempotent, so a lost Redis job is re-created). Anything else takes a slot first (`consumeRateLimit`: one `INSERT … ON CONFLICT DO UPDATE … WHERE count < limit`, so racing requests can't overshoot), and the slot is **refunded** if the worker is down or answers `created: false` (another request's job already covered the commit). Limited ⇒ `429` with `retryAt`, `Retry-After`, and "You've analyzed 5 repos this hour. Try again in N minutes." ("or sign in" arrives with M8).
  - **Windows are fixed UTC hours** on the database's clock (`date_trunc('hour', now(), 'UTC')`), one clock for every serverless instance. UX.md's "Try again at 14:32" example implies a sliding window; with fixed windows the honest time is the top of the hour, worded as minutes so no time zone is involved.
  - **Address keys:** `x-real-ip`, else the first `x-forwarded-for` entry (Vercel sets both and clients can't override them); IPv6 counts per /64; IPv4-mapped IPv6 as IPv4. Stored as `ip:` + HMAC-SHA256 under a key derived from `ENQUEUE_HMAC_SECRET` with a fixed label, so no new secret is needed and the table can't be reversed by hashing all IPv4s. Rotating that secret resets the counters, which is harmless.
  - **Rows written by the web app:** only when its request created the job, `upsertRepo` (from GitHub's facts) and `queueAnalysis` (insert `queued`, or move a `failed` row back to `queued`; `running`/`done` untouched). That's what makes the next request see the commit in flight. The worker's `startAnalysis` already accepted a pre-inserted row.
  - **HTTP edge** (`lib/analyzeRoute.ts`): `application/json` only (a cross-site page can't send it without a CORS preflight we never answer, so no CSRF token), 4 KiB body cap checked on the declared length and while streaming, body exactly `{ "url": string }`, pasted text over 2,048 characters refused unparsed, `cache-control: no-store`. Unexpected errors are `500 INTERNAL`, logged by error name only (driver messages can carry connection details). Missing `DATABASE_URL`/`WORKER_URL`/`ENQUEUE_HMAC_SECRET` (or a non-https worker in production) ⇒ every request is UX.md's "temporarily unavailable" (503), which is what production shows until M5.13.
  - **Worker client** (`lib/worker.ts`): signs with `@gitinside/worker/hmac` over the exact path and bytes sent, 5 s timeout, no redirects, validates the answer's job ID; anything else is `WorkerUnavailableError` ⇒ 503.
  - **`@gitinside/db`'s `migrationsFolder`** is now built with `join(dirname(fileURLToPath(import.meta.url)), …)`: Turbopack read `new URL("../drizzle", import.meta.url)` as an asset import and failed the web build.
- **Alternatives rejected:** checking the limit without consuming, then enqueueing (racing requests overshoot); charging re-asks for a commit in flight (a visitor refreshing would burn their limit on one job); asking the worker for the analyzer version (a network hop before every cache lookup; a version skew between Vercel and the VM only costs cache misses until both deploy); importing `ANALYZER_VERSION` from the analyzer's root (loads TypeScript into a serverless function); a new `RATE_LIMIT_SECRET` (one more secret for Abhinav to create for no extra safety); sliding-window counters (more rows or state for a limit of 5); `serverExternalPackages` for `@gitinside/db` (Next.js bundles workspace packages regardless).
- **Consequences:** the landing form still opens the repo page; M5.7 points it at `/api/analyze` and the progress page (job ID from the `202`). Without `GITHUB_TOKEN`, GitHub allows the web app 60 requests an hour per IP, two per lookup, so production wants a token (fine-grained, public repos read-only) until M8's app token. Every lookup, cached or not, spends GitHub quota; cached lookups are never rate-limited by us (SPEC: viewing is unlimited). Old `rate_limits` rows are pruned by M5.12's retention job. Signed-in limits (30/h, a `user:` key) arrive with M8.

## ADR-0067: The progress page: job ID in the path, the worker's status put into words on the server, short SSE streams the browser chains
- **Context:** M5.7. UX.md's "Analyze" flow needs a progress page with real stages ("Downloading", "Parsing 1,204 files") and the queue position ("2 ahead of you"), and an error state with direction. The worker already reports all of it on its signed `GET /jobs/:id` (ADR-0060, ADR-0064); the browser can't call the worker (it holds no secret and the VM only trusts the web app). DESIGN.md §11 names `GET /api/jobs/:id` and an SSE variant at `/api/jobs/:id/events`. The web app runs as Vercel serverless functions, which have a time limit per request; an analysis can take 5 minutes plus its wait in the queue.
- **Decision:**
  - **Page:** `/<owner>/<repo>/jobs/<jobId>`, where the job ID is the one `/api/analyze` returned. The owner and repo are only the page's label and where it goes when done; both are checked with GitHub's name rules, and the ID must be `analyze-<32 hex>`, else a 404 that echoes nothing. `noindex`. Deriving the ID on the web side from owner/repo/SHA was rejected: an analyzer version skew between Vercel and the VM would turn every progress page into "not found".
  - **Worker client** (`lib/worker.ts`): `status(id)` signs `GET /jobs/:id` (empty body), `404` ⇒ `undefined`, and `parseJobStatus` copies only the documented fields after checking each (known state/stage/step, safe integers, `errorCode` a code, the ID the one asked for); anything else is `WorkerUnavailableError`.
  - **Words on the server** (`lib/jobs.ts`, `jobView`): queued ⇒ `queueText` ("2 ahead of you", "You're next", or "Waiting in the queue" without a position); running ⇒ the stage plus `describeProgress`'s text and the 0–100 progress; failed ⇒ `failureView`: limits (`LIMIT_*`), missing or private repos, blocked repos, and unreadable archives (`TAR_*`) say what happened and "Try a smaller repo" with no retry; every other code is "The analysis failed on our side. Try again." with a retry (the code itself is never shown). A job the worker doesn't know, or a diff job, is `missing` ("may have finished over a day ago", the queue keeps jobs 24 h). Both routes send these views, so the browser renders and never interprets codes.
  - **`GET /api/jobs/:id`:** the view as JSON, `no-store`; `missing` 404, `unavailable` 503.
  - **`GET /api/jobs/:id/events`** (`lib/jobRoute.ts`, `handleJobEvents`): `text/event-stream` (`no-store, no-transform`, `x-accel-buffering: no`), `retry: 1000`, then polls the worker every second and sends `event: status` only when the view changes; a `: keep-alive` comment after 10 s of silence. It **ends after 25 s** (`maxDuration` 30) or a final view (done, failed, missing). `EventSource` reconnects by itself after `retry`, so a long analysis is a chain of short requests inside the function limit, and the first event of each new stream is the current state. The request's abort signal (tab closed) and a reader's cancel stop the polling at once. A worker that's down is `unavailable` in the stream, which keeps polling, so the page recovers by itself.
  - **Deps** (`jobDepsFromEnv`): only `WORKER_URL` + `ENQUEUE_HMAC_SECRET` (same checks as `/api/analyze`): watching a job opens no database connection.
  - **Browser** (`app/[owner]/[repo]/jobs/[job]/JobProgress.tsx`): the five steps (in the queue, downloading, unpacking, analyzing, saving) as a path: walked ones checked with an accent line, the current one with the worker's words and a pulsing dot (off under reduced motion), the rest ahead; a `progressbar` with `aria-valuetext`, a polite status region with the words. Done ⇒ `router.replace` to the repo page. Failed/missing ⇒ the message as an alert, focus on the heading, "Try again"/"Analyze again" when it could help (it posts `owner/repo` to `/api/analyze`; the same job ID restarts the stream in place), plus "Analyze another repo" and "Open on GitHub". Unreachable ⇒ the last progress stays with UX.md's notice.
  - **Landing form** (`RepoForm`, `lib/startAnalysis.ts`): a valid URL is posted to `/api/analyze`: `200` opens the repo page, `202` the progress page, a refusal shows the server's message in place (rate limit, not found, unavailable) with focus back in the field. Not `disabled` while pending (focus loss); repeat submits are ignored and the hint says "Checking the latest commit on GitHub…". Only a non-2xx answer's `message` is shown, so a 200 can't smuggle text in. `UNAVAILABLE_MESSAGE` moved to the import-free `lib/messages.ts` so client code doesn't pull in the database module.
- **Alternatives rejected:** client polling of the JSON route (SPEC and DESIGN.md name SSE; the stream also avoids a request per second from every open tab when nothing changes, since it only writes on change); one stream for the whole job (cut off by the function limit mid-analysis, and a dead connection stays open on the worker side); Redis pub/sub or BullMQ `QueueEvents` from the web app (Redis is never exposed, ADR-0014); WebSockets (serverless functions can't hold them); deriving the job ID in the web app (version skew, above); showing raw error codes (UX.md: say what happened and what to do).
- **Consequences:** each open progress page costs the worker one signed status call a second, and keeps one function invocation open; on Vercel Hobby that time counts against the free function quota, so M5.13 checks usage against it (the JSON route is the fallback if it's tight). "Done" opens the repo page, which still says analysis is unavailable until M5.8 draws the diagram. UX.md's "Over the limit" subfolder input waits for subfolder analysis (not in v1's analyzer API); the limit messages suggest a smaller repo instead.

## ADR-0068: Serving graphs and check-on-view: snapshots streamed from R2 by the web app, re-analysis on view charged to the repo
- **Context:** M5.8 (split: M5.8a server side, M5.8b the page). The diagram page needs a commit's `architecture.json`, which sits gzipped in a private R2 bucket (ADR-0055 rejected public r2.dev access; ADR-0062 left GET for M5.8). SPEC §3: "Viewing re-analyzes automatically if the default branch has a new commit", and viewing is never rate-limited, while new analyses are (5/h per IP). The diagram is viewed by many people at once (a shared link, later a README image), and GitHub allows the web app 60 or 5,000 API calls an hour.
- **Decision:**
  - **Reading snapshots:** the worker's store gains a signed `get(key)` (empty-payload SigV4 GET, no redirects followed, `404 NoSuchKey` ⇒ `undefined`, anything else a `StorageError` with status and S3 code only), and `storage.ts` is exported as `@gitinside/worker/storage` so the web app reads with the code the worker writes with. `fetch` decodes the stored `Content-Encoding: gzip`, so the route streams plain JSON and the platform compresses it for the browser again.
  - **`GET /api/graph/:owner/:repo/:sha`** (`lib/graphRoute.ts`): names checked with GitHub's rules and a full 40-hex SHA, else `404` before any lookup; the newest `done` analysis of that commit of a **public** repo (`findPublishedAnalysis` in `@gitinside/db`: owner/name ignoring case, latest finish first, so a newer analyzer version's graph replaces the old one); streamed with `cache-control: public, max-age=300, s-maxage=86400`. A missing object ⇒ `404` (logged `graph_object_missing`); a storage failure ⇒ `503` "temporarily unavailable" (logged with status and S3 code); anything else ⇒ `500`, logged by name. Needs `DATABASE_URL` and the `R2_*` variables (`graphDepsFromEnv`), not the worker. DESIGN.md §11's "public: redirect to CDN" becomes "stream through the web app, cached by Vercel's CDN".
  - **What a repo page shows** (`lib/repoView.ts`, `viewRepo`): the newest finished analysis of the public repo. A permalink (`/<owner>/<repo>/<sha>`) is served as is and never asks GitHub (`pinned`). Otherwise GitHub's latest commit (`resolveRepo`, successful answers remembered per repo for 60 s in process memory, failures never) decides: same commit and analyzer version ⇒ `current`; newer commit already finished ⇒ that one is shown; queued or running ⇒ `updating` (with the job ID, fetched free from the idempotent enqueue); failed ⇒ `behind/failed` and not re-run on view (a repo over the limits would run on every page view; "Analyze" retries it through `/api/analyze`); none ⇒ enqueue and `updating`. GitHub unreachable ⇒ the stored diagram with `unknown`; GitHub says not found or blocked (deleted, **made private**, 451) ⇒ `missing`, so a repo that went private stops being served publicly. A name now held by a different GitHub ID (renamed away, name reused) ⇒ `not-analyzed`.
  - **Who pays for re-analysis on view: the repo, not the visitor.** Each new commit check-on-view enqueues takes a slot from `repo:<GitHub repo ID>` in `rate_limits` (6 per hour, the same atomic `consumeRateLimit`), refunded when no job was created (worker down, or someone's request already made it). Past it ⇒ `behind/limited`. Only repos someone already analyzed (and paid for) are re-analyzed this way; a repo with no analysis shows "Analyze", which goes through `/api/analyze` and the visitor's own limit.
  - **No worker configured** ⇒ the page still serves stored diagrams; newer commits are reported (`behind/unavailable`, or `updating` if in flight) but not enqueued (`repoViewDepsFromEnv` needs only the database).
- **Alternatives rejected:** a public bucket or presigned redirects (needs public access or bucket CORS and a new CSP origin, and presigned URLs expire, which defeats caching; reconsidered at M5.13 if Vercel's function response size limit is hit on large graphs); the graph inside the page's server-rendered payload (sent twice, and not cacheable apart from the page); charging re-analysis on view to the visitor (a viewer would spend their limit on someone else's repo by opening a link, and one popular repo would rate-limit its readers); not limiting it at all (anyone pushing commits to their own repo and reloading would queue an analysis per push); auto-analyzing never-analyzed repos on view (a crawler following `/<owner>/<repo>` links would bypass the per-IP limit); asking GitHub on every view (60 calls an hour without a token is 30 page views).
- **Consequences:** M5.8b renders the page from `viewRepo` and fetches `graphUrl` in the browser. The head memory is per serverless instance, so a cold start asks GitHub again. `repo:` rows join `ip:` rows in `rate_limits`, pruned by M5.12. M5.13 checks large graphs against Vercel's function response limits and that streamed JSON is compressed.

## ADR-0069: The diagram page: server-decided state, graph fetched and schema-checked in the browser, the M4a prototype as the diagram until M4b
- **Context:** M5.8b. `viewRepo` (ADR-0068) decides what `/<owner>/<repo>[/<sha>]` shows, and the graph lives behind `/api/graph`. The interactive explorer (M4b) waits for the design gate (#2), but the early-December demo needs a diagram page now. The M4a prototype (`ExplorerPrototype`) draws any graph, but its top bar's search, filters, and share do nothing yet, and its start hint promised a "checkout request" trace that only the fixture has.
- **Decision:**
  - **The server decides the state** (`app/[owner]/[repo]/repoScreen.tsx`): no database configured, or the lookup throws (logged `repo_view_failed` by error name only) ⇒ UX.md's "temporarily unavailable" notice; `missing` ⇒ a real HTTP 404; `not-analyzed` ⇒ an **Analyze** button (`/api/analyze`, the visitor's own limit; if the answer is this very page, `router.refresh()`); `ready` ⇒ `RepoDiagram`. `/<owner>/<repo>/<sha>` takes only a full lowercase 40-hex SHA, else 404 before any lookup; its title is `owner/repo at <short sha>`.

  - **The repo bar** (one quiet row under the site header): `owner / repo`, the commit chip linking to the tree on GitHub, one line from `headStatus` (current; updating with **Watch progress** when the job is known, the dot breathing unless reduced motion; behind because failed with **Analyze again**, limited, or unavailable; GitHub unreachable; a permalink with **See the latest**), and **Open on GitHub**. ELK (M4b.2) replaces it after the gate. Screenshots of the database-backed states come from a scratch Vite harness rendering the page components (no local Postgres server); the E2E suite covers the real routes that need no database. The page has no drill-down beyond one level, pan/zoom, or deep links until M4b.

## ADR-0070: An internal error costs an expression or a detector, never the analysis; `storybook-static` is skipped
- **Context:** M5.8c. `gitinside analyze .` on this repo failed with `TypeError: Cannot read properties of undefined (reading 'id')`. The trigger wasn't the eval/bench checkouts, as M5.8b guessed. It was `packages/viewer/storybook-static/assets/Icon-*.js`, Storybook's gitignored build output, which bundles zod. The Express detector asks the checker about every call's callee. On `this.safeParse.bind`, TypeScript 5.6 builds a "property doesn't exist" message, prints the type of `this.safeParse`, and throws while printing a getter-only property it considers writable (`addPropertyToElementList` finds no set accessor; the package's tsconfig has `exactOptionalPropertyTypes`). The crash only reproduced inside the full checkout. The bundle alone, the viewer package copied with its config (also at a shorter path), and the repo without the eval/bench checkouts all analyzed fine, so the trigger depends on more than those files. A repo we analyze can hold code like this, and one uncaught error fails its whole analysis.
- **Decision:**
  - **Per expression:** the resolver's checkers (`checkerOf`, the only checkers detectors use) are wrapped by `guardedChecker`. If `getSymbolAtLocation` throws, it answers `undefined` (no symbol known, which every caller already handles), and the resolver records one `TYPESCRIPT_INTERNAL_ERROR` warning per expression (file, line:column, error name and message). Only that method is guarded: its "no answer" is part of its contract. Methods that must return a value still throw, which the stage guard below catches.
  - **Per detector:** `analyze` runs imports, Express, Next.js, Prisma, infra, calls, HTTP, SDK, and queue stages through `detector()`. If a stage throws anything but an `AnalysisError` (limits still fail the analysis), it contributes an empty result and a `DETECTOR_FAILED` warning naming the stage and error. Later stages see the empty result (no Express routes ⇒ no HTTP edges to them). Inventory, workspace, programs, files, symbols, and assembly stay unguarded: other parts' edges point at their nodes, so a graph without them would be invalid rather than partial.
  - **Warning text** (`errorText`) keeps the error's name and message, never the stack (machine paths, build-dependent), with the checkout's path removed in both slash styles, cut to 200 characters, so the graph stays deterministic.
  - **`storybook-static`** joins `IGNORED_DIRS`: it's Storybook's default build output, like `dist` and `build`.
  - **Regression:** `fixtures/checker-crash` holds the same shape (constructor rebinding `safeParse`, object literal with a getter-only `error`, the viewer's strict options) plus a `storybook-static/` copy that must be skipped. It doesn't crash TypeScript on its own (see Context), so `analyze.test.ts` makes the checker throw on its `.bind` to test the per-expression guard, and makes detectors throw to test the stage guard.
- **Alternatives rejected:** upgrading TypeScript (changes every program's behavior and goldens for a crash we can't reproduce in isolation, and the next TS bug would fail analyses the same way); guarding every checker method through a `Proxy` (methods that must return a type or array would answer `undefined` and fail later, far from the cause); retrying the analysis without the failing file (non-local, slow, and the file's real content would silently vanish); dropping the failure without a warning (breaks "fail visibly").
- **Consequences:** a repo that trips a TypeScript bug now gets a graph with a named warning instead of `ANALYZER_CRASHED`. Warnings carry codes and file paths, so the viewer can list them later (M4b.12's error states). A crash inside the TS checker may leave its caches half-built, so later answers in that program are best effort. The warning says which expression failed.

## ADR-0071: README images are SVG text from a server entry of the viewer, with their own top-level layout
- **Context:** M5.9a. Pillar 1 (SPEC §3 F1) is a README badge and a live image of the repo's top level. They're served by `/api/badge/…` (M5.9b) as `image/svg+xml`, which GitHub's image proxy passes to the reader's browser. That rules out everything an image can't load: web fonts, external CSS, scripts. The image has to be built on the server from the stored graph. The viewer's main entry is `"use client"` (ADR-0056), so route handlers can't call into it, and the M4a prototype's layout puts each layer in one column (GitInside's own graph: ten datastores in a single stripe).
- **Decision:**
  - **A third viewer entry, `@gitinside/viewer/image`** (`src/image.ts`): no CSS, no `"use client"`, no React rendering. It exports `renderDiagram(graph, { theme })`, `renderBadge({ message, tone })`, and `topLevelCounts`. It reuses the canvas's own pieces (`liftEdges`, `nodeSize`, `routeEdges`, `edgeGeometry`, `nodeLabel`/`nodeSubtitle`, `edgeLabel`, `iconFor`, brand paths, tokens), so the image says what the canvas says. Glyphs are serialized from their React artwork (`glyphMarkup` walks the element tree), so there's one glyph source.
  - **Text, not a DOM:** pure string building, deterministic (same graph ⇒ same bytes), about 10 ms for GitInside's graph and 50 ms for cal.com's. Text can't be measured on the server, so widths are estimated per character, generously, and names are cut with "…" before they could overflow. The badge draws its two texts with `textLength`, so they fit whatever font the reader has.
  - **Colors:** the live image defines token colors as CSS custom properties on its root. `auto` (the default) is dark with a light override under `prefers-color-scheme: light`, so it follows the reader's system. GitHub's own `<picture>` / `#gh-dark-mode-only` switch can request `theme=dark|light` (M5.9b/c). The canvas's `color-mix` values are computed to hex (`mix`), since image renderers vary. The badge is fixed (dark raised surface + accent, or muted for non-diagram states), because it sits on white and near-black pages alike. Every text pair is ≥ 4.5:1 (tested).
  - **Layout:** three layer columns (frontend, backend, then datastores → queues → outside APIs). Putting outside APIs in a fourth column made backend → API lines cross the datastores. A column wraps into balanced, top-aligned sub-columns beyond 5 boxes. Beyond 15, rows grow with √n so big repos stay roughly 16:10 rather than a strip (cal.com was first drawn 20 sub-columns wide). Lines into or out of a wrapped sub-column run through the gaps between rows and enter at the top or leave at the bottom. Lines between non-neighbors of one sub-column take a lane beside it.
  - **Untrusted text:** every graph string goes through `esc` (`& < > " '`, plus characters XML can't carry, replaced with U+FFFD so a browser never rejects the image). Nothing from the graph reaches an element name, attribute name, style, or URL. A test renders `</text><script>…` names and checks that the result parses and holds no `<script`. M5.9b still serves the images with a CSP that forbids scripts, because the SVG is also opened directly on our origin.
- **Alternatives rejected:** rendering React components to markup with `react-dom/server` in a route handler (pulls the client bundle and its CSS classes into an image that can't load our stylesheet); rasterizing to PNG (needs a headless browser or a native dependency on Vercel, isn't crisp, and loses the theme switch); a Mermaid snippet in the README (GitHub renders it, but with Mermaid's own layout and look, no logos, and it would have to be committed: the read-only promise, SPEC §3 Cut); reusing the prototype's layout as is (tall stripes, lines through boxes).
- **Consequences:** M5.9b's route only looks up the graph and caches the text. Known limits, until M4b.2's ELK layout can replace this one: a frontend → data line passes the backend column at its source's height and can cross a box there; labels in busy columns overlap; a repo with 100+ services (cal.com) reads as texture at README width, and the image links to the interactive view for that.

## ADR-0072: README image routes: two SVG URLs, check-on-view, one link-only badge, always an image
- **Context:** M5.9b. ADR-0071's renderers need URLs a README can embed. A README image is fetched through GitHub's image proxy into an `<img>`, so it can't show an error page or follow a redirect to sign in. It's also viewed by many people at once, and SPEC §3 says viewing re-analyzes when the default branch moved. SECURITY.md T6 says private repos get a link-only badge.
- **Decision:**
  - **Two routes:** `GET /api/badge/:owner/:repo.svg` (the badge) and `GET /api/diagram/:owner/:repo.svg[?theme=dark|light]` (the live image; any other `theme` is `auto`). DESIGN.md §11 first had one badge URL for both. Two URLs keep each one's Markdown obvious, and `<picture>` (M5.9c) needs a URL per theme. Next.js has no partial segments, so `[repo]` holds `shop.svg` and the handler strips the `.svg`. A path without it isn't one of our image URLs: 404.
  - **Check-on-view through `viewRepo`** (ADR-0068) with no SHA: a new commit is enqueued and charged to the repo (`repo:<id>`, 6/h), never the visitor; the newest finished analysis is drawn meanwhile. The graph is read from R2 and schema-checked (`parseGraph`) before drawing (since ADR-0097, through `/api/graph`).
  - **The badge's words:** `badgeMessage(graph)` in the viewer's image entry, "3 services · 2 datastores", as many kinds as fit in 40 characters, "no services found" for an empty top level.
  - **One link-only badge** ("view architecture", muted) for every repo without a diagram: never analyzed, private (never in our public rows), gone or private on GitHub now, or a name GitHub wouldn't allow. The same bytes for all of them, so the image never tells a private repo from a missing one. The README's link (M5.9c) still opens the repo page, which offers Analyze.
  - **Always an image, never a 5xx:** when the database, bucket, or snapshot fails, the answer is the link-only badge; failures are logged by name (and S3 status/code) only.
  - **Caching:** an answer (diagram or link-only) is `public, max-age=600, s-maxage=600`, so the CDN and GitHub's proxy ask us at most every 10 minutes per URL, which also bounds the check-on-view cost. A failure's fallback is cached 60 s, so an outage doesn't stick for 10 minutes but a busy README can't hammer a struggling database either.
  - **CSP of its own:** `default-src 'none'; style-src 'unsafe-inline'; sandbox` (`IMAGE_CSP`). The images use only their own `<style>` and `style` attributes; opened directly on our origin, they can't run or load anything. `/api` is outside proxy.ts's page CSP, and next.config.ts adds `nosniff` as everywhere.
- **Alternatives rejected:** a 404 or 503 for missing or failed repos (a broken-image icon in someone's README, and a 404 vs 200 would tell private from public); different words for "not analyzed" and "private" (confirms existence); rendering without check-on-view (the image would go stale until someone opened the site, against SPEC F1); caching in process memory as well (serverless instances don't share it, and the CDN already holds the 10 minutes).
- **Consequences:** a repo's README shows a commit at most ~10 minutes plus one analysis behind the default branch. M8 (private repos) keeps the link-only badge for private repos: the image URL carries no credentials. M5.9c builds the Markdown on these URLs.

- **Context:** M5.9c. UX.md puts "Add to README" in the top bar's share menu, but the repo page hides the prototype's top bar until M4b (ADR-0069). Both link to the repo page, never a permalink.
  - **Origin:** `window.location.origin`, read when the panel opens, so production, previews, and local dev each give their own URLs with no new configuration. Names are encoded per path segment (including `()!'*`, which `encodeURIComponent` leaves alone and Markdown would read) and HTML-escaped in attributes.
- **Alternatives rejected:** a modal dialog (the page needn't be blocked, and focus trapping is M4b.7's palette work); a configured `SITE_URL` (one more env var, wrong on preview deployments); a single `auto` image (shows the wrong theme for readers whose GitHub theme differs from their system); Markdown `#gh-dark-mode-only` URL fragments (GitHub-specific and older; its docs show `<picture>` for theme-aware images).
- **Consequences:** the snippet is only as stable as the origin it was copied from (copy it from the production site). Windows' clipboard stores the line breaks as CRLF, which GitHub renders the same.

## ADR-0074: The worker image: built from source with `pnpm deploy`, laid out under `/app/apps/worker`, hardened in compose, checked on CI
- **Context:** M5.10a. SECURITY.md §3 asks for a non-root worker with a read-only root, a size-capped tmpfs at `/tmp/jobs`, no capabilities, `no-new-privileges`, and the default seccomp profile, next to a Redis that nothing outside can reach. ADR-0059 left CPU share to the container; ADR-0065 left log rotation, `HOST=0.0.0.0`, and a stop grace over 20 s to it. The analysis child may read everything under the app root (`runner.ts`: three levels above `dist/`), so that folder must hold code only. There's no Docker daemon on the dev machine, and the VM is ARM.
- **Decision:**
  - **Image** (`apps/worker/Dockerfile`, context = repo root, `.dockerignore` drops `.git`, builds, checkouts, and `.env*`): `node:22.18.0-bookworm-slim` (Node 22 like CI; `--permission` is stable from 22.13). The build stage installs only `@gitinside/worker...` from the frozen lockfile, builds those packages, and `pnpm deploy --prod /out/apps/worker`; schema, analyzer, and worker gain `"files": ["dist"]` so the deploy copies their builds (db already listed `dist` and `drizzle`). The runtime stage copies `/out` to `/app` (owned by root), removes npm/npx/corepack/yarn, and runs `node dist/bin.js` as the image's `node` user (1000). So the child's read root is `/app`: code and production dependencies, no secret, no `/proc`.
  - **Stack** (`infra/oracle/compose.yml`, project `gitinside`): the worker with `read_only`, `user: 1000:1000`, a `/tmp/jobs` tmpfs (1,200 MB: two jobs × 500 MiB extracted + graphs; `noexec,nosuid,nodev`, mode 0700), `cap_drop: ALL`, `no-new-privileges`, seccomp left at Docker's default, `init: true` (reaps children), 3 CPUs / 12 GB without swap / 256 PIDs on the 4 OCPU / 24 GB VM, `stop_grace_period: 30s`, a `/health` healthcheck, json-file logs rotated at 5 × 10 MB, and the API published on `127.0.0.1:8080` only (Caddy proxies, M5.10b). `REDIS_URL`, `JOBS_ROOT`, `HOST`, `PORT` are set by the stack; secrets come from `env_file: ${WORKER_ENV_FILE:-/etc/gitinside/worker.env}`. Redis 7.4 runs as `redis` from the start (its entrypoint then needs no capability to switch users), read-only with an AOF volume, `noeviction` (BullMQ), 512 MB, on an `internal: true` network only, no published port.
  - **Check** (`infra/oracle/check.mjs`, CI job `worker-image`): builds the image, starts the stack with a fake env file plus `compose.check.yml`'s throwaway Postgres, migrates from inside the image, and asserts health on loopback, the port bindings, Redis's isolation, uid/capabilities/`NoNewPrivs`/seccomp of the worker process, `EROFS` everywhere but `/tmp/jobs`, the tmpfs flags, no package managers, a fixture tarball extracted and analyzed by the real sandboxed child into the golden bytes, and a clean SIGTERM with JSON logs.
- **Alternatives rejected:** copying the whole built workspace (the child's read root would hold every package's sources and dev tooling, and the image would be several times larger); a registry-built image (GHCR is free, but building on the VM from the checkout needs no account, token, or ARM cross-build); `distroless` (no `/bin/sh` is nice, but it pins a Node build we can't match to CI, and the read-only root plus no capabilities already leave a shell little to do); `seccomp` profile file of our own (Docker's default already blocks the dangerous calls; a custom one is maintenance with little gain for a process that never runs repo code).
- **Consequences:** the egress allowlist, Caddy, the provisioning script, and the VM docs are M5.10b. The image is built where it runs (`docker compose … up -d --build` on the VM). A new runtime dependency on a workspace package needs that package's `files` to include what it loads at runtime, or the CI check fails. Migrations run from inside the image (`@gitinside/db`'s `runMigrations`) or from a dev machine with `DATABASE_URL_UNPOOLED`.

## ADR-0075: Egress through a DNS-allowlisting gateway namespace; Caddy as a container; one idempotent provisioning script
- **Context:** M5.10b. SECURITY.md T4 makes the container's egress allowlist (GitHub API, codeload, R2, Neon) the boundary against network abuse. The worker speaks HTTPS through `fetch` and Postgres over TCP through postgres.js, so an HTTP proxy wouldn't cover the database (and the image's Node 22.18 `fetch` ignores proxy variables). Neon, R2, and GitHub addresses change, so a fixed IP list goes stale. ADR-0060 needs Caddy to pass the request target unchanged; ADR-0074 left Caddy, the provisioning script, and the VM docs here. SPEC asks for a VM rebuilt in minutes from a script.
- **Decision:**
  - **Gateway namespace:** a small `egress` container (`infra/oracle/egress/`, Alpine 3.22 with dnsmasq, ipset, iptables; `NET_ADMIN`, `NET_RAW` (iptables' set match looks the set up over a raw socket), and `NET_BIND_SERVICE` only, read-only root; it runs as root, so the env file it reads must be root's own, as on the VM, since it has no `DAC_OVERRIDE`) owns the network namespace, and the worker joins it (`network_mode: service:egress`). The rules belong to the namespace, and the worker has no capabilities, so it can't change them.
  - **DNS is the allowlist:** a shared `resolv.conf` (`nameserver 127.0.0.1`) sends every lookup to the gateway's dnsmasq. It forwards `api.github.com`, `codeload.github.com`, `<R2_ACCOUNT_ID>.r2.cloudflarestorage.com`, and the hosts of `DATABASE_URL`/`DATABASE_URL_UNPOOLED` (read from the mounted env file at start; only host names are logged), plus single-label service names, to Docker's resolver. Everything else is NXDOMAIN (`local=/#/`), and AAAA answers are dropped. Each address handed out for an allowlisted name goes into the `gitinside-allow` ipset.
  - **Rules (`OUTPUT`):** loopback, replies, the internal network's fixed subnet (`172.30.250.0/24`), DNS from root only, and TCP 443/5432 to addresses in the set. Everything else is rejected at once (TCP reset or ICMP, so a bug fails fast instead of hanging), and IPv6 is dropped. Docker's resolver (127.0.0.11) answers any name, so non-root processes may not ask it, which closes DNS as a side channel.
  - **Caddy** (`caddy:2.10.2-alpine`, `infra/oracle/Caddyfile`) publishes 443 only, gets a Let's Encrypt certificate through the TLS-ALPN challenge (port 80 stays closed), forwards only `/health`, `/enqueue`, `/jobs/*` to `egress:8080` with the target unchanged, caps bodies at 16 KiB, and answers anything else with 404. Admin API off, no access log (it would record signature headers). CI runs the same file with `WORKER_DOMAIN=localhost`, served from Caddy's local CA.
  - **Provisioning** (`infra/oracle/provision.sh`, run as root, safe to repeat): Docker Engine + Compose from Docker's apt repository, the `ip_set`/`xt_set`/`xt_owner` modules (persisted), NTP on, a check that the host's INPUT chain still rejects by default, a detached checkout of `/opt/gitinside` at `--ref` (default `origin/main`), `/etc/gitinside/worker.env` created from the example on the first run (then it stops for the values) and checked for required names after, images built on the VM, migrations from inside the image through the gateway, and a oneshot `gitinside.service` (`up -d --build --wait` / `down`) enabled at boot. The script body is one function, so replacing the script during the checkout is safe.
  - **Checks:** CI's `worker-image` job runs shellcheck on both scripts, loads the same modules, and `check.mjs` asserts, from inside the worker as uid 1000: allowlisted names resolve (IPv4 only) and connect on 443; port 80, raw IPs, the metadata address, other names, outside DNS servers, and Docker's resolver all fail; Redis still connects. It also checks Caddy (TLS health, an unsigned enqueue reaching the worker's 401, 404 elsewhere) and the gateway's and Caddy's hardening and networks. The script itself can't run on CI (it installs Docker), so its first full run is on the VM (M5.13).
- **Alternatives rejected:** host-level rules in `DOCKER-USER` (the same idea, but split between the host and the stack, and not testable on CI without changing the runner's resolver); an HTTP(S) CONNECT proxy such as Squid (doesn't cover Postgres, and `fetch` would need an agent); a static IP allowlist from GitHub's meta API and Cloudflare's ranges (stale, and far wider than four names); an SNI-filtering TLS proxy (Postgres starts TLS inside its own protocol, so there's no ClientHello to read); Caddy from Caddy's apt repository on the host (another package source on the VM, and outside the CI check); opening port 80 for the HTTP challenge (SECURITY.md allows 443 only).
- **Consequences:** R2 and Neon addresses are shared with other tenants, so the allowlist is by address, not by account (documented in SECURITY.md T4 and the VM README). A changed R2 account or Neon host takes a stack restart. If the gateway restarts alone, the worker keeps the old namespace and its rules but loses DNS, so it fails closed until `systemctl restart gitinside`. Addresses stay in the set until the gateway restarts. The VM firewall is the OCI security list plus Oracle's own host rules; the script checks but doesn't rewrite them, so it can't lock SSH out.

## ADR-0076: The security suite runs each malicious repo through the whole job pipeline at the production limits
- **Context:** M5.11. TESTING.md asks for malicious fixtures (postinstall scripts, huge files, symlink escape, path traversal, zip bombs, deep nesting, too many files) showing that the worker never runs repo code, stays inside the job folder, stops at its limits, and keeps secrets out of graphs. Each defense already had unit tests (`extract.test.ts`, `runner.test.ts`, `inventory.test.ts`), mostly at lowered limits and one layer at a time. Nothing showed the layers working together on a hostile repo, or that the real limits hold.
- **Decision:**
  - **One suite, `apps/worker/src/security.test.ts`,** where every case goes fake GitHub ⇒ `processJob` ⇒ `extractTarball` ⇒ the real sandboxed child ⇒ the stored graph, with no stand-ins and the default limits (500 MiB, 100,000 entries, 4,096-byte paths, 2 MB files, depth 64, 20,000 source files).
  - **Only `fixtures/malicious/postinstall-script/` is committed.** The other cases are archives no honest tool writes (`../` names, links, lying sizes) or are too big to commit, so the suite builds them byte by byte; `fixtures/malicious/README.md` lists them all. The `.npmrc` hook file is added to the archive in the test, because this repo's tooling refuses to write a committed `.npmrc`.
  - **"Never runs package scripts"** is checked three ways: the sentinel file every hook would write never appears (the job's `src` holds exactly the archived files, checked while the folder still exists), `node:child_process` is wrapped so the test sees every process the worker starts (exactly one: `node --permission … child.js`, no `--allow-child-process`/`--allow-worker`/`--allow-addons`), and the hostile Express route is still found, so the result isn't a skipped analysis. The fixture is never run to prove the sentinel works, as TESTING.md forbids executing fixtures.
  - **Defense in depth is tested on its own:** a symlink (a junction on Windows) planted on disk after extraction, which the extractor can never create, is still not followed by the analysis child.
  - Failures before analysis must leave no process and no files (`listing(root)` is exactly `jobs/`).
- **Alternatives rejected:** lowering the limits through the child protocol to make `too-many-files` cheap (a test-only knob on the production path, and it wouldn't show the real limit holds); committing the archives as binary files (opaque in review, and the zip bomb and 20,001 files would bloat the repo); running the cases in a container on CI only (the defenses are Node and our own code, and they hold on Windows too).
- **Consequences:** the 20,001-file case takes about 2.5 minutes on the Windows dev machine (extraction and the analyzer's walk cost ~2.7 ms per file each there) and seconds on Linux CI; the zip bomb case compresses 520 MiB of zeros (~11 s). Webhook signatures and private-snapshot access, the other two items in TESTING.md's list, arrive with M8.8.

## ADR-0077: Snapshot retention: a pure plan from the database rows and the bucket's own listing; rows deleted before objects
- **Context:** M5.12a. R2 is the one service that bills past its free 10 GB instead of stopping (ADR-0055, PROPOSALS P-1), and DESIGN.md §10 sets the policy: the latest 5 commits per public repo, plus commits a PR from the last 30 days names, and the oldest first, globally, past 8 GB. Nothing deleted snapshots yet.
- **Decision:**
  - **Pure planner, thin runner.** `planRetention` (`apps/worker/src/retention.ts`) takes the `done` rows, the bucket listing, the pinned commits, and the time, and returns the rows and objects to delete; `runRetention` reads those inputs and applies the plan. The plan is sorted with `compareStrings` and ties broken by ID, so the same input gives the same plan.
  - **Per public repo, by commit:** commits ranked by their served analysis (newest finish, as `findPublishedAnalysis` picks); the top 5 stay, older ones go (`beyond-latest`) unless pinned. Every other analysis of a kept commit is `superseded` (an older analyzer version no page serves). Private repos skip this rule (they are deleted on uninstall, M8.5) but count against the budget.
  - **Budget:** 8 × 10⁹ bytes, the smaller reading of "8 GB", measured from the **bucket listing** (ListObjectsV2), which is what R2 bills, not from our rows' `snapshotBytes`. Past it, the oldest unpinned snapshots go, private and latest ones too, until it fits.
  - **Orphans** (objects shaped like a snapshot key that no `done` row names: a failed last attempt after its upload, or a delete that failed last run) are deleted after an hour, since publish uploads before it writes the row. Keys of any other shape (future diffs) are counted, never deleted.
  - **Order of a run:** rows are read before the bucket is listed (so every row seen has its object listed); the whole listing must parse before anything is deleted (a page missing a field throws instead of under-counting); evicted rows are deleted, each only if still `done` with the listed key, and then only those rows' objects, unless a kept row still names the key (possible after a rename). A crash or a failed delete between the two leaves an orphan for the next run, never a row pointing at nothing.
  - **A `done` row whose object is missing is reported, not deleted:** deleting rows on the word of a listing is how a listing bug would wipe the database.
  - **Storage:** `ObjectStore` gains `list(prefix)` (async iterator, 1,000 keys a page, XML parsed by hand; no SDK, as ADR-0062) and `delete(key)` (a missing object counts as deleted), on the same SigV4 signer. The fake S3 server lists and deletes too.
  - **db:** `listStoredSnapshots`, `listPinnedShas` (PR base/head updated within 30 days, by the database's clock), `deleteDoneAnalyses` (matches `(id, snapshot_key)` pairs, 500 per statement).
- **Alternatives rejected:** summing `stats.snapshotBytes` instead of listing (misses orphans and anything not ours, and isn't what R2 bills); deleting objects before rows (a failure leaves `done` rows whose graph 404s); R2 lifecycle rules (age-only, can't express "latest 5 per repo" or pins); keeping every analyzer version of a kept commit (nothing serves them).
- **Consequences:** a commit re-analyzed in the instant between its row's delete and its object's delete would lose the new object (same key); the next view re-analyzes it, so this race is accepted and documented. Scheduling the run, the 80% quota alarm (R2 and Neon), and a quota command for M5.13's smoke test follow in M5.12b.

## ADR-0078: Hourly maintenance inside the worker (retention, rate-limit pruning, quota check); quota alarm as a log line and a command's exit code
- **Context:** M5.12b. ADR-0077 built retention but nothing ran it. SPEC §5 asks for a quota check in M5's smoke test, DESIGN.md §12 and SECURITY.md T9 for an alarm at 80% of a free quota, and the `rate_limits` table gained one row per caller per hour forever.
- **Decision:**
  - **Where it runs:** in the worker process (`apps/worker/src/maintenance.ts`), on a `setTimeout` chain: a minute after startup (so a crash-looping worker still runs it), then an hour after each run **ends**, so two runs never overlap. Shutdown cancels the next run and waits for one in progress (every step is safe to abandon, ADR-0077). No BullMQ repeatable job: there is one worker process, and a timer needs no Redis state to clean up.
  - **A run** (`runMaintenance`): retention, then `pruneRateLimits` (windows that ended over an hour ago; the current and the previous window stay, because `consumeRateLimit` relies on a row never vanishing inside its own hour and a refund may name the window that just ended), then the quota check. Each step runs even if an earlier one failed, logs `maintenance_failed` with its step name, and never throws.
  - **Quota check** (`measureQuotas`): a **fresh** bucket listing after retention (what R2 bills, not retention's estimate) and `pg_database_size(current_database())`, against 10 × 10⁹ bytes (R2) and 10⁹ bytes (Neon, SPEC's assumption until planning #4 reports the plan's figure). One `quota` log line with both, plus one `quota_alarm` line per resource at ≥ 80%.
  - **The alarm:** the worker can't open a `needs-abhinav` issue itself (it holds no token that may write issues, and shouldn't). `quota_alarm` is the signal in the VM's logs, and the **`quota` command** (`node dist/quota-bin.js`, `pnpm --filter @gitinside/worker quota`) prints the same lines and exits 0 / 2 (alarm) / 1 (bad config or a failed measurement), so M5.13's smoke test and any later check can act on it. The command is read-only and needs only `DATABASE_URL` and `R2_*`.
- **Alternatives rejected:** a cron container or systemd timer on the VM (a second process with the same secrets, more provisioning); Vercel Cron (Hobby allows only daily runs, and the web app has no R2 delete rights); measuring Neon through its API (another secret; `pg_database_size` needs none, though it is a floor of Neon's figure, which also counts history retention); reusing retention's `retainedBytes` for the quota (an estimate that assumes every delete succeeded).
- **Consequences:** the bucket is listed twice an hour (well inside R2's free Class A operations). The Neon limit is a constant to update when #4 closes. A `quota_alarm` only reaches Abhinav when someone reads the logs or runs the command; automating the issue would need a write token on the VM, which this design avoids.

## ADR-0079: M5 pre-deploy review fixes: a repo that went private is hidden in the database; canonical query redirects; deferred findings get their own task
- **Context:** M5.14a. The production half of M5's acceptance criteria needs the deploy (M5.13, blocked on planning #3–#7), so M5.14 is split: a (everything verifiable now) and b (the production smoke test and the `m5` tag). The fresh-eyes review of `m4a..HEAD` (two reviewers: web, and worker/db/infra) found 1 high, 4 medium, and 10 low issues.
- **Decision:**
  - **A repo GitHub no longer shows publicly is hidden in the database** (`hideRepo`: `visibility = 'private'`), not just answered with a 404. `viewRepo` does it when GitHub says `REPO_NOT_FOUND` or `REPO_UNAVAILABLE` for a published repo, so permalinks and `/api/graph` (which never ask GitHub, ADR-0068) stop too. It comes back only through GitHub's facts: `/api/analyze` now refreshes the repo row (`upsertRepo`) on a cache hit, so "Analyze" on a repo made public again restores it. Accepted gap: a permalink-only audience is never checked until someone opens the repo page or a README image does, and a CDN copy of a graph can live a day.
  - **Canonical queries:** the graph, badge, and diagram routes answer any query other than their own (none, or `?theme=dark|light` for the diagram) with a `308` to the canonical URL, cached a day, before any lookup (`lib/canonical.ts`). Made-up queries can no longer miss the CDN and reach the database and R2 one by one. Case variants of the path still can (bounded by the name's length).
  - **The CSP matcher excludes `api/`, not `api`:** owners such as `api-platform` are pages and get the CSP.
  - **A failed row write after a job was created is logged and still answered `202`** (the worker inserts the row itself when the job starts).
  - **Skipped tar entries list at most 512 characters of their path** (a pax path can be 1 MiB, and the first 50 go into the job's stored result in Redis).
  - **Shutdown cancels jobs before waiting for a maintenance run** (maintenance registered before the worker).
  - **DESIGN.md §12 corrected:** stalls and attempts are counted apart, so a job can start up to 5 times, not 3.
  - **Deferred to M5.14c, before the deploy:** the gateway mounting the whole env file (give it a hosts-only file); Redis without a password (reachable from the shared namespace); a stale head cache labeling an older commit "up to date" right after a job; "Analyze again" offered for permanent failures; retention deleting a row whose completed BullMQ job is kept (`created: false` loop for up to a day); `getTypeAtLocation` unguarded (one crash costs the whole `http` stage). Bumping `ANALYZER_VERSION` (M5 changed the output) joins M5.13, right before the first deploy. Job IDs that ignore the installation go to M8.3, the first time a job carries one.
- **Alternatives rejected:** checking GitHub on every permalink view (spends the 60-calls-an-hour unauthenticated quota on the views ADR-0068 kept free); deleting a went-private repo's rows and snapshots (an owner flipping visibility back would lose its history, and M8.5's uninstall deletion is the real deletion path); ignoring unknown queries in the handler (still a cache miss per query).
- **Consequences:** a repo made public again shows "Not analyzed yet" until someone asks for an analysis; that request is a cache hit, so it's free and immediate.

## ADR-0080: `getTypeAtLocation` is guarded too, answering `any`; M5.14c split into four
- **Context:** M5.14c, the deferred findings of ADR-0079. ADR-0070 guarded only `getSymbolAtLocation`, because "no symbol" is part of its contract. The M5 review noted that `getTypeAtLocation` runs on the same kind of node (the HTTP detector asks whether `axios(x)`'s argument is a string, the URL normalizer reads literal types) and goes through the same checker code that crashed in M5.8c. A throw there is caught only by the stage guard, so one bad expression cost the whole `http` stage: every request edge of the repo, with a `DETECTOR_FAILED` warning. The six deferred findings touch the analyzer, the web app, the worker's retention, and the infra stack, so M5.14c is split: c (this guard), d (web: stale head cache, "Analyze again" for permanent failures), e (retention removes evicted analyses' BullMQ jobs), f (gateway hosts-only file, Redis password; verified on CI's container check).
- **Decision:** `guardedChecker`'s `getTypeAtLocation` answers the checker's own `any` type (`getAnyType()`, public API) when TypeScript throws, and reports the node through the same `failed` callback, so the resolver adds one `TYPESCRIPT_INTERNAL_ERROR` warning per expression. `any` is the type TypeScript itself gives an expression it knows nothing about, and both callers already treat it as unknown: `isStringValued` answers false (the argument is read as a config), `literalType` answers no literal (a hole). Other checker methods stay unguarded: they take symbols or types the guarded methods already returned, or (`getShorthandAssignmentValueSymbol`, `getConstantValue`) haven't been seen to throw; the stage guard still catches them.
- **Alternatives rejected:** answering `unknown` or `never` (not public API in TS 5.6, and `never` reads as "no value", which a caller could treat as known); a `Proxy` over every method (rejected in ADR-0070 for the same reasons).
- **Consequences:** a TypeScript crash on a type costs that expression's reading (`axios(target)` becomes "the URL can't be read statically" instead of "starts with a value only known at runtime"), not every edge of the stage. Graphs that never tripped the guard are unchanged.

## ADR-0081: The head cache is keyed by the shown analysis; a failed latest commit carries its code
- **Context:** M5.14d, two web findings deferred by ADR-0079. (1) `viewRepo` remembers GitHub's latest commit per repo for a minute (ADR-0068). If a newer commit's analysis is published inside that minute (usually started by `/api/analyze`, which asks GitHub itself), the remembered answer still names the older commit; that commit has a finished analysis, so the page showed it as "Up to date with the latest commit". (2) A failed latest commit always offered "Analyze again", even for failures that fail the same way every time (over a limit, a blocked repo, an unreadable tarball): the click spends a slot of the visitor's limit and lands on the same failure.
- **Decision:**
  - **The head cache key includes the shown analysis** (`owner/repo@sha/version`). A publish changes what `findPublishedAnalysis` returns, so the old answer is a miss and GitHub is asked once more; repeated views of an unchanged page still cost one lookup a minute. No clocks are compared (the database's `finishedAt` and the web process's clock never meet).
  - **`HeadState` `behind`/`failed` carries the row's `errorCode`.** `headStatus` asks `permanentFailure` (`lib/jobs.ts`, the same table as the progress page's messages, now split into reason and advice): a permanent code gets "can't be analyzed" plus the reason and no button; anything else keeps "Analyze again".
  - **The status dot is drawn on the text**, not as the line's own flex item, so a sentence that wraps keeps the dot beside its first line (found in the screenshot review).
- **Alternatives rejected:** comparing the cached answer's time with the analysis's `finishedAt` (two clocks; tests on a fake clock would always miss); asking GitHub whenever the cache and the shown commit disagree (a repo that's behind for hours, e.g. a failed latest commit, would ask on every view and burn the 60-an-hour quota); dropping the button for every failure (a crash or a dropped download can pass on the next try).
- **Consequences:** each publish costs a repo page one extra GitHub lookup per web process. Codes the table doesn't know read as retriable, so a new permanent code needs a table entry to lose its button.

## ADR-0082: Retention removes the completed BullMQ job of each analysis it deletes
- **Context:** M5.14e, the last worker finding deferred by ADR-0079. A job ID is derived from the commit and analyzer version (ADR-0060), and BullMQ keeps a completed job a day (`removeOnComplete`). When retention deletes a `done` row inside that day, the next visit finds no analysis and enqueues the commit, but `add` sees the completed job and answers `created: false`; the progress page reports "done" and sends the visitor to a repo page that still has nothing. That loop lasts until the job expires.
- **Decision:**
  - **After deleting rows, `runRetention` asks the queue to remove the jobs of the rows actually deleted** (`CompletedJobs.removeCompleted`, on `BullJobQueue`), then deletes objects as before. Each ID is `jobIdFor({ kind: "analyze", owner, repo, sha }, analyzerVersion)` from the row and its repo's **current** owner and name (`StoredSnapshotRow` gains both): that's the name the web app enqueues under, so it's the ID a new request would collide with. A job enqueued under an older name has another ID and can't block anything.
  - **Only `completed` jobs are removed.** A waiting, running, or failed job with that ID is left alone (a running one is a re-analysis already on its way; a failed one has its own retry rules in `add`).
  - **A failed removal never fails the run.** The first ID that can't be read or removed (one 5 s timeout) stops the call and the rest count as `failedJobRemovals`, so a Redis outage costs one timeout, not one per ID. The job expires within the day anyway.
  - **`jobs` is optional in `runRetention`;** the worker's maintenance passes its queue. Tests and the read-only `quota` command run without Redis.
- **Alternatives rejected:** removing completed jobs sooner (`removeOnComplete` of minutes: the progress page and `GET /jobs/:id` need the result for a while after the job ends); having `add` re-run a completed job (the worker can't tell a deleted analysis from a cache hit without a database lookup on every enqueue); storing the job ID on the row (a migration for a value that's a pure function of the row).
- **Consequences:** a commit evicted by retention can be analyzed again at once. The Redis tests (the queue method and the whole loop through the worker process) run on CI only.

## ADR-0083: The egress gateway reads host names only; Redis requires a generated password
- **Context:** M5.14f, the two infra findings deferred by ADR-0079. (1) The egress gateway (ADR-0075) mounted the whole `worker.env` to learn three host names, so the one container that is root with `NET_ADMIN` also held every secret. (2) Redis had no password. It is reachable from the worker's network namespace, which the analysis children share, so a child whose network guard (`netguard.ts`) failed could read or forge queue jobs.
- **Decision:**
  - **`infra/oracle/egress-hosts.sh` derives `/etc/gitinside/egress.hosts` on the host** (the R2 endpoint and the hosts of `DATABASE_URL` / `DATABASE_URL_UNPOOLED`, one per line, world-readable, written then renamed). The parsing moved there unchanged from the gateway's entrypoint. `provision.sh` runs it, and so does the systemd unit's `ExecStartPre`, so an edited env file still needs only a restart. The gateway mounts that file alone and refuses any line that isn't a dotted lowercase DNS name (no wildcards, no dnsmasq syntax), so a bad file stops it rather than widening the allowlist.
  - **Redis gets `requirepass`.** `provision.sh` generates 32 random bytes (hex) once into a root-only `/etc/gitinside/redis.env`. Compose gives that file to Redis and to the worker (`env_file`); the gateway and Caddy don't get it. Redis reads the password as config on stdin (`redis-server -`), so it's on no command line, and it refuses to start without one. The health check passes it through `REDISCLI_AUTH`.
  - **The worker reads an optional `REDIS_PASSWORD`** and passes it to BullMQ beside the URL (`redisConnection`), never inside it, so the URL stays safe to log. The analysis child already starts with an empty environment (ADR-0059), so it never has the password.
  - **CI's container check covers it:** it runs `egress-hosts.sh` on good and bad env files (bad values exit 1 and are never echoed), runs the gateway image on bad hosts files (each exits 1), and asserts on the running stack that the gateway's only bind mounts are the hosts file and `resolv.conf`, no secret name is in its environment, Redis answers `NOAUTH` to an unauthenticated `PING` from the worker's namespace, and the password is on no command line in the Redis container. The worker's own health check (a queue ping) shows the password works.
- **Alternatives rejected:** a password inside `REDIS_URL` in `worker.env` (Redis would then need the whole env file, or Abhinav would have to keep two copies in sync); Compose `secrets:` (without Swarm they're bind mounts, and the non-root `redis` and `node` users can't read a root-owned 0600 file); an ACL file with a hashed password (the worker still needs the plain one, so it adds a file without removing one); a one-shot container that derives the hosts file (it would mount the secrets itself).
- **Consequences:** a fresh VM needs nothing new from Abhinav: the password is generated. Rotating it is deleting `redis.env` and running `provision.sh` again. Local development and CI's Redis service stay passwordless (`REDIS_PASSWORD` unset).

## ADR-0084: `GraphDiff` carries head records so it's complete on its own; `packages/diff` starts with `applyDiff`
- **Context:** M6.1. DESIGN.md §8 asks for a `GraphDiff` of "ID references plus summary counts", and also for the property `apply(base, diff(base, head)) == head`. ID references alone can't rebuild head: an added node's record, a model's new fields, or a symbol's new source line are only in head. The same section classifies nodes as added, removed, modified ("different fingerprint"), and renamed, and edges as added or removed; but most records differ between commits only in facts nobody reviews (a source line that moved, an edge's call sites), and a renamed node changes the IDs of every edge on it, since `edgeId` embeds the endpoints.
- **Decision:**
  - **Added, changed, and renamed entries carry the head record whole; removed entries carry the base ID.** `applyDiff(base, diff)` in `packages/diff` rebuilds head (canonical order, validated by `parseGraph`) and refuses a diff that doesn't fit: another base repo, commit, or analyzer version, a removed or changed ID the base lacks, an added ID it already has.
  - **Two lists for "same ID, different record": `modified`** (a fingerprint field changed, shown amber) **and `updated`** (anything else, not shown). Each entry names the differing fields (`changes`), so the viewer and the PR comment can say "method changed" without diffing records again. The fingerprint fields per kind are M6.2's call, not the schema's.
  - **Edges get `renamed` too**, for edges whose endpoints were renamed, so a moved file doesn't show every one of its edges as removed and added.
  - **`broken` entries name the base edge**, its base target, a reason code, a sentence, and the head call sites, so the PR comment and the Check Run need nothing else.
  - **Warnings are a multiset diff** (`added`/`removed`), because the same warning can occur twice and has no ID.
  - **`summary` is checked against the lists** by `parseGraphDiff`; builders call `summarizeDiff`. **`stringifyDiff`** serializes like `stringifyGraph`.
  - **`checkComparable` refuses graphs from two analyzer versions** (every analyzer change would read as a code change), not graphs of two repos (a fork's PR head is analyzed under the fork's name; the CLI names local folders as told). The diff records a single `analyzerVersion`.
- **Alternatives rejected:** ID references only, with `apply(base, diff, head)` (the property would be trivial, and a stored diff couldn't be rendered without fetching head); one `modified` list with a "significant" flag (every consumer would filter it); edge renames as removed + added (a file move would flood the changes list).
- **Consequences:** a stored diff grows with the size of the change, not the repo. `packages/diff` has no `diffGraphs` yet; M6.2 builds it on these types and `summarizeDiff`, and M6.5's property tests check it against `applyDiff`.

## ADR-0085: Fingerprints are an explicit per-kind field table checked against the schema
- **Context:** M6.2. `diffGraphs` must split "same ID, different record" into `modified` (shown to a reviewer) and `updated` (not shown). DESIGN.md §8 names the fingerprint as "signature, route method/path, or model fields", but the schema has no symbol signature or body hash, and a rule like "everything but `label`/`source`" would silently promote any field added to the schema later.
- **Decision:**
  - **`NODE_FINGERPRINTS` (`packages/diff/src/fingerprint.ts`) lists, per kind, the fields that make a node `modified`;** `label` and `source` are incidental for every kind. `kind`, `parentId`, and `layer` count for all kinds (they change where and how the node is drawn). A test checks that every field of every kind in the zod schema is classified exactly once, so a schema change fails the test until someone decides.
  - **Edges:** every field but `sites` (and `id`) is a fingerprint: `confidence`, `label`, `reason`, `fields`.
  - **A model's `fields` are compared as a set keyed by name:** reordering columns makes the model `updated`; a dropped, added, retyped, or newly optional column makes it `modified`.
  - **Comparison ignores key order and `undefined`** (`changedFields` uses sorted-key JSON), so a record read back from Postgres `jsonb` equals the one written; both graphs are canonicalized first, so input order never shows up.
  - **Symbols have no signature fingerprint:** a function whose body or parameters changed shows through its file's `hash`. M6.4's `PARAMETERS_ADDED` will need parameter facts that the schema doesn't carry yet.
- **Alternatives rejected:** a blacklist of incidental fields (new fields would be fingerprints by accident); hashing whole records minus `label`/`source` (no `changes` names, and model reordering would read as a change); adding a symbol signature to the schema now (an analyzer and schema change belongs with M6.4, which needs it).
- **Consequences:** `diffGraphs` exists with `renamed` and `broken` empty until M6.3 and M6.4; a moved file is removed + added for now.

## ADR-0086: Rename detection reads file contents from the caller; thresholds measured on real repos; ties stay unmatched
- **Context:** M6.3. DESIGN.md §8 matches moved files by shingled-token Jaccard (≥ 0.6) and symbols by body hash or by name plus similarity ≥ 0.8. The graph has no file text and no symbol body hash, only each file's SHA-256 and each symbol's line span. `packages/diff` also has to stay usable in browsers (M6.9), so it can't read the disk.
- **Decision** (`packages/diff/src/rename.ts`, `detectRenames`, called by `diffGraphs`):
  - **Contents are an option:** `diffGraphs(base, head, { contents: { base(path), head(path) } })`, by repo-relative path. The CLI (M6.6) and the PR job (M8.6) have both trees. Without contents, a file matches only by identical `hash`, and symbols only by following their file. The graph schema doesn't change.
  - **Only base-only and head-only IDs are paired, of the same kind, one to one.** The order is files, then modules, then symbols, then unresolved nodes:
    - **Files:** identical hash scores 1. Otherwise, with contents, a Jaccard over 4-token shingles of at least 0.6. Files under 50 tokens match by hash only.
    - **Modules (folders):** a removed folder matches an added one when more than half of its files moved there and more than half of the new folder's files came from it.
    - **Symbols:** the same qualified name and `symbolKind` under a renamed parent (file or class), with a body similarity of at least 0.8 when both bodies can be read. Otherwise the body (the `source` lines, its own name masked) must be equal token for token, at least 20 tokens, and the only such body on both sides. That catches a function renamed in place or moved to another file. Parent-following runs again afterwards, so a renamed class's methods follow it.
    - **Unresolved nodes** (their IDs are positions): the same reason, expression, and detail in the same file or its renamed file, paired in source order only when both sides have as many.
  - **Ties are never broken by guessing.** Candidates are sorted by score, then a shared base name. Within one (score, rank) tier, a pair is taken only when neither end has another candidate. Ambiguous ends are dropped from lower tiers too, so two identical files removed and two added stay removed + added.
  - **Edges follow their endpoints:** a base-only edge whose endpoints map to a head-only edge ID is `renamed`. A same-ID node whose `parentId` followed a renamed parent is `updated`, not `modified` (a route in a moved file).
  - **Budget:** past 250,000 removed × added file pairs, content is compared only between files with the same base name. Identical hashes always match.
  - **Thresholds were measured** on 5,898 source files of cal.com and the eval repos at their pinned commits, using synthetic edits of 400 sampled files at 50+ tokens:

    | Shingle size | 20% of lines deleted | 20% new lines inserted | Top identifier renamed |
    | --- | --- | --- | --- |
    | 3 | 96.5% | 96.0% | 98.5% |
    | 4 | 96.0% | 92.0% | 95.5% |
    | 5 | 89.5% | 86.3% | 87.8% |

    Each figure is the share of edited files scoring ≥ 0.6 against their original. Random pairs of different files scored ≥ 0.6 in 0.04% of 20,000 at every size. Same-name pairs (e.g. two `route.ts`) did so in 4.9% at size 4 (3: 5.6%, 5: 4.3%); these are mostly near-copies such as cal.com's app-store templates. The checkouts are shallow, so real renames couldn't be replayed from history. Among the repo's fixtures, the only pair over 0.6 is a 13-line server copied with 4 lines changed; a test pins that list.
- **Alternatives rejected:**
  - Per-file shingles or MinHash in `architecture.json`: every graph grows, and it's an analyzer change for a diff-only need.
  - Hashing contents inside `packages/diff` to check them against `hash`: that needs `node:crypto` in a browser-bound package.
  - Greedy matching that breaks ties by path: a guessed rename can hide a removed target from M6.4's broken-edge check.
  - k = 3: slightly better recall, but more same-name near-copies matched. k = 5: a tenth fewer true moves.
- **Consequences:** a moved and edited file is renamed only when the caller passes contents. A renamed service (every ID in it changes) and a moved model, route, or page are not detected: the last three keep their IDs and show as `updated`. A file split in two matches at most one half. M6.5's property tests must cover diffs with renames.

## ADR-0087: Broken edges are found by re-resolving head's unresolved calls against the base target, inside `packages/diff`; the route grammar moves to the schema
- **Context:** M6.4. DESIGN.md §8.4 calls a base edge broken when its source still makes the call but the target is gone or changed incompatibly, found by "re-running the resolver on head". The diff gets only two graphs (plus optional file contents) and must run in browsers, so it can't import the analyzer (TypeScript). Head's analyzer already ran its resolver: a call whose target disappeared shows up in head as an `unresolved` node with the call's text (`NO_MATCHING_ROUTE` + `METHOD url` label, `UNKNOWN_SYMBOL` + import specifier, `UNKNOWN_SYMBOL` + `client.accessor.op`). What's missing is the link from that unresolved call back to the base target.
- **Decision** (`packages/diff/src/broken.ts`, `detectBroken`, called by `diffGraphs`):
  - **Only base edges whose target is gone** (removed, not renamed) **and whose source exists in head** (by ID or rename) are candidates. A route's ID contains its method and path, so a changed route is always removed + added; there is no same-ID "incompatible route" case.
  - **Head re-resolution:** the candidate is broken when the head source has an edge of the same kind to an unresolved node that would have resolved to the base target:
    - `http` ⇒ route: the node's label is read back into a method and path segments (clipped labels and remote hosts refused) and matched against the base route with the analyzer's own path grammar and method rules.
    - `imports` ⇒ file: a relative specifier, resolved from the importer's head path as TypeScript does without `paths` (extensions, `.js` ⇒ `.ts`, `index.*`), names the file's path.
    - `reads`/`writes` ⇒ model: the Prisma call's accessor is the model name with its first letter lowercased.
  - **`ROUTE_CHANGED`** when the removed route's handler (or its renamed self) serves a route that's new in head ("POST /api/orders is now PUT /api/orders"); otherwise `TARGET_REMOVED`. Each broken edge carries the head sites that still make the call.
  - **The route path grammar** (`parseRoutePath`, `alignSegments`, `UrlSegment`) moves from `analyzer/src/match.ts` to `@gitinside/schema` (`routes.ts`), which the analyzer re-exports, so the matcher and the diff can't drift apart.
  - **`GraphDiff` validation** now requires each broken edge to be a removed edge, its target a removed node, and its source in head.
- **Alternatives rejected:** matching base call sites to head ones by position (lines shift with any edit); pairing "the source lost a target and gained some unresolved call" without re-matching (flags unrelated new calls); importing the analyzer's matcher into the diff (pulls TypeScript into the browser bundle); a separate copy of the grammar in the diff.
- **Consequences:** M6.4 split. **M6.4a** (this) covers `TARGET_REMOVED` and `ROUTE_CHANGED` for routes, relative imports, and Prisma models. **M6.4b** needs analyzer facts the graph lacks: required parameter counts on symbols and argument counts at call sites (`PARAMETERS_ADDED`), and the field names a Prisma call uses that the model no longer has (today the analyzer drops unknown names, so `FIELD_REMOVED` can't be seen). Not detected at all: calls to removed functions (an unresolved local call makes no node), aliased or package imports, and `renders`/`publishes`/`consumes`/`external_call` edges.

## ADR-0088: `PARAMETERS_ADDED` and `FIELD_REMOVED` from per-call facts on edge sites and a required-parameter count on symbols
- **Context:** M6.4b. DESIGN.md §8.4 also calls an edge broken when its target survives but changed incompatibly: a function needs more arguments, or a model field the caller uses is gone. The graph couldn't show either: symbols had no signature, `calls` edges no argument counts, and the Prisma detector dropped field names the model doesn't declare, so head had no trace of a call still naming a removed field. A count on the edge (e.g. the fewest arguments any site passes) or a list of unknown names on the edge would flag every site of the edge, including ones that are fine, and the PR comment would point at the wrong lines.
- **Decision:**
  - **Symbols get `requiredParams`**, the position of the last parameter without `?`, a default, or `...` (TypeScript's minimum argument count; `this` doesn't count). A class's count is its constructor's; a class without one is 0 unless it `extends` something (then unknown). Absent for non-callable variables, overloaded functions and methods (callers see the overloads), several constructor signatures, and **every symbol in a JavaScript file**: the checker treats JS parameters as optional, so a count would claim a contract the code doesn't state. It's a symbol fingerprint, so a function needing another argument is `modified`.
  - **Edge sites become `CallSite`**: a `SourceLocation` plus facts about that one call. `args` on every `calls` site (absent when a spread hides the count; `new C` passes 0). `missingFields` on a Prisma `reads`/`writes` site when the call uses names its model lacks, except `AND`/`OR`/`NOT`, `_`-prefixed selectors, and compound unique keys whose `_`-parts are all fields. The edge's `fields` still lists only real fields.
  - **The diff checks surviving edges** (`contractBreak` in `broken.ts`): for a base edge whose target and source exist in head (by ID or rename) and whose head edge exists, `PARAMETERS_ADDED` when `requiredParams` rose and a head site passes at least the old count but fewer than the new one; `FIELD_REMOVED` when a head site's `missingFields` names a field base's model had and head's lacks. Only those sites are listed, as plain locations.
  - **Validation by reason:** `TARGET_REMOVED`/`ROUTE_CHANGED` keep ADR-0087's rules; `PARAMETERS_ADDED`/`FIELD_REMOVED` need the edge not removed and the target modified or renamed.
  - **No schema version bump:** the fields are optional, so stored graphs still parse.
- **Alternatives rejected:** a full parameter signature (names and types) on symbols: bigger graphs, and type changes can't be judged without the checker; edge-level `minArgs`/`missingFields` (flags every site of the edge); flagging any site passing fewer than the new count (a call already short in base wasn't broken by this change); counting JS parameters (most JS code omits trailing arguments on purpose).
- **Consequences:** every fixture golden gained `args` and `requiredParams`; the eval report is re-recorded. A renamed field reads as removed + added, so callers of the old name are flagged (correct: they break). A named compound key (`@@unique(name: "…")`) appears in `missingFields` but is never flagged, since base's model has no such field. Not detected: parameter type changes, a field that became required, JS functions, overloads.

## ADR-0089: `gitinside diff` lives in the analyzer's CLI, checks git refs out into hook-free temporary worktrees, and has an architecture-level Mermaid summary in `packages/diff`
- **Context:** M6.6. DESIGN.md §4 put a CLI in `packages/diff`, but diffing two git refs means analyzing both, and the diff package must stay free of TypeScript and Node (the viewer's diff mode and the web app import it). The PR comment (M8.6) needs a Mermaid summary of the change. A repo's diff can touch thousands of files and symbols, which no PR comment can draw, and labels come from the repo (SECURITY.md T10).
- **Decision:**
  - **One binary:** `gitinside diff <base> <head> [--repo <dir>] [--format json|mermaid] [--out <file>]` is a second command of the analyzer's `gitinside` CLI, which now depends on `@gitinside/diff` (not the reverse).
  - **Each side** (`openSide`, `packages/analyzer/src/revisions.ts`) is tried as a graph file (parsed, no file text), then a folder (analyzed in place), then a commit in `--repo` (default `.`): `git rev-parse --verify --end-of-options <ref>^{commit}` (so a ref can't pass as an option), then `git worktree add --detach` into a fresh temp folder with `core.hooksPath` set to an empty folder, so no `post-checkout` hook runs, then analyzed with the full SHA recorded. Worktrees are removed in a `finally`, including when the other side fails. Both sides' file text is passed to `diffGraphs` for rename detection.
  - **`renderMermaidSummary(diff, base, head)`** in `packages/diff`: broken connections first, source to base target, at any level, since they're the point of the comment. Then added/removed/changed/renamed services, routes, pages, models, datastores, queues, external hosts. Then changed `http`/`reads`/`writes`/`stores`/`publishes`/`consumes`/`external_call` edges, each endpoint lifted to the nearest node of those kinds and merged per pair ("Added reads, writes"). Files, folders, symbols, and `imports`/`calls`/`handles`/`renders` edges appear only as broken endpoints. Status is in words and in border color (the light theme's diff tokens, legible on both GitHub themes), removed dashed. At most 40 nodes (broken endpoints first), the rest counted in a note. Node names are `n1…` by draw order. Nodes that would read the same ("datastore postgres" from two compose files) add their service, else their declaring file. Labels are whitespace-collapsed, cut at 60 code points, and every character outside `[A-Za-z0-9 ._,()/:@-]` becomes a `#<code>;` entity, so a label can't close its quotes or carry `%%`, HTML, or a `click` directive.
- **Alternatives rejected:** a CLI in `packages/diff` (it would need the analyzer, pulling TypeScript into a browser-bound package); `git archive` + extraction instead of worktrees (needs a tar extractor in the analyzer; the worker's lives in `apps/worker`); drawing every changed node (unreadable past a few dozen); a per-character escape list of Mermaid's syntax (an allowlist can't miss one); a `--fail-on-broken` exit code (CI use waits for the PR bot's Check Run, M8.6).
- **Consequences:** the worker image now carries `@gitinside/diff` with the analyzer (it needs it for M8.6 anyway). Git filters configured by the user (e.g. LFS) still run on checkout; repo content can't define one. `.gitignore` isn't read, so a folder side walks ignored folders outside `IGNORED_DIRS` (as `analyze` does); refs don't, since a worktree holds only tracked files. Each ref side is a full analysis; M6.7's cache will share unchanged files.

## ADR-0090: Incremental analysis reuses per-service facts, validated against every input the service's analysis observed, from a disk LRU cache
- **Context:** M6.7. DESIGN.md §9 planned per-file facts in which a changed file invalidates itself and its direct importers. But the detectors ask the type checker, which follows types through transitive imports, and some facts depend on importers rather than imports: Express composes a router's routes with prefixes from the files that mount it, and a wrapper keeps its own request only when nothing calls it. Direct-importer invalidation would let a warm run produce a different graph from a cold one, breaking "same commit ⇒ byte-identical graph". The time goes into building the per-service programs (12–33 s of 27–77 s on cal.com, M1) and checker queries (imports, calls), and a checker needs the whole program, so per-file facts alone save little unless the program isn't built at all.
- **Decision:**
  - **The unit of reuse is a service.** Its facts are what each program stage found in its files, in serializable form (symbol nodes, import and call edges, Express and Next.js routes, Prisma reads/writes, HTTP requests before route matching, SDK and queue edges, warnings).
  - **Entries are validated by observed inputs.** While a service is analyzed, every repo path its program host and detectors read or probe is recorded with its content hash (SHA-256) or "absent", including other services' files reached through workspace imports. On the next run the entry is reused only if every recorded input answers the same. A changed, added, or deleted file therefore invalidates each service that read or looked for it: its own, its importers transitively, and dependents in other services. This is §9's importer invalidation made transitive, and it's sound because the facts are a function of those answers.
  - **Global steps always rerun from facts:** route matching, wrapper binding (wrappers become per-service facts first), the Prisma schema, infra, file nodes, and assembly. A clean service's program is built only when a dirty service's checker needs it.
  - **Storage** (`openDiskCache`, M6.7a): gzipped JSON entries in a folder, named by the SHA-256 of the key, which the cache prefixes with its entry format, `SCHEMA_VERSION`, and `ANALYZER_VERSION`. The full key is stored and compared on read. Writes go to a temporary file and are renamed into place. Past the cap (2 GB by default), the folder is listed again and the least recently used entries (by file time, touched on hits) are deleted down to 90%. Corrupt or mismatched entries are misses and are deleted; failed writes are counted and ignored, so the cache can only cost time.
  - **Steps:** a cache store; b observed inputs; c wrappers as facts; d per-service fact bundles with no output change; e `analyze({ cache })` and `--cache`, tested by comparing warm and cold bytes over fixture edits; f the worker's cache volume.
- **Alternatives rejected:** per-file facts with direct-importer invalidation (unsound, above); per-file facts invalidated through the transitive import closure within one program (the checker still needs the whole program built, and every detector would need a per-file/global split; reconsider if single-package repos need it after M6.8 measures); persisting TypeScript ASTs or programs (not serializable); an in-memory cache in the worker (each analysis runs in a fresh child process, ADR-0059); a cache library or SQLite (a folder of renamed files needs no dependency and is safe across the worker's two concurrent children).
- **Consequences:** a single-package repo gains nothing from M6.7, since any change reruns its one service; M6.8 measures a monorepo and reports this. Facts derived from private repos would outlive an uninstall on disk, so M6.7f keeps private entries in a per-installation folder that M8.5 deletes. The cache never enters the graph: a miss recomputes the same facts.

## ADR-0091: Observed inputs are recorded by a per-service compiler host, plus the programs the resolver reached
- **Context:** M6.7b. ADR-0090 validates a service's cached facts against every repo path its analysis read or probed. Before this, all service programs shared one host, the config lookup and the shared `package.json` cache bypassed it, nothing noticed a file added to a service folder that nobody probed, and detectors reach other services' programs through workspace package imports TypeScript can't resolve.
- **Decision:**
  - **Each service gets its own host** (`buildServicePrograms`), the only way its program and per-service detectors reach repo files. It records into the service's `InputLog` (`inputs.ts`): a read file's SHA-256 (of its bytes; hashed once per run per path), a probed file as `present`/`absent`, a probed folder as whether the inventory has a file under it. The tsconfig lookup now probes through the host, and the module resolver's manifest cache is keyed by reading service too, so each service's read is logged.
  - **The root-file listing is an input.** A service's program roots are its folder's source files (`programRootFiles`, moved to `inputs.ts`), so a new file changes its program even if nothing probed that path.
  - **Programs reached count too.** `SymbolResolver.reached(sp)` lists the other programs `sp`'s analysis used, recorded in `importTarget` (also inside `resolve`) and `programOf(path, from)`, which now takes the asking program; detectors must reach other programs only through these. `serviceInputs` merges a service's log with those of every program it reached, transitively (a superset: a hop recorded during another service's analysis is included too).
  - **Answers are compared, not timestamps.** `createInputVerifier(root, workspace, inventory)` checks listings, folders, then files (hashing lazily, once per path per verifier), and returns the first input that changed, or undefined. An unreadable file counts as changed.
  - **Global inputs stay out of the log** and go in M6.7e's cache key: the workspace layout (service keys, folders, package names), the inventory limits, TypeScript's bundled `lib.*.d.ts` (our install, so `ts.version` belongs in the key), and the inputs of global steps (workspace configs, Prisma schemas, compose and `.env` files, file nodes), which always rerun.
- **Alternatives rejected:** recording the `reached` hops dynamically with a "current service" set by each detector loop (every detector would need to set it, and a missed one fails silently; the resolver is already the single door); hashing decoded text (bytes match `file` node hashes and need no decoding to verify); listing whole folders as inputs (an added non-source file would invalidate a service for nothing).
- **Consequences:** reverse dependencies aren't inputs: a wrapper's request and an Express router's prefixes depend on who imports them, which an importee's log can't see. M6.7c (wrappers) and M6.7d (route composition) make those global steps over facts. The log covers every read by test: over 13 fixtures, every `readFileSync` the pipeline makes is in some service's log with its hash, and every repo file in each program is in that service's log; edits on a temporary monorepo invalidate exactly the expected services.

## ADR-0092: Wrapper calls are inlined in the caller's service; a global step only decides which wrappers keep their own requests
- **Context:** M6.7c. ADR-0091 left one reverse dependency in the HTTP stage: a wrapper's site makes its own request only when nothing calls it, and who calls it isn't in the wrapper service's inputs. ROADMAP's plan was wrapper URL templates per service, bound to callers' arguments by a global step without TypeScript. But `normalize(site, bindings)` isn't compositional over argument values: a ternary keeps its parts only when both branches read the same after binding, `new URL(path, base)` and axios's `baseURL` join depend on the argument's text (absolute or not), `?? fallback` keeps only an env var, and the step and hop budgets span wrapper and argument together. A template language reproducing that would be a second normalizer to keep byte-identical with the first.
- **Decision:**
  - **`HttpRequest` is plain data.** The `fetch`/axios call is its location and client, `via` is the wrapper's symbol ID, and the text an unresolved node shows (`label`, `expression`, both through `redactedText`) is computed with the request instead of in `buildHttpEdges`.
  - **`collectHttpFacts` gives each service an `HttpFacts`:** the requests of its non-wrapper sites, its wrappers (ID, called name, and the requests they make uncalled), and its calls to wrappers anywhere, inlined during that service's analysis with the wrapper's live sites. A service calling a wrapper in another program records that program with `resolver.programOf`, so the wrapper's inputs are the caller's inputs (`serviceInputs` follows it); before, a cross-service relative import TypeScript resolved itself recorded nothing.
  - **`bindWrappers` is the global step:** direct requests, then per wrapper (by ID) every service's calls in program order, or the wrapper's own requests when there are none, then the same sort as before. `inlineWrappers` is the two together; `analyze` calls them separately.
  - **One global input remains:** a call is resolved only if spelled like some wrapper in the repo or through an import alias (the cheap filter, unchanged), so a service's call facts also depend on the repo's set of wrapper names, which every service's facts carry (`WrapperFact.name`). M6.7e recomputes a clean service's call facts when that set changes.
- **Alternatives rejected:** URL templates bound globally (not byte-identical, above); resolving every call to drop the name filter (doubles the resolver's work, and a newly resolved expression can add a `TYPESCRIPT_INTERNAL_ERROR` warning, changing output); keeping TypeScript nodes in `HttpRequest` (not cacheable).
- **Consequences:** no output change: goldens and eval are identical. Every wrapper site's own request is now normalized even when called (the same expressions `parameters` already evaluated, so no new checker questions), and `redactedText` runs for every request rather than only unresolved ones. Owners from inline Express handlers are route IDs, whose prefixes still depend on mounting files; M6.7d handles route composition.

## ADR-0093: Express routes are per-service facts with router references, composed globally
- **Context:** M6.7d1. Express was the largest reverse dependency left (ADR-0091): a router's full paths come from the files that mount it, possibly in another service, and whether an expression *is* a router depends on every service (a parameter becomes one when any call passes it a router, in rounds until nothing new appears). Its one pass over all programs mixed checker questions with that global state. M6.7d was split: d1 Express; d2 the owners other detectors take from inline handlers (route IDs); d3 every remaining stage as a fact bundle, with `analyze` rebuilt as facts → compose.
- **Decision:**
  - **`collectExpressFacts(sp)` asks only its own program:** router creations (syntax), parameter bindings (argument → parameter), and route and `use` registrations in source order, with static paths and prefixes, path text and sites, and each handler's resolved symbol and inline-function node keys. Handlers of dynamic paths aren't resolved (they never get edges).
  - **Routers are `RouterRef`s, not objects:** what `routerOf` would have walked (the value's node key, then a chained call's receiver or a factory's returns), evaluated later against the known routers in the same order, so the first match is the same. Only nodes that can become routers keep a key (creation calls with their file's `express` bindings, parameters), and references with no such node are dropped.
  - **`composeExpressRoutes` is the old passes 1–3 and the walk over facts,** in program order: creations, binding rounds, registrations, then composition. A router's service (its routes' ID prefix) is the program owning its file as a root, from `rootFileServices` (a listing, available without programs), else the collecting service, as `programOf(file) ?? sp` was; so the collector records no reached program for it.
  - **`inlineHandlers` is keyed by node key** (`inlineRoutesOf`), not `ts.Node`, so it can come from facts; queues' enclosing-owner walk looks it up only in root files, as node identity did.
  - **A repo with no router creation collects only creations** (`scanned: false`), keeping the old early return's cost; M6.7e recomputes such facts when a creation appears anywhere.
- **Alternatives rejected:** Express as a global stage over all programs (every clean program would be built on every run); resolving `RouterRef`s per service against a cached router set (a global input changing whenever any service adds a router); keeping only syntactic creation keys (a creation call outside a root file would stop descending where the old code descended).
- **Consequences:** no output change: goldens and eval are identical, and composing JSON round-tripped facts equals the one-shot detector on four fixtures. The collector evaluates references eagerly, so it asks the checker about more expressions than the old short-circuiting walk (it descends past nodes that turn out to be routers, and reads paths and handlers of registrations on things that turn out not to be); those answers never reach the output.

## ADR-0094: Detector owners name inline handlers by node key, bound after Express composition
- **Context:** M6.7d2. The Prisma, HTTP (sites and wrapper calls), SDK, and queue detectors draw edges from the code a call sits in: the innermost symbol, or the routes of an inline Express handler around it. Each walk looked the routes up in Express's `inlineHandlers` while descending, so a service's results depended on Express's global composition: remounting a router in another service changed them, and a cached service would go stale with none of its inputs changed.
- **Decision:**
  - **`Owners` is plain data** (`packages/analyzer/src/owners.ts`): the node keys of the arrow and function expressions around a call, innermost first, up to and including the one at the nearest symbol, plus fallback `ids` (that symbol, a detector's fallback such as the file node, or none). `ownersAt` is the one step every walk takes per node; queues' bottom-up enclosing-owner walk builds the same shape.
  - **`bindOwners` is the global step:** the routes of the first key Express lists, else `ids`. It runs after the walk: `bindWrappers(facts, inlineHandlers)` for HTTP, and after each detector's walk for Prisma (`PrismaUse` list), SDK (request list), and queues (events), in walk order, so edge merging (first confidence kept unless `exact`, site order) is unchanged.
  - **File-node fallbacks are applied before binding** (`withFallback`): bound routes are never empty, so "fallback when `ids` is empty" equals the old "fallback when the bound owners are empty".
  - `inlineRoutesOf` is gone; `collectHttpCalls` and `collectHttpFacts` no longer take `inlineHandlers`.
- **Alternatives rejected:** recording only the innermost function expression (a call in a non-handler callback inside a handler belongs to the handler, so every candidate up to the symbol is needed); running these detectors after Express with its map as a per-service input (any remount anywhere would invalidate them).
- **Consequences:** no output change (goldens, eval). Walks compute a node key for every arrow and function expression, even in repos without Express, and the Prisma, SDK, and queue detectors still keep TypeScript nodes in their intermediate results; d3 turns those into fact bundles.

## ADR-0095: Snapshots live in Oracle Object Storage, reached through its S3-compatible API with `SNAPSHOTS_*` settings
- **Context:** M5.12c. ADR-0013/0055/0062 put snapshots in Cloudflare R2. Abhinav won't put a card on Cloudflare (#5), and chose PROPOSALS P-2 option 1: Oracle Cloud Object Storage on the Always Free account the worker VM uses (#3). Oracle lists 20 GB of storage and 50,000 API requests a month free, and an Always Free account isn't billed unless upgraded. The store code was already plain S3 (our SigV4, path-style URLs, ListObjectsV2), so the change is configuration, limits, and the egress allowlist.
- **Decision:**
  - **Settings:** `SNAPSHOTS_NAMESPACE`, `SNAPSHOTS_REGION`, `SNAPSHOTS_ACCESS_KEY_ID`, `SNAPSHOTS_SECRET_ACCESS_KEY` (a Customer Secret Key), `SNAPSHOTS_BUCKET`, in the worker's env file and in Vercel. The `R2_*` names are gone; nothing reads them.
  - **The endpoint is built, never read:** `https://<namespace>.compat.objectstorage.<region>.oraclecloud.com` (`oracleS3Host`). Namespace and region must each be lowercase DNS-label text (no dots), so a bad setting can't send the bucket's keys, or the egress allowlist, to another domain. `egress-hosts.sh` applies the same rule to the same two values and derives the same host.
  - **Signing region** is the Oracle region identifier (`us-ashburn-1`), not R2's `auto`; the fake bucket now checks the region it was started with.
  - **Limits:** the quota check measures the bucket against 20 × 10⁹ bytes (the smaller reading of "20 GB"); retention's budget is 16 × 10⁹ bytes, the 80% alarm point, as 8 GB was for R2's 10 GB.
  - Object keys, cache headers, the listing parser, and retention's rules are unchanged.
- **Alternatives rejected:** a free-form `SNAPSHOTS_ENDPOINT` (more general, but any host could be configured, and the shell allowlist would need a URL parser); keeping the `R2_*` names (misleading next to Oracle's values); snapshots in Neon or on the VM's disk (P-2 options 2 and 3: tighter retention, or snapshots lost with the VM).
- **Consequences:** the request quota is new: R2 had no request cap that mattered here, Oracle has 50,000 a month. Graph reads are already behind Vercel's CDN (`s-maxage=86400`); counting the requests the worker and web make, with an alarm, is M5.12d. Oracle's handling of a stored `Content-Encoding: gzip` and of `DELETE` on a missing key is assumed S3-like and checked by M5.13's smoke test (a `404 NoSuchKey` on delete is already treated as done).

## ADR-0096: Bucket requests are counted per UTC month in Postgres, through a counting `fetch`, and alarmed at 80% of 50,000
- **Context:** M5.12d1. Oracle Object Storage's Always Free tier allows 50,000 API requests a month (ADR-0095), and nothing in Oracle's API reports how many were used. Requests come from the worker (one PUT per analysis; retention's and the quota check's listings, a request per 1,000 keys each, every hour; deletes) and from the web app (`/api/graph` and the README images read snapshots), across many serverless instances that share no memory.
- **Decision:**
  - **Counter:** a `store_requests` table, one row per UTC calendar month (`date_trunc` on the database clock) and source (`worker` or `web`, checked by the database), incremented by one upsert per request (`countStoreRequests`), so concurrent instances never lose a count. Two rows a month; none are pruned. Oracle doesn't document its month boundary; UTC is assumed.
  - **Where:** `countingFetch` in `@gitinside/worker/storage` wraps the `fetch` the store already takes. Every attempt is counted, refused or failed (an overcount only raises the alarm early); the count runs alongside the request and is awaited with it, since a serverless instance may freeze once it answers. A failed count is logged (`store_request_count_failed`; the web app logs the error's name only) and never fails the request. The worker uses `createCountedStore` (main process and `quota-bin`), the web app wraps `graphDepsFromEnv`'s store.
  - **Check:** `measureQuotas` adds a third resource, `requests` (`storeRequestsThisMonth`, read after the bucket listing so the check's own requests are in it), against `QUOTA_LIMITS.monthlyRequests = 50,000`, with `bySource`. Usage lines are now `{ resource, unit, used, limit, percent, alarm }` for all three; `quota_alarm` at 80% (40,000) as for storage.
- **Budget:** the hourly maintenance costs ≈ 1,440 listing requests a month while the bucket holds under 1,000 objects, plus one PUT per analysis and the deletes retention makes. Graph reads are at most one per commit per day per CDN region. README images are the risk: each image URL is cached only 10 minutes and reads its snapshot on every miss, up to ≈ 4,300 requests a month per busy URL. M5.12d2 puts those reads behind the day-long graph cache.
- **Alternatives rejected:** counting in process memory and flushing (serverless instances are frozen or dropped without warning, so counts would be lost); counting at the `ObjectStore` method level (a listing is several requests); one row per request (the table would grow by tens of thousands of rows a month); reading usage from Oracle's metrics API (another credential and API on the web app, for a number that lags).
- **Consequences:** every bucket request now costs a small Postgres write as well. It adds no new database wake-ups (Neon's free plan limits compute time): each bucket request already follows a query on the same connection. The count is an upper bound of what Oracle sees, never lower, except for requests made with the keys outside GitInside (the console, `aws` CLI), which aren't counted.

## ADR-0097: README images read the graph through the day-cached `/api/graph` URL; graph paths redirect to the stored spelling before any bucket read
- **Context:** M5.12d2. ADR-0096's budget found the README images (ADR-0072) the biggest consumer of Oracle's 50,000 requests a month: each image URL is cached 10 minutes, and each miss read its snapshot from the bucket, up to ≈ 4,300 reads a month per busy URL, per theme and per badge. `/api/graph` serves the same bytes and is cached a day by the CDN. Also, `/api/graph/ACME/shop/…` and `/api/graph/acme/Shop/…` were separate cache entries, each reading the bucket.
- **Decision:**
  - **Images fetch `/api/graph`:** `handleImageRequest` asks the `graphUrl` that `viewRepo` returns (the stored spelling, so all case variants and both themes of an image share one entry) on the image request's own origin (`cdnGraphReader`, 10 s timeout), and no longer has a bucket. A non-200 answer is logged as `image_graph_unavailable` with its status, and the image is the link-only badge for a minute, as before. `imageDepsFromEnv(origin)` needs only the database; without the bucket `/api/graph` answers 503.
  - **The origin is the request's:** on Vercel a request reaches the function only through one of the project's hosts, so the self-request can't be steered to another site; the reader also refuses a path that leaves the origin. A configured `SITE_URL` was rejected in ADR-0073 already (wrong on previews).
  - **One URL per graph:** `/api/graph` compares the path with the stored owner and name after its database lookup and answers a `308` to the stored spelling before reading the bucket, cached an hour (`SPELLING_REDIRECT_CACHE_CONTROL`), not a day: if a repo is renamed in case only, a cached redirect can point back at the path that now redirects to it, and an hour bounds that loop.
- **Budget:** bucket reads for the website and the images together are now at most one per commit (and analyzer version) per day per CDN region that asks, however many READMEs show it. A case variant costs a database lookup and a redirect, never a bucket read.
- **To confirm in M5.13:** that Vercel serves the function's own request from its CDN (the second image miss within a day shows `x-vercel-cache: HIT` on the graph URL, and `store_requests` doesn't grow). Preview deployments behind Vercel Authentication answer the self-request with 401, so their images are the link-only badge; README images point at production.
- **Alternatives rejected:** longer image caching (the image would trail the default branch by more than SPEC F1's check-on-view allows); caching graphs in function memory (serverless instances don't share it); calling `handleGraphRequest` in-process (skips the CDN, so the bucket is read as before); Next.js's data cache (`fetch` with `revalidate`: a second cache with its own quota on Hobby, invalidated separately from the CDN's); a public bucket behind the CDN (ADR-0055).
- **Consequences:** an image miss now costs two function invocations instead of one, both inside Vercel Hobby's limits. A new commit's image appears as before (its graph URL is new, so it misses once). A re-analysis by a newer analyzer version reaches the images up to a day later, as it already did for the diagram page.

## ADR-0098: Imports, symbols, and calls are per-service facts, one record per site, merged into edges globally
- **Context:** M6.7d3a. ADR-0090 caches each service's facts; d3 turns the remaining program stages into fact bundles. The import and call stages looped over all programs into one edge map, merging repeated sites into one edge and upgrading its confidence to `exact`, so a service's result was an edge map shared with every other service's. M6.7d3 was split: a imports, symbols, calls; b Next.js and Prisma client uses; c SDK and queues; d resolver warnings per service, a `ServiceFacts` bundle, and `analyze` as facts → compose.
- **Decision:**
  - **Facts are one record per site,** not edges: `ImportFact` and `CallFact` (`from`, `to`, confidence, site) in file and source order, plus the import stage's `unresolved` nodes and `IMPORT_OUTSIDE_SERVICE` warnings. `collectImportFacts(sp, …)` and `collectCallFacts(sp, resolver)` ask only their service's program (calls reach others through the resolver, recorded in `reached`, ADR-0091).
  - **Merging is global:** `composeImports` and `composeCallEdges` merge records in program order exactly as the old loops did (first confidence, `exact` if any site is, `UNKNOWN_SYMBOL` on unresolved imports), then sort edges by ID and sites by position.
  - **Symbols are already plain data:** `collectSymbolNodes(sp)` returns the service's nodes; composition is concatenation in program order.
  - `buildImportGraph`, `buildSymbolNodes`, and `buildCallEdges` stay as collect-then-compose, for tests; `analyze` calls the two steps.
- **Alternatives rejected:** per-service edges merged again globally (two merge rules to keep equal, and an edge's confidence would depend on merge order twice); keeping the shared edge map and splitting it by `from` afterwards (a site's service would have to be recovered from its file).
- **Consequences:** no output change (goldens, eval), and composing JSON round-tripped facts equals `analyze`'s edges and nodes on fixtures. Facts are larger than edges (one record per site, `from` and `to` repeated); M6.7e's gzip absorbs most of it.

## ADR-0099: Next.js routes and Prisma client calls are per-service facts; the Prisma schema stays a global input
- **Context:** M6.7d3b. Next.js looped over all programs into shared node and edge maps. Prisma's client scan matched each call to a model while walking, so a service's result depended on every schema in the repo: removing a field elsewhere changed which `missingFields` its calls had, and adding a schema changed which model (or `AMBIGUOUS`) a call got.
- **Decision:**
  - **Next.js:** `collectNextFacts(sp, resolver)` returns the service's route and page nodes, `handles`/`renders` edges, and warnings. Every ID carries the service key and duplicates are only possible within one service, so `composeNextRoutes` only concatenates and sorts.
  - **Prisma schema is global:** `buildPrismaSchemas(root, workspace, sourceFiles)` parses every `.prisma` file into model and datastore nodes, `stores` edges, warnings, models by accessor per service, and `usesPrisma`. Schema files are small text read directly, not a program, so recomputing them each run is cheap and caching them buys nothing.
  - **Client calls are facts without the schema:** `collectPrismaFacts(sp, resolver, usesPrisma)` records each call in walk order as a `PrismaCall`: `raw` (the `unresolved` node it makes) or `model` (accessor, the origin service's key when traced, confidence, every name the argument uses as a field via `fieldNames`, the would-be `unresolved` node's ID and text). `composePrisma` does the model lookup (origin, caller, single candidate, `AMBIGUOUS`/`UNKNOWN_SYMBOL`), splits names into fields and `missingFields` (`splitFields`), binds owners to Express's inline handlers, and merges edges in program then walk order, as before.
  - **`usesPrisma` gates the scan,** like Express's `repoHasRouters` (ADR-0093): facts record `scanned`, and unscanned facts compose to nothing.
- **Alternatives rejected:** schema models as per-service facts of the schema's own service (the lookup still needs every service's models, so it would be global anyway); resolving models during the walk with the schema as part of the cache key (every service's facts go stale when any schema changes); scanning every repo regardless of Prisma (wasted checker work and possible resolver warnings in repos without Prisma).
- **Consequences:** no output change (goldens, eval). A client service's facts don't change when a schema loses a field it uses (only the composed `missingFields` do), and a client package's facts don't change when another service starts calling it. Facts record calls that may compose to nothing (a heuristic receiver naming no known model), which is the cost of not knowing the schema while walking. `usesPrisma` is a global input for M6.7e's key.

## ADR-0104: Motion is short, small, and asymmetric; exits stay mounted through `usePresence`
- **Context:** At the design gate (planning #2) Abhinav asked for "natural motion everywhere", like a smooth modern web app, looking as little AI-coded as possible. The viewer already glided boxes on drill-down and eased hover colors, but the legend and palette popped in and vanished, the inspector swapped its content in one frame, and a window's band and a folder's tab snapped to their hover color ahead of the box (CSS variables don't transition, so pseudo-elements need their own transition).
- **Decision:**
  - **Entrances:** opacity plus a few pixels of movement toward the overlay's anchor (legend and status chips rise 4px, the palette settles 6px down, inspector content rises 2px), over `standard` on `--ease-standard`.
  - **Exits are faster than entrances:** a fade over `fast` on a new `--ease-exit` (accelerating), as native popovers do. A leaving overlay stays mounted that long through `usePresence(open)` (`motion.ts`), which returns `"open" | "closing" | null`; the overlay sets `data-state`, and a closing one is `inert` and `aria-hidden`. Reopening mid-exit returns to `"open"` on the same element. Under reduced motion (`prefersReducedMotion`, the same query tokens.css uses) it unmounts at once.
  - **Content swaps by key:** the explorer keys the inspector by the selected node, so the new content plays the swap and starts at the top; in trace mode only the step's header, summary, and code are keyed, so focus on "Next step" survives.
  - **State colors move together:** shape pseudo-elements, the table's fields rule, and the edge label's fill and ring transition with the node or line.
  - **Guarded by tests:** easings may not overshoot (y in [0, 1]); the chrome's keyframes may not scale, blur, or rotate, or move more than 6px; every timing uses the duration tokens, so reduced motion zeroes it.
- **Alternatives rejected:** a spring library (bounce is the clearest generated-UI tell, and a dependency for a few fades); scale-from-95% pops (the macOS-Spotlight feel he liked comes from the palette's surface, not a zoom); a crossfade that keeps the old inspector content mounted (two copies of focusable rows, and the swap is 240ms); `animationend` to unmount (never fires when the duration is 0 or the tab is hidden, so a timer from the same tokens is more reliable); staggered list entrances (busy, and slow on long result lists).
- **Consequences:** no visual baseline changes (screenshots finish animations, and the end states are unchanged). M4b.7 wires the palette through `usePresence` and its `state` prop. Later M4b tasks (drill-down, trace player, filters) use the same tokens and rules.

## ADR-0105: The viewer's graph model; a service's routes and pages are drawn at its first level until their file opens
- **Context:** M4b.1 replaces the prototype's one-level model with the explorer's: any number of open nodes at any depth. The design gate (planning #2, question 4) asked that an open service "lead with its routes and then have the folders". In the graph a route sits under its file, three or four folders down, so drawing the tree as is buries the entry points.
- **Decision:**
  - **Two layers:** `buildHierarchy(graph)` (`model/hierarchy.ts`) builds the lookups once per graph in one breadth-first pass: tree children in graph order, depth, owning service, kind counts inside every node (deepest first, so a frame's badges are a lookup), and each service's routes and pages sorted like a route table (path, pages before routes, method, ID). `buildView(index, expanded)` (`model/view.ts`) is a pure function from an expansion set to the visible nodes, the frame each is drawn in, and the lifted edges.
  - **Routes first:** an open service draws its routes and pages as an `entries` section ahead of its children. A route or page moves into its file when that file is open, so it's drawn once and edges never have two candidate ends. Inside a frame, folders come before loose files, and both before the rest (unresolved calls, symbols), each group in graph order.
  - **Effective expansion:** a node asked open counts only if it can open and every ancestor is open. Inner requests survive closing an outer node, so reopening restores its inside; `view.open` is the sorted effective set, the key M4b.2's layout cache uses.
  - **Edge aggregation:** one view edge per (kind, visible from, visible to), each end lifted to its innermost visible holder (an entry is visible itself, so a route at the service level shows who calls it and what it runs); the weakest confidence wins; edges inside one visible node are left off; imports are hidden by default (`hiddenKinds` lets M4b.8's filters change that). A test checks that every graph edge is drawn exactly once or lies inside one visible node, at five expansion states.
- **Alternatives rejected:** drawing a route both at the service and in its file (two nodes for one ID, and every edge to it needs a rule for which copy it reaches); a virtual "Routes" folder node in the hierarchy (invents a node the graph doesn't have, and breaks `parentId` lookups like `isWithin`); routes only at the service level, never in their file (UX.md keeps them in the file, where the code is).
- **Consequences:** `ExplorerPrototype` keeps its own `prototype/model.ts` until M4b.3 builds the drill-down on this model and removes it. Breadcrumbs use `viewTrail`, so an entry's trail is its service, then itself. Viewer-only; no graph or eval change.

## ADR-0106: ELK lays out the whole view in one run; node sizes are measured from their content
- **Context:** M4b.2a replaces the prototype's fixed columns with ELK (SPEC D5.2) for any expansion state of M4b.1's view. The design gate asked that every node fit its content, and the prototype sized nodes per tier (every card 232px), so long route paths were cut while short names wasted room.
- **Decision:**
  - **Sizes from content** (`layout/size.ts`): each node's width is its name or subtitle (method chip, mono code at 95%), badges, and a model's fields, estimated with `textWidth` plus the paddings, tile, and gaps of `nodes.css` and 16px of slack. Widths grow between a floor and a ceiling per tier (cards 184–360, frames 248–420, icon-first 136–208); past the ceiling the name is cut and the tooltip holds it, but count badges never wrap, so they can widen a frame further. Edge labels are measured the same way (pill ≤ 280px). Estimates rather than DOM measurement, because the layout runs in a worker and in tests.
  - **One ELK run** (`layout/elk.ts`): layered, left to right as a request travels, with open nodes as compound nodes and `INCLUDE_CHILDREN`, so a line from inside one service to inside another is routed once. ROOT coordinates, so boxes and routes come back absolute. Open nodes get their header as top padding and their closed size as a minimum.
  - **Stable ordering:** the input follows the view's drawing order (graph order, routes first) and ELK keeps it where edges leave a choice (`considerModelOrder: NODES_AND_EDGES`, fixed seed). A service's routes and pages are held to its first column with `layerConstraint: FIRST`.
  - **Labels:** ELK keeps room for each label (between columns) and places it beside its line; the pill is drawn on the line, so it moves to the nearest point of the route. ELK ignores a label without `text`, leaving it at 0, 0 with no room, so each label carries a placeholder.
  - **Two steps for the worker:** `layoutInput` (main thread, plain data) and `runLayout(elk, input)`, which takes the ELK instance, so the library's main bundle imports only ELK's types; the worker (M4b.2b) bundles ELK itself.
- **Alternatives rejected:** ELK partitions for "routes first" (ignored across levels of a compound graph with `INCLUDE_CHILDREN`; checked); laying out each frame on its own, bottom up (edges between frames would be routed by hand, as in the prototype); measuring in the DOM before layout (needs a render pass per state and can't run in the worker); ELK's own label position (beside the line, while the design puts the pill on it).
- **Consequences:** elkjs 0.12.1 (EPL-2.0 or GPL-3.0, used unmodified as a library) is a viewer dependency. The prototype keeps its own layout until M4b.3, sharing the count-row constants. M4b.2b adds the Web Worker, the layout cache keyed by `view.open` and the hidden kinds, and a story with screenshots; M4b.3 draws from the result. Viewer-only; no graph or eval change.

## ADR-0107: ELK's own worker script runs the layout; the host builds the worker; one cache per graph
- **Context:** M4b.2b moves ELK (ADR-0106) off the main thread, as SPEC D5.2 and ADR-0011 ask, with a fallback and a cache per expansion state. A library can't build a Web Worker for its host: each bundler (Vite for Storybook, Turbopack for apps/web) only builds one from a `new Worker(new URL("./x", import.meta.url))` it can see.
- **Decision:**
  - **The worker body is ELK's worker script** (`elkjs/lib/elk-worker.min.js`), shipped as the library entry `@gitinside/viewer/layout-worker` (`src/layout/worker.ts`). Loaded where there's no document, it answers ELK's own `register`/`layout` messages on `self`. The main thread talks to it through elkjs's small API (`elk-api.js`) and reads the result with `readLayout`, so no protocol of ours crosses the boundary. A handler of our own next to it would have been answered twice (ELK's script sets `self.onmessage` on load).
  - **The host passes a factory** (`createLayoutEngine({ worker })`); the story's is `new Worker(new URL("./worker.ts", import.meta.url), { type: "module" })`.
  - **Fallback:** without a factory, if it throws, or on the worker's `error`/`messageerror` event (didn't load, crashed), layouts run on the main thread with `elk.bundled.js`, loaded by dynamic import on first use (a separate chunk, so the main bundle stays ELK-free). The switch is permanent, logged once as a warning, and finishes what was pending. ELK's own errors still reject (fail visibly), and the worker stays in use. `dispose()` stops the worker and rejects what's running.
  - **Cache:** `createLayoutCache(index, engine)` keeps the last 32 states, least recently used out first, keyed by `layoutKey(view)` = the view's effective open set and its hidden edge kinds (`GraphView.hidden`, new, so a view describes itself). Concurrent asks share one run, a failed run isn't kept, and `peek` gives a finished layout synchronously so a known state draws with no pending frame. One cache per graph (keys hold no graph identity).
  - **Labels on the line:** each label has `elk.edgeLabels.inline` (a label option, ignored on the root), so ELK routes the line through the pill's room. Placed beside their lines and moved onto them, the `reads`/`writes` pills of two parallel edges 11px apart covered each other.
- **Alternatives rejected:** our own message protocol (needs ELK in the worker without its self-registration, and `readLayout` gains nothing off-thread); the library constructing the worker itself (no bundler can see the path); Comlink or similar (a dependency for two messages); a timeout as a failure signal (a big layout is slow, not broken); resolving label collisions after layout by sliding pills along their lines (two pills on 190px of parallel line can't both fit; ELK has to keep the room).
- **Consequences:** The story "Explorer/Layout" draws the shop-demo fixture at three expansion states with the real node and edge components, laid out in a real worker. The visual spec now waits for `data-layout="pending"` to clear, fails a story that fell back to the main thread, and fails on a laid-out label wider than its measured room or covering another (a real-browser fit check that runs on Linux CI). apps/web gets a host worker file when it draws from the engine (M4b.3/M5). Viewer-only; no graph or eval change.

## ADR-0108: Drill-down as an ordered expansion list, a pure transition plan, and Web Animations glides
- **Context:** M4b.3 turns the view model (ADR-0105) and the ELK layout (ADR-0106/0107) into the drill-down UX.md describes: a node expands **in place** (its frame grows, siblings glide aside, children emerge from its center, 600ms), Esc or a breadcrumb collapses back, never an abrupt re-render, instant under reduced motion. M4b.3 was split: 3a builds the canvas and its motion, 3b moves the explorer (selection, trace, breadcrumbs, the website) onto it.
- **Decision:**
  - **State is the open nodes in the order they were opened** (`Expansion`, `explorer/drill.ts`). The view needs only the set; the order makes Esc close the level opened last (`upFrom` skips nodes remembered inside a closed one), and a breadcrumb (`collapseTo`) closes and forgets everything inside its frame. `useDrill` keeps the view object stable while the effective open set is unchanged, so the canvas and the layout cache see one state.
  - **Motion is planned apart from playing it.** `planTransition(prev, next, current)` (`explorer/transition.ts`, pure) gives each box of the next state its start rect: its old rect if it was drawn (a route moving from its service's first column into its file glides there), else centered on the nearest ancestor drawn before (the node just opened), starting transparent; boxes that disappear fold into the center of the box that now holds them and fade out. Boxes that don't move are left out.
  - **`DrillCanvas` plays it with the Web Animations API:** each box is placed at its final rect and animated from its start (transform plus width and height, so text never stretches and a frame grows around its children), with the `layout` duration and `ease-layout` tokens. Folding boxes stay mounted, inert and hidden from screen readers, for one glide. Lines and pills fade in over the second half, as the boxes land. A change mid-glide measures where boxes are drawn and starts from there. Under `prefers-reduced-motion` nothing is animated and nothing is left behind.
  - **No whole-canvas swap:** until the next layout is ready the current one stays (`aria-busy`); a cached state (`peek`) swaps in the same frame. A layout error shows as an alert.
  - **Focus:** opening or closing replaces the node's element (a card becomes a frame); if focus was on the canvas and got lost, it goes to the toggled node.
  - **An open file is a card, not a frame:** its own row stays at the top (`align-items: flex-start`), in the header room the layout kept. Found in the self-critique: centered, the row sat behind its routes. The visual spec now fails an open box whose row isn't at its top, and the "Inside the api" story opens a file so CI checks it.
- **Alternatives rejected:** CSS transitions on `left`/`top` (can't start a new box from another box's center, and interrupting needs the same measurement anyway); a FLIP transform with `scale` (stretches text and badges mid-glide); morphing edge routes point by point (routes before and after have different bends; a fade after the boxes land reads calmer); a plain set with "close the deepest" for Esc (ambiguous with two services open); a motion library (a dependency for one keyframe pair per box).
- **Consequences:** `DrillCanvas`, `useDrill`, and `planTransition` are exported. Story "Explorer/Drill-down" (system level; four levels into the api) runs in a real worker; mid-glide frames are in `docs/milestones/M4b/drill-*`. M4b.3b replaces the prototype's one-level model and column layout with these. Viewer-only; no graph or eval change.

## ADR-0109: The explorer on the drill-down canvas; selection and trace drawn on whatever box holds them
- **Context:** M4b.3b. `ExplorerPrototype` (ADR-0052) drilled one level with its own model and a fixed column layout, and the website showed it. M4b.1–M4b.3a built the real model, ELK layout, and drill-down canvas. M4b.3b was split: 3b1 moves the explorer and the website onto them; 3b2 moves the README image off the prototype's model and layout and deletes `prototype/`.
- **Decision:**
  - **`Explorer` replaces `ExplorerPrototype`** (`explorer/Explorer.tsx`): `buildHierarchy`, `useDrill`, a layout engine (the host's worker factory, else the main thread) and cache per graph, and `DrillCanvas`. Any box with something inside breaks down, to any depth. The inspector panels moved to `explorer/panels.tsx`, the trace script to `explorer/trace.ts`, and `connectionsOf` to `model/connections.ts`, all on the hierarchy index.
  - **The host owns selection and looks; the canvas draws them.** `DrillCanvas` gained `onSelect` (click, Space, Enter on a box that can't open further, per UX.md's key table) and `boxLook` / `lineLook` callbacks. A selection or a trace node that isn't drawn is shown on the innermost drawn box holding it (`visibleAncestor`); an open frame holding part of the path stays plain instead of dimmed.
  - **A connection in the inspector drills to its node** (`revealIn`, UX.md "selecting flies there, drilling if needed"): closed ancestors open outermost first, stopping as soon as the node is a box (`isShown`), so a route needs only its service. The prototype opened only the top level and marked the holder.

  - **A hop inside a closed box** offers "Break down <box>" at any depth (the prototype only offered top-level boxes).
  - **Fit until M4b.4:** each drawn level is scaled to the canvas (`fitScale`, 40–100%), the scale moving with the layout token.
  - **The website** draws `Explorer` without its top bar, laying out on the main thread until M4b.3b2 gives it a worker file.
- **Alternatives rejected:** keeping `ExplorerPrototype` beside `Explorer` until 3b2 (two explorers to keep in step, and the website would stay on the old one); selection state inside `DrillCanvas` (the inspector, trace, and deep links need it in the host); revealing a connection by opening every ancestor (a route would also open its folder and file, moving it out of the service's first column for no reason).
- **Consequences:** `Explorer`, `connectionsOf`, `isShown`, `revealIn`, `fitScale`, and the trace helpers are exported; `ExplorerPrototype` is gone. Stories "Explorer/Explorer" (overview, broken down, drilled deep, tracing at two depths) run in a real worker; screenshots in `docs/milestones/M4b/explorer-*`. Still weak: fitted at 40–48%, a broken-down service's text is small until pan and zoom (M4b.4). Viewer and web only; no graph or eval change.

## ADR-0110: The README image keeps its own fixed layout on the hierarchy index; the layout worker survives the host's bundler
- **Context:** M4b.3b2. The README image (`image/diagram.ts`, ADR-0071) was the last user of the M4a.7 prototype's model (`indexGraph`, `liftEdges`, `frameCounts`) and layout (`nodeSize`, `routeEdges`). The website still laid out on the main thread. Building its worker with Next.js 16 (Turbopack) showed ELK dying at load inside the worker with "window is not defined", and the explorer then waiting forever instead of falling back.
- **Decision:**
  - **The image moves onto the hierarchy index and `buildView`** (nothing open = the top level, imports hidden, same lifting). Its fixed per-tier sizes and one-bend routing move to `image/layout.ts` (`imageNodeSize`, `routeEdges`, `route`, `pointAlong`), and `prototype/` is deleted. The image keeps fixed arithmetic rather than ELK: `renderDiagram` is synchronous and its bytes are cached by commit.
  - **Same bytes, pinned:** `image/bytes.test.ts` hashes `renderDiagram` for every fixture's golden graph and a synthetic graph that wraps, uses a lane, and has parallel lines, in all three themes. The hashes were taken from the code before the move, and the synthetic graph's checked against the pre-move build. A change to the image now has to update them on purpose.
  - **The website lays out in a worker:** `apps/web/app/[owner]/[repo]/layoutWorker.ts` imports `@gitinside/viewer/layout-worker`, and `RepoDiagram` passes `new Worker(new URL("./layoutWorker.ts", import.meta.url), { type: "module" })`. Turbopack builds it into its own worker chunk.
  - **`layout/workerSetup.ts` runs before ELK in the worker:** (1) Next.js folds `typeof window` to `"object"` in browser code, workers included, so ELK's `$wnd = window` throws; the setup names the worker's global `window` (checked with `in`, which isn't folded), which is the `self` ELK would have picked. (2) Turbopack's worker runtime turned that load error into a rejected promise inside the worker, which the page's `error` listener never hears; the setup rethrows unhandled rejections from a listener, so they reach the page as uncaught errors and the engine falls back (ADR-0107's rule: a broken worker costs speed, never correctness).
- **Checked in a real browser:** a scratch Next.js page (not committed) drawing `RepoDiagram` on shop-demo under the site's real CSP: the layout runs in the worker, a drill-down lays out there too, and nothing is logged. With the `window` line removed, the page logs the worker failure and lays out on the main thread instead of hanging.
- **Alternatives rejected:** copying the built worker into `public/` and starting it by URL (skips the bundler's transforms, but adds a copy step, an unhashed 2 MB file, and a second way to load it); drawing the README image with ELK (asynchronous, and the layout would differ from the bytes already cached); a timeout as the failure signal (still rejected, ADR-0107: a slow big layout isn't a failure).
- **Consequences:** `prototype/` and its tests are gone; `shopDemo.testkit.ts` moved to `src/`. The CSP needs no change: the worker and its chunks loaded under it in Chromium (`worker-src` falls back to `script-src`, and the worker is started by a trusted script). Still weak: no committed E2E draws the diagram page (it needs a database the E2E server doesn't have), so the worker's real-browser check is a scratch run; M4b.14's E2E should cover it. Viewer and web only; no graph or eval change.

## ADR-0111: The worker runs on Google Cloud Run instead of an Oracle VM; snapshots stay in Oracle Object Storage
- **Context:** ADR-0015 put the analysis worker (enqueue API, Redis + BullMQ, the sandboxed analyzer) on an Oracle Cloud Always Free ARM VM, and named "Cloud Run Jobs + pg-boss" as the fallback needing its own ADR. Three things changed when the VM was due (planning #3, 2026-10-29 to 10-30):
  - **No capacity.** Ashburn, the account's permanent home region, returned "Out of host capacity" for `VM.Standard.A1.Flex` in all three availability domains, by hand and from a script retrying every two minutes for hours. Free Tier accounts can't use another region.
  - **The free allowance halved.** Oracle's docs now give Always Free A1 as 1,500 OCPU hours and 9,000 GB hours a month, i.e. **2 OCPU / 12 GB** running all month, down from 4 / 24 in June 2026. The spec, the issue, and most guides still said 4 / 24.
  - **The usual fix bends the $0 rule.** Upgrading to Pay As You Go gets capacity, but Oracle then can bill the card, places a ~$100 authorization hold (Oracle Support Doc 2972946.1), and documents no way back to Free Tier. Abhinav declined it. Idle Always Free VMs can also be reclaimed after 7 quiet days, and a stopped VM can hit the same capacity wall when restarted.
- **What the worker needs** (bench, 2026-10-26): cal.com (5,041 files) peaks at ~2 GiB and takes 27–77 s on a laptop; each analysis is capped at 3 GB heap and 5 minutes; two run at once. So roughly 2 cores and 8+ GB, or the equivalent per job. Traffic is small: the site is a portfolio piece for recruiters, not announced.
- **Options:**

  | | Free, no charge possible | Available now | Big repos, 2 at once | Rework |
  |---|---|---|---|---|
  | Keep retrying Oracle A1 (2 / 12) | yes | no | yes | none |
  | Oracle E2.1.Micro (1 GB) | yes | yes | no | small (swap, size limit) |
  | Oracle Pay As You Go | no; ~$100 hold, one-way | likely | yes | none |
  | Azure for Students ($100/yr credit) | yes, but runs out after ~3 months/yr | yes | yes | small |
  | Abhinav's own PC + tunnel | yes | yes | yes, only while it's on | small |
  | **Google Cloud Run** | within the monthly allowance; caps bound the rest | yes | yes | significant |

- **Decision:** the worker moves to **Google Cloud Run**; everything else stays.
  - **Why Cloud Run:** containers start per job from Google's pool, so there's no capacity hunt, no idle reclaim, and nothing to patch. Each job can get its own 1 vCPU / 4 GiB (up to 8 vCPU / 32 GiB), so big repos fit and two run side by side. The free allowance is **monthly and permanent** (as published Oct 2026: 180k–240k vCPU-seconds and 360k–450k GiB-seconds), worth roughly 1,000 cal.com-sized or 10,000 small analyses a month. Expected use is a few percent of that, and cached commits never wake the worker.
  - **The queue leaves Redis.** Cloud Run scales to zero, so an always-on BullMQ worker doesn't fit. Jobs are tracked in Neon and dispatched by a managed or Postgres-backed queue (Cloud Tasks, or pg-boss as ADR-0015 named); the implementing ADR picks one. The behavior stays: at most 2 at once, `repo@sha` dedupe, 3 attempts, live progress, the HMAC-signed request from Vercel.
  - **Snapshots stay in Oracle Object Storage** (ADR-0095). A Free Tier account can't be charged at all, it holds 20 GB versus Cloud Storage's 5 GB, the code is done, and keeping storage off Google's meter means a Cloud Run incident can't make storage cost money. Moving it to Google wouldn't remove a cross-cloud hop: diagram views go Vercel → storage either way, and every service sits in northern Virginia (~1–5 ms apart).
  - **Cost guardrails are part of the decision, set up before the trial ends:** a Cloud Run **spend cap** (preview since July 2026; pauses the service at the cap) around $1; a budget alert that turns billing off (Google's documented kill switch) as a backstop that doesn't depend on a preview; `max-instances` 2, concurrency 1, a 5-minute timeout, min instances 0; image cleanup to stay inside Artifact Registry's free storage; no Cloud NAT, load balancer, Memorystore, or static IP; a free-tier region near Vercel's `iad1`. The existing rate limits and dedupe stay.
- **Consequences:**
  - **$0 becomes "$0 in practice, bounded worst case."** The 90-day trial can't bill. After it, the account must be activated to keep the free allowance, and usage above it is billable. With the caps, a bot hammering the form costs about the cap plus a few cents of reporting lag; without them the theoretical ceiling is ~$150–170 a month. This is the one place in the stack where the card could be charged, so the guardrails are checked in M5.13's smoke test and written into SECURITY.md T9.
  - **The sandbox changes shape.** The egress-firewall gateway (ADR-0075) needs a network the worker controls; on Cloud Run, the platform's sandbox and egress settings replace it. The analysis child still has no network (`netguard.ts`), so the main protection carries over, but SECURITY.md §3 and T1–T9 get a fresh review.
  - **Infra shrinks.** `infra/oracle` (provision script, Caddy, egress gateway, compose stack) is replaced by a container image and a Cloud Run service deployed from GitHub Actions with keyless Workload Identity Federation. The `worker.gitinside` DNS record isn't needed; Cloud Run serves HTTPS on its own address.
  - **Latency:** a cold start adds ~2–5 s to the first job after a quiet period. The analysis itself dominates.
  - **Oracle stays** for Object Storage (#5). A1 remains a possible future host if capacity and the free tier allow, but nothing waits on it.
  - **Superseded:** the worker-host and Redis lines of ADR-0015, and the VM-specific parts of ADR-0074/0075. Sizing numbers in SPEC §5 and the docs move from the 4 / 24 VM to per-job Cloud Run resources.

## ADR-0112: The explorer's camera follows the fit until the user moves it; drilling then keeps the opened node in place
- **Context:** M4b.4. The explorer scaled each level to fit (ADR-0109, 40–100%) and had no pan or zoom, so a broken-down service's text was small, and the zoom buttons and minimap were drawings only. UX.md asks for zoom controls (− / level / + / fit, keys − + 0), a minimap, and a read-only mobile explorer that pans and zooms.
- **Decision:**
  - **A camera is three numbers** (`explorer/camera.ts`): a diagram point `p` is drawn at `p × zoom + (x, y)`, one CSS transform on the canvas. The math is pure and unit-tested: `fitCamera`, `zoomAt` (the point under the pointer stays put), `stepZoom` (×1.25 around the center), `keepInView` (at least 48px of the diagram stays on each axis, so it can't be lost), `visibleRect` (the minimap's frame), `centerOn`, `ensureVisible`, `holdInPlace`. Zoom is 25–200%.
  - **Fitted until the user moves it.** With no hand-set camera, each level is fitted (centered where it fits; else from the inset, so a service's first column shows) and refits glide with the layout. Any pan or zoom makes the camera the user's; 0 or the fit button hands it back. Rejected: always refitting on drill (the view jumps away from what the user zoomed in on) and never fitting (a deep drill opens off-screen).
  - **Breaking a node down with a hand-set camera keeps that node's corner where it was:** the camera shifts by the node's move times the zoom, over the same 600ms and easing as the boxes' glide, so on screen the node holds still (a real browser holds it at the same pixel every frame) while its frame grows around its children.
  - **Input** (`explorer/gestures.ts`, native listeners because React's wheel listener is passive): the wheel or a trackpad pans, Ctrl/⌘ + wheel and a trackpad pinch zoom around the pointer, a drag (mouse, finger, pen) pans from anywhere, boxes included, two fingers pinch. A press that moves under 4px is still a click; once it's a pan, pointers are captured (the drag can leave the canvas) and the click that ends it is swallowed. The corner overlays keep their own pointer and wheel. − / + / = / 0 work while focus is in the explorer, but not in a text field.
  - **Camera motion by source:** `layout` (refit, drilling, flying to a connection), `standard` (buttons, keys), none (pointer, wheel, minimap, which move with the hand). The duration tokens make all of them instant under reduced motion.
  - **The minimap navigates:** pressing moves the view's center there and a drag follows, with the map's scale held for the drag so it doesn't slide under the pointer. Its frame is the visible part of the canvas.
  - **A connection picked in the inspector flies there** when its box is off the canvas once its level is drawn (UX.md "selecting flies there"); one already in view doesn't move the camera.
- **Alternatives rejected:** a pan/zoom library (d3-zoom, react-zoom-pan-pinch: a dependency for ~150 lines, and none knows about the drill-down's glides); CSS `zoom` or scrolling a scaled box (the previous approach; overflow that grid-centering can't scroll to, and no zoom around a point); arrow keys for panning (UX.md gives them to moving between nodes, M4b.11).
- **Consequences:** zoom buttons, keys, the minimap, and breadcrumbs all work on the explorer and the website. `camera.ts` and `DRAG_THRESHOLD` are exported. Tests: the camera math, and the explorer in jsdom with a stubbed canvas size and `PointerEvent` (jsdom 25 has none); a scratch Playwright run checked zoom around the pointer, no page scroll, drags captured off the canvas without selecting, refit glides, the held node, the minimap, and reduced motion. Still weak: labels don't yet thin out at low zoom (UX.md "zoom-dependent detail", M4b.4b), and the keys need focus in the explorer, like T and Esc. Viewer only; no graph or eval change.

## ADR-0113: Zoom-dependent detail in three levels set by legibility; text fades, boxes never move; service names scale up
- **Context:** M4b.4b. UX.md: "labels, counts, and edge labels appear progressively. At low zoom, show only service names and aggregated edges." Since M4b.4 the camera zooms 25–200% and fits at 40–100%, so at a fitted broken-down level (41% for the shop-demo api at 1280 × 800) every 12px subtitle, badge, and pill was drawn at about 5px: clutter nobody could read.
- **Decision:**
  - **Three levels from the zoom** (`explorer/detail.ts`, `detailAt`): `full` from 65% (12px secondary text is then about 8px on screen, the smallest that still reads), `names` from 40%, `outline` below. 40% is the fit's floor, so a fitted level is at most `names`; only zooming out by hand reaches `outline`.
  - **`names`:** box names stay; subtitles, count badges, model fields, and edge pills fade out, except the pills of the selection's lines, the current trace hop, and a broken edge (diff mode), which are what the reader is looking at. **`outline`:** only service names, and only the lines that leave a service (to another service, a datastore, a queue, an outside API); lines between two boxes of one service fade and can't be pointed at; no pills. A selected, traced, hovered, or keyboard-focused box keeps its name, and a selected, traced, or broken line stays. Icons and shapes always stay: they're the primary marker (DESIGN_SYSTEM §3).
  - **Fade, don't remove.** The canvas sets `data-detail` and marks lines inside one service `data-inner`; `drill.css` changes opacity over `standard` (instant under reduced motion). No box, line, or pill leaves the DOM and no size changes, so zooming never relayouts, the measured sizes (ADR-0106) stay valid, and the accessible names are unchanged.
  - **Service names scale up below full detail** (`serviceNameScale`): enough to draw the 14px name at 12 screen px, at most 3×, like region names on a map. A CSS transform from the label's left edge, with its width divided by the same factor, so it still ends in an ellipsis inside its box and no box grows. The scale snaps with the zoom rather than gliding: the width can't glide in step with it, and Linux CI's capture caught a gliding scale drawing the name wider than its box.
  - **`initialZoom`** on `Explorer` starts at a zoom centered on the first level, as if zoomed by hand (stories now; deep links can use it, M4b.9).
- **Alternatives rejected:** re-aggregating lines to service level at `outline` (new endpoints need a new ELK layout per zoom level, and a zoom would then move lines); removing hidden text from the DOM (a zoom would re-render every box, and a box's content would shift as rows leave); scaling every label (cards' names would overflow their measured boxes); hysteresis around the thresholds (opacity fades already soften a crossing; nothing jumps).
- **Consequences:** fitted broken-down levels now draw names only, so those Linux baselines changed; two new stories (Explorer / Zoomed out at 55%, Outline at 30%). Tests: the levels and scale (pure), the canvas's attributes, the CSS rules, the explorer's detail across zoom steps and its start zoom, and a scratch Playwright run measuring computed opacity and service-name heights and checking no node overflows. Also fixed a race in the fly-to test (the camera moves in an effect a render after `data-layout` says done; the test now waits for it). Still weak: names other than services are under 6px at the bottom of `names`; a long service name is cut at `outline`. Viewer only; no graph or eval change.

## ADR-0114: Cloud Tasks dispatches analyses to Cloud Run; job state and progress live in Neon
- **Context:** ADR-0111 moves the worker to Cloud Run, which scales to zero, so the always-on BullMQ worker and its Redis go. The replacement must keep the queue's behavior: at most 2 analyses at once, `repo@sha` dedupe, 3 attempts, live progress with a queue position, and an HMAC-signed request from Vercel (planning #9). ADR-0015 named pg-boss as the fallback; ADR-0111 left the choice to this ADR.
- **Options:**
  - **pg-boss on Neon.** Free, and the job table is plain SQL. But something has to poll it, and on Cloud Run nothing runs between requests: Vercel would have to wake an instance per job, and a job whose instance died would sit until the next wake. Polling also keeps Neon's compute awake (100 CU-hours a month on the free plan).
  - **Cloud Tasks.** Google's push queue: it holds each task and POSTs it to Cloud Run, with the queue's own limits (`maxConcurrentDispatches: 2`, `maxAttempts: 3`, backoff), and a task name can't be reused, so naming a task after `repo@sha` dedupes it. It signs each push with an OIDC token for a service account, so the Cloud Run service can refuse unauthenticated calls outright. Free for the first 1M operations a month (each create and each delivery attempt is one); this site needs a few thousand.
- **Decision:** **Cloud Tasks**, with Neon as the record.
  - Vercel writes the job row in Neon (`queued`, the existing `repo@sha` dedupe) and creates a task named from it, with the HMAC-signed job as its body. `ALREADY_EXISTS` means it was already queued.
  - Vercel calls the Cloud Tasks REST API without a Google SDK (like the SigV4 store), authenticated keylessly: Vercel's OIDC token is exchanged through Workload Identity Federation for a short-lived token of an enqueue-only service account. No key file exists anywhere.
  - The worker is a Cloud Run service (not a Job: Cloud Tasks pushes HTTP requests, and a Job execution can't receive one): one task is one request, concurrency 1, max instances 2. It checks the HMAC on top of Cloud Run's IAM check, runs the analysis inside the request, and answers 2xx for success and for permanent failures (so Cloud Tasks doesn't retry a `LIMIT_*`), 5xx only for retryable ones.
  - Progress and status go to the job's Neon row (a few writes per stage); the progress page's SSE reads Neon, and the queue position is the count of `queued` rows ahead. `GET /jobs/:id` on the worker goes away.
- **Consequences:**
  - The worker needs no public, unauthenticated endpoint at all, which is stronger than the VM's HMAC-only API.
  - Cloud Run's request timeout (5 min, ADR-0111) bounds the whole job, so download, extraction, analysis, and publish share one deadline; the child's kill time comes from what's left. `/tmp` on Cloud Run is memory, so the extracted tarball counts against the 4 GiB along with the child's heap.
  - Two of Google's meters join the quota check: Cloud Tasks operations and Cloud Run's free vCPU- and GiB-seconds (planning #11).
  - Local dev and tests use a fake Cloud Tasks server that pushes to the worker, as the fake S3 server does for storage; no Redis anywhere.
  - To verify when implementing (M5.17b): the HTTP-target dispatch deadline's range (believed 15 s–30 min) and how long a used task name stays reserved.
  - Supersedes the queue parts of ADR-0015 and D5.6, and the BullMQ worker of M5.4d.

## ADR-0115: The inspector's summary is templated per kind and per connection; code loads from GitHub in the viewer's browser
- **Context:** M4b.5a. The inspector (UX.md "Selection and inspector") had a summary only for systems, services, routes, and unresolved calls ("Model with 1 connection out and 2 in" for the rest), no "Open on GitHub" unless the file's text was at hand, and code only from text passed in (`sources`), which the website never had: a snapshot holds the graph, not the files. The design gate asked for the code sample to link to the file and line.
- **Decision:**
  - **Summary = a lead from the node's own fields + one sentence per connection kind** (`explorer/summary.tsx`). Leads: "Express service in `apps/api` with 2 routes and 1 model.", "Handles `POST /api/orders` requests.", "Exported function, called with at least 2 arguments.", "Datastore running postgres.", and so on for every kind. Then outgoing sentences ("Runs createOrder.", "Writes Order.", "Calls the outside API api.stripe.com.") and incoming ones ("Requested by placeOrder in @shop/web.", "Read by listOrders."), in request order (handles, renders, calls, http, reads, writes, stores, publishes, consumes, external_call, imports). At most 3 names per group, then "and N more". A name from another service carries it ("in @shop/web"), grouped, because two services often share names (the client's `listOrders` requests the API's). No connections: "Nothing else in the repo connects to it." Every word is from the graph; nothing is guessed.
  - **Open on GitHub is an action** whenever the node has a source and the graph a commit SHA, whether or not the code loads (`LinkButton`, a link styled as a button). **The code sample's path is itself the link** to that file and line at the commit (design gate); the caption's separate "Open on GitHub" text went, so the frame has one link.
  - **Code loads on selection** through a new `loadSource` prop (`explorer/sources.ts`): one load per path per explorer, kept once loaded (reselecting shows it at once), forgotten on failure (the next selection retries). States: none (no way to get the file: no code section), loading (the frame keeps its 15-line height, `aria-busy`), ready, failed ("Couldn't load this file.", the link stays).
  - **The website loads public files from `raw.githubusercontent.com` at the analyzed SHA, from the viewer's browser** (`createGitHubSourceLoader`): no cookies, no redirects (a renamed repo fails visibly rather than loading something else), only a 200, at most 2 MB (the analyzer's own skip limit, ADR-0020), no NUL bytes. The CSP's `connect-src` adds exactly that origin; nothing else may load from another origin (the CSP test pins it).
- **Alternatives rejected:** storing file text in snapshots (bytes per commit against the 20 GB bucket and 50k requests/month for something GitHub already serves for free); a proxy route on Vercel (function invocations and bandwidth for public files, and it would need its own size limits); GitHub's contents API (60 requests/hour per IP unauthenticated); summaries counting connections ("1 out and 2 in" says nothing a reader can use).
- **Consequences:** private repos (M8) need a signed-in source route, since raw URLs need a token; the loader is the seam for it. The viewer's visitors make the requests, so GitHub sees their IPs, not ours (said on the privacy page, M9.4). Text is rendered through React (escaped); M4b.5b adds Shiki as tokens, still without HTML (SECURITY.md T10).

## ADR-0116: Shiki in the code preview: lazy chunks, the JavaScript regex engine, one CSS-variable theme, tokens as React spans
- **Context:** M4b.5b. The inspector's code preview (ADR-0115) was plain text. UX.md asks for Shiki. The website's CSP allows no WebAssembly or eval, SECURITY.md T10 forbids rendering repo content as HTML, and the explorer's bundle shouldn't grow for a panel most visits open late.
- **Decision:**
  - **Fine-grained and lazy** (`chrome/syntax.ts`): `shiki/core`, `shiki/engine/javascript`, and one grammar per language (TS, TSX, JS, JSX, JSON, Prisma, YAML), each a dynamic `import()` the bundler splits off (core ≈ 37–44 kB gzipped, engine ≈ 21–28 kB, a grammar ≈ 16 kB), fetched on the first preview that needs it. Other files stay plain.
  - **The JavaScript regex engine** (`forgiving`: a pattern it can't translate matches nothing instead of failing the grammar), so no `.wasm` and no `wasm-unsafe-eval` in the CSP. The built chunks contain no `eval`, `new Function`, or WebAssembly (checked).
  - **Our own theme whose colors are CSS variables** (`var(--syntax-keyword)` and four more, plus `--text-muted` for comments): one tokenization serves dark and light, and a theme switch needs no re-tokenizing. Five new theme tokens, each the layer hue at ≥ 4.5:1 on the canvas and on the selected line's tint (tested). Color only; no italic or bold, so highlighting never changes a line's width.
  - **Tokens as data, not HTML:** `codeToTokensBase`, merged into runs per kind; each run is a React `<span data-token="…">` with escaped text. A row whose tokens don't spell the line exactly falls back to the plain line.
  - **Plain text first, colored in place:** the frame shows plain lines until Shiki is ready (`data-syntax="pending"`), then the same characters colored (`done`); a failed load or tokenizer shows plain (`plain`). After the first load, highlighting is synchronous in render, cached by content (32 entries), so reselecting doesn't flash.
  - **Warm-up on load:** the engine compiles patterns on first use, and Shiki gives each line 500 ms before coloring the rest of it like its start (CI's first `import … "express";` came back as one keyword). Loading a grammar tokenizes our own sample without the limit, so that cost never lands on a preview.
  - **Context:** the tokenizer reads up to 200 lines above the preview, so a preview starting inside a block comment or template string is colored right; lines over 1,000 characters (minified) aren't tokenized.
- **Alternatives rejected:** the Oniguruma WASM engine (needs `wasm-unsafe-eval` in the CSP); `shiki`'s bundled highlighter (every language and theme in the graph of chunks); `codeToHtml` + `dangerouslySetInnerHTML` (T10); two concrete themes (tokenizing twice, or re-tokenizing on a theme switch); tokenizing the whole file (a 2 MB file would block the main thread); a Web Worker for tokenizing (15 lines plus 200 of context take milliseconds once loaded; not worth the plumbing now).
- **Consequences:** a comment or string opened more than 200 lines above the preview is colored as code. Visual tests wait until no preview is `pending` or `plain`. Other languages (Python, Go) are a grammar import each when the analyzer supports them.

## ADR-0117: The request path is computed: breadth-first reach within 12 hops, steps depth-first in call order
- **Context:** M4b.6a. Since M4a.7 the trace was a hand-written script for shop-demo (ADR-0052), so the website had no trace at all. UX.md asks for a BFS from a page or route over `http → handles → calls → reads/writes → stores` and `external_call`/`publishes`, up to depth 12, "ordered by call order within each function when known".
- **Decision** (`explorer/trace.ts`, `traceFrom`):
  - **Which hops:** `renders`, `calls`, `http`, `handles`, `reads`, `writes`, `stores`, `external_call`, `publishes`, and `consumes` backwards (the analyzer draws it from the worker to the queue, ADR-0037, so the path goes queue → worker). Not `imports`: a file importing another isn't a request going there. Edges to `unresolved` nodes are steps like any other, so the path ends visibly where the analyzer lost the URL, and the step quotes the node's `detail`.
  - **How far:** breadth-first distances from the start; nodes 12 hops out are reached but not followed. Nodes cut off that way are listed under the steps ("The path goes on past 12 hops, from f11"), never silently dropped.
  - **In what order:** depth-first, each node's hops sorted by their first call site (file, line, column; edges without sites last, then by ID), each followed to its end before the next. So the steps read in the order the request runs ("createOrder writes Order", "Order stored in db", "createOrder calls chargeOrder"), where a breadth-first order would interleave branches. Each node is followed once and each edge is one step, so cycles end where they close. Iterative, so a 5,000-deep walk doesn't overflow the stack (tested).
  - **Where it starts:** **Trace from here** on any page or route that has a hop; T and the top-bar button trace the selected page or route, else the explorer's `traceStart` prop (the stories' checkout page), else they say "Select a page or route to trace its request path". The searchable picker is M4b.6b. The status chip names a route with its method ("Tracing GET /api/orders"), since GET and POST share a path.
- **Alternatives rejected:** steps in breadth-first order (branches interleave, so the player jumps between services); a plain depth-first search with a depth counter (a node reached deep first would be cut off though a shorter way in exists); following `imports` (every page would trace into its utility files); a cap on the number of steps (the depth cap bounds it, and a cut would hide hops without saying where).
- **Consequences:** on shop-demo the computed path equals the old script hop for hop, so the trace stories' baselines don't move; the overview's hint now names its start ("press T to trace the request from `/checkout`") or says to select a page or route. `CHECKOUT_TRACE`, `checkTrace`, and `TraceScript` are gone from the viewer's API (`traceFrom`, `canTraceFrom`, `TRACE_DEPTH`, `Trace` instead). A big repo's route can have a long steps list; the list scrolls.

## ADR-0118: Trace picker on the palette's shell, a player that plays at three pulses a step, and a pulse that runs the request's way
- **Context:** M4b.6b. UX.md "Trace mode": "A picker lists pages and routes, searchable", "A pulse travels each hop (900ms)", and the player's "previous / play-pause / next". After M4b.6a, T with nothing traceable selected and no `traceStart` (the website's case) only said "Select a page or route".
- **Decision:**
  - **Picker** (`explorer/picker.tsx`): T and the Trace button open it exactly where the message used to be (a traceable selection or `traceStart` still trace at once, so the demo's T is unchanged). It lists every page and route with a hop (`canTraceFrom`), pages first, then by label; a query keeps the entries whose name or file contains every word, in any case, marking each word's first match in the name. It reuses `CommandPalette`'s dialog (new props: label, placeholder, empty text, the footer's verb, and focus on every open, also when reopened mid-exit). Tab stays in the field. Closing returns focus to the control it opened from (the Trace button, a box); opened with nothing focused, it leaves the field so the trace's first step takes focus.
  - **Player:** Play advances a step every 2,700ms (three trace hops, `PLAY_STEP_MS`) and stops on the last step, where the button reads Replay and starts over. Previous, Next, or a step in the list pause it, since the reader has taken over. One button changes its label in place (fixed width, so Next step holds still and focus stays on it). Auto-advance keeps running under reduced motion: it changes content, not position.
  - **Pulse** (`DiagramEdge`'s `pulse` prop, `.gi-edge__pulse`): a 14%-long, 3px-wider dash on the current hop's line, mixed from `--trace` toward `--text` so it reads on its own trace-colored line in both themes, eased like a glide over 900ms and faded at both ends, repeating. `pathLength="100"` makes the dash and its travel proportional on any line. `"backward"` reverses it on a line drawn against the request (a queue's consumer, ADR-0117). It's transparent at rest, so baselines (animations off) don't show it, and hidden under reduced motion, where the hop's width and halo still mark it. Unresolved hops pulse too, unlike flow particles: the pulse marks where the request is.
- **Alternatives rejected:** opening the picker even when `traceStart` exists (adds a keystroke to the demo's lead moment); fuzzy matching (M4b.7's palette brings it; whole-word containment is predictable for paths); a separate picker component with its own styles (two dialogs that would drift); a dwell of one pulse (900ms is too short to read a step's title and code); a bigger particle as the pulse (particles already flow on every path edge, so a third kind of dot wouldn't read as "here").
- **Consequences:** the website's diagram page gets a working trace from T with no selection. `CommandPalette` focuses its field when `autoFocus` is set and keeps Tab in it, which M4b.7 builds on. One new story (Explorer/Trace picker) and two new interface icons (play, pause) change the Controls baseline.

## ADR-0119: The command palette ranks matches by tiers, searches every node, and a pick zooms in to read it
- **Context:** M4b.7. UX.md "Search: command palette": Ctrl+K or ⌘K, a fuzzy match over services, modules, files, symbols, routes, pages, models, and externals, results with kind and path, Enter "flies to the result, drilling as needed, and selects it". The M4a review asked for focus moved into and kept in the dialog.
- **Decision:**
  - **Matching** (`explorer/search.tsx`, `searchNodes`): every word of the query must match the name or, failing that, the path (a service's root, a folder's or file's path, an outside API's host, else the source file). In the name a word scores by tier: the whole name (100), its start (80), a word start (after a non-letter-or-digit or a camelCase step: 60), anywhere (40), or its letters in order with gaps (20 minus the letters skipped, at least 1; two letters or more). A path-only word scores 10. Ties go by kind (services, pages, routes, models, folders, files, symbols, then infrastructure and unresolved items), then the shorter name, then `compareStrings` on name and ID, so the list is the same in any input order. At most 50 results; an empty query lists nothing and says what to type. Every node but the system is searchable, including datastores, queues, and unresolved calls (fail visibly: they're findable too).
  - **Keys and focus:** Ctrl+K or ⌘K (no Shift or Alt) toggles it from anywhere in the explorer, and from the page itself when nothing has focus (a window listener that ignores keys aimed at other fields); the top bar's search field opens it too. Tab stays in the field, and a press anywhere in the dialog but the field doesn't take focus (`mousedown` default prevented), so arrows, Enter, and Esc keep working. Esc and a scrim click close it with focus back where it was. A pick closes it, drills (`drill.reveal`), selects, focuses the picked box, and flies there with `zoomToBox`: centered at 100% (less if the box wouldn't fit), never zooming out, and only panning when already that close. The inspector's connections keep `ensureVisible`, since the reader is already looking at that level.
  - **Esc from a dialog's field** is handled once: the explorer ignores a key whose default the dialog prevented. Before this, the trace picker's Esc ran its close twice and the second blurred the control focus had just returned to.
- **Alternatives rejected:** a fuzzy library (fzf-style scoring is a dependency and harder to keep deterministic and explainable); a typo-tolerant edit distance (noisy on short code names); listing everything on an empty query (thousands of rows on a real repo); keeping the fitted camera on a pick (at 40% a function's name isn't drawn, so "flies to" landed on an unreadable box); ending a trace on a pick (drilling keeps the trace, UX.md; the pick is marked on the canvas).
- **Consequences:** the website gets search as soon as it shows the explorer (Ctrl+K works without the explorer's top bar). Not handled: typos, and a word matched across the name and the path. One new story (Explorer/Search).

## ADR-0120: Filters hide nodes with what's inside them, drop (not re-route) their connections, and find tests and config by name
- **Context:** M4b.8a. SPEC §3 asks for filters "by layer, kind, and confidence, plus a toggle to hide tests and config"; UX.md adds a folder include/exclude, with tests and config hidden by default. The graph has no "test" or "config" flag (the analyzer parses every source file, test files included), and a hidden node's connections need a rule: the view model otherwise lifts an edge to the nearest visible ancestor.
- **Decision:** `model/filters.ts`, applied by `buildView`'s new `filters` option.
  - **Rules:** a node is hidden when its own layer or kind is off, when its repo path (a service's root, a folder's or file's path, an unresolved call's source file) is a test or config path, in an excluded folder, or, with folders included, neither in one nor (for a service or folder) above one. Everything inside a hidden node is hidden; so is a folder whose contents all are. Files stay even when emptied (hiding symbols keeps the file boxes). Datastores, queues, and outside APIs have no path, so folders don't touch them. The kind filter offers routes, pages, symbols, models, datastores, queues, outside APIs, and unresolved calls; services, folders, and files are structure and go by layer or folder. Edge kinds stay with `hiddenKinds` (imports off by default).
  - **Connections:** an edge with a hidden end, or of a hidden confidence, is dropped before lifting. Redrawing it from the hidden node's visible parent would say the parent does it, which the filter's reader asked not to see.
  - **Tests and config by name** (`isTestOrConfig`): `*.test.*`, `*.spec.*`, `*.e2e.*`, `*.config.{js,ts,…}`, `.*rc.js`, Jest/Vitest/Playwright setup files, `setupTests.*`, and folders named `__tests__`, `__mocks__`, `__fixtures__`, `test`, `tests`, `e2e`, `cypress` (so a test workspace goes too). Not stories, `fixtures/`, `.d.ts`, or framework files like `middleware.ts`.
  - **Cache key:** `filtersKey` is the canonical JSON of the sorted, deduplicated filters ("" when none apply), stored on the view as `filtered` and added to `layoutKey`, so equal filters set in any order share a layout. `buildView` without `filters` is unchanged (`NO_FILTERS`), so the README image, which shows everything, keeps its bytes; the explorer will start from `DEFAULT_FILTERS` (tests and config hidden).
- **Alternatives rejected:** an analyzer flag for test files (a schema change and eval re-record for what is a naming convention the viewer can read from paths); lifting a hidden node's edges to its parent (misattributes them); dimming instead of hiding (the canvas's dim state already means "off the trace"); glob patterns for folders (a prefix by whole segments is what "include this folder" means, and needs no glob engine).
- **Consequences:** the explorer can show "N filters" and a chip from `activeFilterCount`. The popover, chip, and explorer wiring (selection, trace, and search over hidden nodes) are M4b.8b. Not handled: test files named by other conventions (`*_test.ts`, `testUtils.ts`); they stay visible.

## ADR-0121: The filters popover offers only what the graph has; the chip shows only when something is hidden; going to a hidden node takes off just the filters hiding it
- **Context:** M4b.8b. UX.md "Filters": a popover from the top bar with toggles by layer, kind, and confidence, a folder include/exclude, and "Hide tests and config" on by default; active filters as a chip with "Clear". The explorer starts from `DEFAULT_FILTERS` (ADR-0120), the website hides the explorer's top bar, and search, the trace picker, the inspector's connections, and a trace's steps can all lead to a node the filters hide.
- **Decision:**
  - **Popover** (`chrome/FiltersPopover.tsx`, non-modal): the tests switch first (it takes focus on open), then pill choices for layers, node kinds, connection kinds (imports included, off by default), and confidence, each pressed while what it names is shown and counted from the graph (`filterOptions`); a choice the graph has none of isn't offered. Off pills are muted with a dashed edge, so "hidden" doesn't rest on color. The folder field suggests the graph's service roots and folders and refuses any other path with a message ("No folder x in this repo") instead of a filter that hides nothing; Enter hides, "Show only" includes; folders in use are listed, each removable. Esc or the close button closes it with focus back on its opener; a press outside closes it and leaves focus where the press put it. From the top bar it opens under the zoom controls; from the canvas under the chip.
  - **Count and chip:** the Filters button counts the settings that are on (`activeFilterCount`, plus connection kinds hidden beyond the default), so the shop demo reads "Filters 1" (tests hidden). The canvas chip ("2 filters · 7 hidden", or "· N connections hidden" when only lines go) shows only when the filters actually hide something in this graph, so a repo without tests isn't told about them on its hero canvas. Its text opens the popover; its × is Clear. Clear sets `NO_FILTERS` and keeps the connection kinds hidden by default as they are: imports are a level of detail, not a filter, and a user who turned them on keeps them. Without the top bar (the website), a quiet Filters button takes the chip's place when nothing is hidden.
  - **Going to a hidden node:** a search pick, a trace-picker pick, a connection in the inspector, "Trace from here", and a step's **Show** call `filtersShowing`, which removes only the rules that hit the node or what holds it (their layers and kinds, the tests switch if one of their paths is a test or config one, the excluded folders holding them; with folders included, the node's nearest path is added), so the other filters stay. A folder still hidden because everything inside it is gets the first single whole rule whose removal shows it, else the rules go in a fixed order. The change is announced and the chip updates. The palette and the picker label hidden results "Hidden by filters".
  - **Hidden, not drawn elsewhere:** a hidden selection or trace hop has no box; it isn't marked on its parent (that would say the parent is it, the same reason ADR-0120 drops its edges). The inspector says "Hidden by filters" with **Show on canvas**; a trace step with a hidden end says "Checkout is hidden by filters." with **Show Checkout**. The steps list is computed on the whole graph, so it never skips a hop.
- **Alternatives rejected:** offering every kind and layer whatever the graph has (a long popover of choices that do nothing); a chip whenever a setting is on (every demo and test-free repo would carry "1 filter · nothing hidden"); clearing all filters when going to a hidden node (loses the reader's other choices); refusing to go to a hidden node (search would find what it can't show); computing the trace on the filtered graph (a hidden middle hop would silently end the path); a modal dialog (filters are adjusted while watching the canvas change).
- **Consequences:** every explorer story's top bar now shows "Filters 1", so their baselines change by that count. New story Explorer/Filters. Not handled: the filters aren't in the URL yet (M4b.9 deep links); the folder field matches whole service roots and folders only, not files.

## ADR-0122: Deep links are a readable query of what differs from the default, checked against the graph, and reported by the explorer as it changes
- **Context:** M4b.9a. SPEC §3 and UX.md "Deep links": the URL encodes repo, commit, the drill-down path, the selection, the trace's start and step, and the filters (the diff base comes with M6). The website's path already carries the repo and commit (`/<owner>/<repo>/<sha>`). A link may be old (a node renamed at a later commit), hand-edited, or hostile, and the explorer is uncontrolled: it takes `initial*` props.
- **Decision:**
  - **Codec** (`explorer/deepLink.ts`): `encodeState` writes only what differs from `DEFAULT_STATE`, in a fixed parameter order: `open` (the open nodes, in opening order so Esc still closes the last), `sel`, `trace`, `step` (1-based like the player, left out on the first step), then `hideLayers`, `hideKinds`, `hideConfidence`, `hideLines` (the hidden connection kinds, written only when not just imports; empty means all shown), `only`, `hideFolders`, and `tests=shown`. Filters are canonical (`normalizeFilters`), so equal states give equal strings. Lists are comma-separated; values are percent-encoded with `/`, `:`, and `@` kept, so node IDs read as themselves (`sel=route:api/POST%20/api/orders`) and a comma inside an ID can't split a list.
  - **Nothing in a link is trusted:** `decodeState(query, index)` keeps a node only if the graph has it and it can do what's asked (break down, be selected, start a trace), a step only within that trace's steps, filter values only from the known lists, and folders only the repo has (the popover's rule). Everything else is left out and returned in `ignored`, so the page can say the link doesn't fully match this commit (fail visibly) instead of guessing. Unknown parameters (`utm_source`) are skipped silently; a malformed escape is noted. `+` reads as a space, as browsers send forms.
  - **Explorer:** `initialTrace` starts a trace from any traceable page or route (before, only `traceStart` could be opened tracing) and `initialHiddenKinds` sets the connection kinds. `onStateChange` gets the state after each change a link keeps, compared by its encoding, so a re-render, a camera move, or filters set to equal values report nothing, and the state it opened with isn't reported. Only effectively open nodes go in (a node remembered inside a closed one isn't drawn, so it isn't linked), and a trace that ended isn't linked though its start is kept for focus.
- **Alternatives rejected:** `URLSearchParams` alone (encodes `/` and `:`, so links become `%2F` soup); repeated parameters (`open=a&open=b`; longer, and UX.md's example uses commas); JSON or base64 state (unreadable and not hand-editable); writing every field (long links for the common case); the camera in the link (screen-size dependent; the drill-down path is what SPEC asks for); a controlled explorer (every host would have to own a dozen pieces of state to get one URL).
- **Consequences:** the website can read `location.search` into the `initial*` props and write `onStateChange` back with `history.replaceState` (M4b.9b, with Copy link in the share menu). Not handled yet: the diff base (M6); back/forward between states (each change replaces the URL rather than adding history entries).

## ADR-0123: The website keeps its URL in step with `replaceState`, says what a link left out, and shares the commit's permalink from a share menu
- **Context:** M4b.9b, on top of ADR-0122's codec. The repo page (`/<owner>/<repo>` for the latest commit, `/<owner>/<repo>/<sha>` pinned) hides the explorer's top bar, so its share menu isn't there; "Add to README" already sits on the repo bar (ADR-0073). Node IDs can change between commits, and `/<owner>/<repo>` moves to newer commits as they're analyzed.
- **Decision:**
  - **In:** once the graph has loaded, `RepoDiagram` decodes `location.search` against it (once per load) and passes the state to the explorer's `initial*` props. What `decodeState` left out is named in a quiet note above the canvas ("Part of this link doesn't apply to commit a1b2c3d, so it was left out: selected route:api/GET /gone."), up to three parts and a count, with Dismiss. The rest of the link applies as usual.
  - **Out:** each `onStateChange` replaces the query with `history.replaceState`, keeping the path and hash. No new history entries: Back leaves the page, as it did before, instead of stepping through every click. Left-out parts drop out of the URL at the first change, since they never applied.
  - **Share menu** (`ShareMenu` in the viewer): a Share button opening a small disclosure panel (not a dialog) with the link in a read-only field and **Copy link**; Esc, the button, or a press outside closes it, and Esc doesn't reach the explorer (it would go up a level). A refused copy selects the field for the reader. The explorer's top bar draws it (`TopBar`'s `share` slot, `linkTo` for the URL, by default this page with the query); the website puts one on the repo bar next to "Add to README", its panel hanging from the bar's right edge like that one's.
  - **The shared link is the commit's permalink** (`/<owner>/<repo>/<sha>?…`), even from `/<owner>/<repo>`: the IDs in it are this commit's, and the page at the repo's path can move to a commit that lacks them.
- **Alternatives rejected:** `pushState` per change (Back would undo one click at a time and the history list would fill with drill-downs); Next's `router.replace` (a server round trip per click for a client-only state); rewriting the URL at once to drop what didn't apply (the reader would lose the evidence of what they were sent before reading the note); sharing the page's own URL (a `/<owner>/<repo>` link would stop matching after the next analysis).
- **Consequences:** a reload or a pasted link reopens the same view at the same commit. Export (M4b.10) joins the share menu. Not done: the diff base in the link (M6); undo with Back.

## ADR-0124: Exports are pure text renderers of the view on screen: SVG from its ELK layout with the README image's markup, Mermaid with the diff's escaping
- **Context:** M4b.10a (UX.md "Export": SVG and PNG of the current view, both themes; Mermaid of the current level). The canvas is HTML boxes over an SVG of lines, styled by CSS with `color-mix`, so serializing the DOM wouldn't give a standalone file: the CSS, fonts, and React state stay behind, and the selection, trace, and zoom detail would leak in. The README image (ADR-0071) already draws nodes, lines, and pills as escaped SVG text from the tokens, and the diff's Mermaid summary (M6.6) already escapes repo text for Mermaid.
- **Decision:**
  - **`renderViewSvg(index, view, layout, { theme })`:** a pure function of the view and its ELK layout (the one the canvas is drawing). Closed frames, icon tiles, lines, pills, and the footer reuse `image/diagram.ts`'s markup (now exported, with the service's layer passed in for nested nodes); new here are open frames (translucent layer tint at 6%, so nested frames deepen, with their name row as the header) and the card shapes the README image never needed (capsule routes, window pages, a model's fields row, dotted unresolved calls). Stacked as the canvas stacks: open frames, lines, closed boxes, pills. One theme per file (dark or light); the raw layer colors go in a second `.gi` rule, so the README image's bytes don't change.
  - **`viewMermaid(index, view)`:** a `flowchart LR` of the visible nodes in drawing order (`n<i>` IDs), open ones as nested `subgraph`s; shapes per kind and label escaping are the diff's (`mermaidShape`, newly exported, and `escapeMermaidLabel`), so both Mermaid outputs read the same and share one escaping rule (SECURITY.md T10). Exact and pattern lines solid, heuristic and unresolved dotted.
  - The viewer now depends on `@gitinside/diff` (browser-safe, no Node APIs); M6.9's diff mode needs it anyway.
- **Alternatives rejected:** serializing the canvas's DOM (needs inlined CSS and `color-mix`, carries the selection and trace, and isn't deterministic); a canvas-only PNG path (no SVG, and text measured per browser); copying the escaper into the viewer (two escaping rules to keep in step).
- **Consequences:** the same view and layout give the same bytes, testable without a browser. Fonts aren't embedded: an exported SVG uses Geist where installed, else the system's sans and mono (text is sized from estimates and cut with "…", so it never overflows). The selection, trace, and zoom-dependent detail aren't exported. PNG (the SVG rasterized) and the share menu's Export section are M4b.10b.

## ADR-0125: Export lives in the share menu, is made in the browser from the drawn view, and the PNG is the SVG rasterized at 2×
- **Context:** M4b.10b wires ADR-0124's renderers to the reader. The explorer's top bar has a share menu, but the website hides that bar and draws its own share menu on the repo bar, outside the explorer, so the page needs the explorer's current view and layout without owning them. A PNG needs pixels, and the site's CSP allows `img-src 'self' blob: data:` and nothing that uploads.
- **Decision:**
  - **What's exported is what's drawn:** `viewExport(index, shown)` wraps the view the canvas last drew and the layout it drew it at (`Shown`), not the view being laid out, so an export never mixes a new view with an old layout. Each file is rendered only when asked for.
  - **Host access by a ref:** `Explorer`'s `exportRef` is kept pointing at that export (`undefined` before the first layout); `ShareMenu`'s `exports` reads it each time it draws. A ref, not state, so the page doesn't re-render on every layout. Without a layout yet, the buttons say "still being laid out" rather than disabling (a disabled focused button loses its keys, see Lessons).
  - **The menu:** an "Export this view" section under the link: SVG and PNG with a Dark/Light choice beside them (starting from the screen's `data-theme` on each open), and Mermaid (no theme) on its own row, saved as `.mmd` or copied. A live region says what was saved, by file name.
  - **PNG:** the SVG loaded as an image from a `blob:` URL, drawn on a canvas at 2× and encoded with `toBlob`. When 2× passes a browser's canvas limits (16,384 px a side, or Safari's 16.7 M px area), it's drawn as large as fits and the message gives the scale. If the browser can't (no 2D canvas, no blob), the message points to the SVG.
  - **Saving:** a hidden `download` link to a `blob:` URL, revoked a minute later (revoking at once cancels the download in some browsers). File names are `owner-name-sha7[-theme].ext`, with anything but `[A-Za-z0-9._-]` replaced, so a repo name can't add a folder or an extension.
- **Alternatives rejected:** lifting the explorer's view and layout state into the page (the page would re-render on every layout, and the explorer's internals would become its API); an `onExportChange` callback into page state (same re-render); rendering the PNG on the server (it would cost compute and upload nothing the browser can't make); disabling the buttons until a layout (focus trap risk, and they'd flash disabled on open).
- **Consequences:** nothing leaves the reader's machine. An exported PNG has no Geist (an SVG image can't load fonts), so text uses the system's sans and mono. Checked in Chromium (both themes: SVG 2108×408, PNG 4216×816, Mermaid saved and copied); Firefox and Safari weren't run here, and the website's export wasn't run under the real CSP in a browser (it uses only `blob:` images, which the CSP allows).

## ADR-0126: The canvas's boxes are a WAI-ARIA tree with every box a Tab stop, arrows move spatially, and the camera follows keyboard focus
- **Context:** M4b.11 (UX.md "Keyboard and accessibility", M4a review finding 4). Boxes were focusable `role="group"` elements whose selection and broken-down state were only words in their `aria-label`, there were no arrow keys, and the live region said only "db, datastore. Selected". Boxes are absolutely placed siblings (one flat list so a node keeps its element and focus when it opens), not nested in the DOM. The canvas is `overflow: hidden` under a CSS-transform camera, so a browser scrolling it to show a focused box would put the drawing and the camera out of step.
- **Decision:**
  - **A tree, not groups or buttons:** the boxes sit in a `role="tree"` ("Architecture"), each a `treeitem` with `aria-level` (frames around it + 1), `aria-setsize`/`aria-posinset` among its visible siblings (these give a flat list a tree's shape), `aria-expanded` only when it can break down (true when broken down), and `aria-selected` on the box holding the selection. The name no longer repeats "Selected" when the role carries it (`DiagramNode` drops it whenever `aria-selected` is given); trace and diff states stay in the name, since no ARIA state fits them.
  - **Every box stays a Tab stop, in drawing order** (a frame, then its inside), as UX.md's table says, rather than APG's single roving Tab stop: a screen-reader user's way through a diagram is reading order, and the arrows are spatial, which only helps sighted keyboard users. (Revisit with M4b.13's culling at 2,000 nodes, where Tab past the canvas gets long.)
  - **Arrow keys move to the nearest box that way** (`nearestBox`): among boxes wholly past the focused one's edge on that side (1px tolerance), the least gap with each pixel off to the side counting double; ties go to the center nearest the line through the focused box, then to drawing order. "Wholly past" excludes the frame a box sits in and a frame's own children, so arrows move between neighbors and Tab goes in and out of frames. Arrows with a modifier are left to the browser and screen reader; plain ones are always kept from scrolling the page, even at an edge.
  - **The camera follows keyboard focus:** a box focused by Tab, an arrow, or focus put back after a change (`:focus-visible`) glides into view with `ensureVisible`, once the explorer has the layout it's in (focus restored after breaking down comes before it). A click's focus doesn't move the camera, so a box half off the edge doesn't jump from under the pointer. A box bigger than the canvas counts as its top-left part that fits (where its name is), for keyboard focus and inspector fly-to alike; before, a big frame was centered and its name could be off-screen. The canvas is `overflow: clip`, which isn't a scroll container, so focus can't scroll it.
  - **The live region says what a selection connects to** (`selectionAnnouncement`): "placeOrder, function. Calls POST /api/orders. Called by Checkout.", the inspector's connections (hidden kinds left out), each end named once, five per list then "and N more"; clearing the selection says "Selection cleared".
- **Alternatives rejected:** `role="button"` with `aria-pressed` (Enter and Space would have to do the same thing, and "pressed" isn't selection); `role="grid"` (the layout isn't rows and columns); nesting boxes in the DOM for an implicit tree (a box opening would remount its children and lose focus, M4b.3a); `aria-owns` to build the hierarchy (poorly supported, and levels already give it); APG's tree arrows (Up/Down through reading order, Right/Left to open and close) instead of spatial ones (UX.md asks for direction, and Enter and Esc already open and close); `scrollIntoView` (scrolls the clipped canvas, not the camera).
- **Consequences:** a box's role and states now reach assistive technology as states, not words (Chromium's accessibility tree: `treeitem "@shop/api, service" [expanded] [level=1] [selected]`). Checked in Chromium (both themes): Tab, arrows, Enter, Space, Esc, the camera bringing 12 tabbed boxes into view at 99% (a too-big frame by its corner), a click on a half-hidden box leaving the camera still, nothing scrolled, and Playwright's ARIA snapshot of the tree. Not checked with a real screen reader here, nor in Firefox or Safari (`overflow: clip` needs Safari 16).

## ADR-0127: First-visit hints are one card at the canvas's top, moved on by doing what they say, remembered per browser through a store the host passes in
- **Context:** M4b.12a (UX.md "Onboarding": three dismissible hints in sequence, zoom in → select → trace; "Don't show again" stored per browser). The explorer is a library: Storybook, its tests, and the README image's pages draw it too, and every Explorer story has a Linux baseline. The canvas's four corners already hold overlays (status chips, zoom, breadcrumbs, minimap), and the inspector's overview has a "Start here" paragraph.
- **Decision:**
  - **Opt-in through a store:** `Explorer`'s `onboarding` prop takes an `OnboardingStore` (`done()`, `remember()`); without one there are no hints, so existing stories, tests, and baselines don't change. `browserOnboarding()` keeps `gitinside.onboarding = "done"` in `localStorage`, reading storage on each call and swallowing its errors (blocked storage shows the hints every visit rather than breaking the page); `memoryOnboarding()` is for stories and hosts with their own settings. The website passes `browserOnboarding()`.
  - **Chosen once, after mount:** the hints are picked in an effect, so a server render (no storage) matches the first client one. A hint already done when the explorer opens (a deep link with something broken down, selected, or tracing) or impossible in this repo (nothing to break down, no page or route with a request path) is left out, so "Tip 1 of 2" can happen and no tip asks for the impossible.
  - **Doing it moves on:** breaking a node down (any way), selecting one, or starting a trace advances the hint that asks for it; Next does too. Only the hint on screen counts, so the click before a double-click doesn't skip "Select a box". Finishing the last hint, by Done or by doing it, is remembered like "Don't show again"; the close button and Esc (with focus in the hint) hide them for this visit only.
  - **One small popover at the top center** (elevation 2, 304px), not a tooltip pointing at a box (which would follow the camera and cover what it points at), nor the inspector (already the overview's "Start here"). It's a `section` named by its title, first in the canvas region so Tab reaches it before the boxes; it rises in and fades out like the other overlays, and between hints only its words swap, so Next keeps focus as it becomes Done. Closing it with focus inside moves focus to the selection's box or the first box, so the keys keep working (focus dropped to `<body>` breaks them, M4b.6b).
- **Alternatives rejected:** hints on by default with a Storybook decorator marking them done (every host would have to know to turn them off, and jsdom tests would all grow a hint); a cookie (sent to the server for nothing); counting visits instead of a done flag (UX.md asks for a first visit and a "Don't show again"); spotlighting the element a hint is about with a scrim (heavy, and DESIGN_SYSTEM's anti-patterns list leans away from such generated-UI flourishes); announcing each hint in the live region (it would talk over the selection announcement; the card is reachable by Tab and labelled).
- **Consequences:** the website shows the hints once per browser; clearing site data shows them again. A host that wants them per account (M8 sign-in) can pass its own store. Not checked with a real screen reader; checked in Chromium (both themes, reduced motion).
