# M3 review: Accuracy eval harness

**Tag:** `m3` · **Range:** `m2..m3` (M3.1–M3.8) · **Date:** 2026-10-28

## What was built

A new `@gitinside/eval` package that measures how often GitInside's cross-service `http` edges are right (precision) and how many real ones it finds (recall), on 5 public repos labeled by hand. Every number in the report can be regenerated byte-for-byte from pinned inputs.

| Piece | File | What it does |
|---|---|---|
| Format + validation | `eval/src/format.ts`, `inputs.ts`, `validate.ts` | zod schemas for `eval/repos.json` and `eval/labels/<owner>__<name>.json`; strict rules (sorted, unique, in-scope call sites; canonical paths; analyzer route spelling; permissive licenses); cross-checks names and SHAs |
| Pinned repos | `eval/repos.json` | 5 MIT repos, one per shape, pinned by SHA, picked by reading code only |
| Ground truth | `eval/labels/*.json` | 144 labels at 142 call sites, drafted from the code without running the analyzer, committed before any scoring existed |
| Scoring | `eval/src/score.ts` | Edge sites ⇒ predictions; TP/FP/FN overall, per repo, per confidence level; abstentions and missing sites kept apart; every FP and FN explained |
| Runner + report | `eval/src/run.ts`, `report.ts` | `pnpm eval` checks out each SHA (read only), analyzes, scores, writes `eval/results/<date>-<version>.md`; `pnpm eval --check` refuses stale inputs and byte-compares |
| Review sample | `eval/src/sample.ts`, `review.ts` | Seeded, stratified 20% sample of call sites for Abhinav's label review, rendered as a checklist with permalinks |
| CI | `.github/workflows/eval.yml` | On-demand workflow that runs `pnpm eval --check` |

Decisions are ADR-0040 to ADR-0044. The method, labeling rules, and scoring rules are in [EVALUATION.md §1](../EVALUATION.md#1-cross-service-accuracy-m3).

## Key decisions and trade-offs

- **The ground truth's rules came before the labels, and the labels before the scorer** (ADR-0040). Every rule that changes a number (what's in scope, where a call through a helper "happens", how a route is spelled) is fixed in `format.ts` and EVALUATION.md before any label is written. Git history shows labels (`05d92e8`, `1794323`) predate the scorer (`6d6c8f4`).
- **A call site is where the code fixes the route, not where the analyzer stops.** A call through `apiClient.get(path)` is labeled at the caller that supplies `path`. That's a fact about the code, so it can be labeled blind, and the analyzer's one-level wrapper limit shows up honestly as false negatives.
- **Conservative counting everywhere.** An in-scope route prediction with no label is a false positive. Empty ratios print "n/a", never 0% or 100%. Per-level recall shares one denominator so the rows add up.
- **Abstaining isn't a false positive** (ADR-0042). For a request to a host outside the repo, an `unresolved` or `external` prediction is right; it's counted as an abstention, apart from precision.
- **Byte reproduction with a Run record** (ADR-0043). The report is a pure function of pinned inputs plus one Run section (date, commit, machine). `--check` refuses if any input changed since that commit, so "reproduced" really means "this code produced this report".
- **No tuning after seeing the numbers.** Two anchoring disagreements (taxonomy's inlined helper, wanderlust's multi-line `axios\n.get`) are analyzer issues under rules fixed earlier, so they stay as misses.

## Hardest problem: a number that can't be rigged, even accidentally

The eval exists to put a defensible number on a résumé, so the threat model is the author, not an attacker. Every place where a choice could drift toward a better score had to be closed:

1. **Repo selection:** the analyzer was never run on a candidate, and rejects are recorded with reasons (EVALUATION.md "The pinned set").
2. **Labels:** drafted from code only and committed before the scorer existed; validated strictly so a sloppy label fails instead of silently scoring.
3. **Scoring rules:** fixed in ADR-0042 before the first run. Route lines aren't compared, but call-site lines are, so an analyzer that anchors a call one line off pays for it.
4. **Reporting:** the report is regenerated, never edited; `--check` byte-compares and refuses stale inputs.
5. **Review:** the 20% sample is drawn by a seeded generator (FNV-1a → mulberry32 → Fisher–Yates), stratified per repo, with the seed fixed to the issue date, so nobody can re-roll for an easy sample.

The cost of this discipline is visible in the result: a 20.3% recall that could have been made to look much better by labeling at the innermost `fetch` line.

## What's still weak

- **Recall is low, and the cause is known.** 83 of 110 misses are WealthWise and foodie requests through path-taking helpers (`apiClient.get(path)`, `httpRequest({ url })`), reported once as `DYNAMIC_URL` inside the helper instead of at each caller. wanderlust's `axiosInstance` (base URL assigned after `create()`) gets no prediction. These are the first analyzer tasks to plan after M3, each with its eval delta.
- **The labels are unreviewed.** Numbers may change when issue #1 is closed. The sample checks labels that exist; it can't find call sites the labeler missed (those would show up as `unlabeled-site` FPs).
- **Small set:** 5 small-to-mid hobby or reference apps, 138 real targets. One repo's pattern can dominate the totals (conversa is 24 of 28 TPs), and the numbers say nothing about large production monorepos.
- **Only HTTP edges are scored.** Prisma reads/writes, SDK calls, queues, and infra links have no accuracy measure yet.
- **Pattern confidence is untested by the eval:** no TP or FP at that level.

A subagent with no prior context reviewed `m2..HEAD` against SPEC.md, ROADMAP M3, EVALUATION.md, TESTING.md, SECURITY.md, and CLAUDE.md, running scratch scripts against the built eval package. It found nothing high-severity and confirmed the committed report reproduces. It reported 9 findings, 5 confirmed by running. Fixed with tests in `3b8e3a9` (ADR-0045); the report was re-recorded in `575dfaa`.

| # | Severity | Finding | Outcome |
|---|---|---|---|
| 1 | Medium | `pnpm eval --check eval/results/<file>.md`, the command the report itself prints, failed with ENOENT: pnpm runs the script inside `eval/`, so the path resolved to `eval/eval/results/…`. The reviewer also confirmed these were fine: the README numbers match the report; per-level TPs add up (4 + 0 + 24 = 28); checkouts use argument arrays with no shell, a 40-hex SHA, and a URL that must equal `https://github.com/<owner>/<name>`, with no path traversal; no install, hooks, submodules, or LFS downloads; the workflow passes its input through an env var; scoring (ADR-0041 per-label scoring, abstentions, scope prefixes, parameter names) behaves as documented; zod rejects every malformed route it tried; ⌈20%⌉ is exact for every n up to 2,000; the shuffle is unbiased and platform-independent; and there's no `localeCompare`, `any`, `Math.random`, or `Date.now` in `eval/src`.

**After the fixes:** 675 tests green, eval line coverage 99.48%, lint and typecheck green, and the regenerated report has the same numbers (only the Run commit changed).

## Interview questions

**1. How do you know your precision and recall aren't tuned to your own tool?**
The order of operations is in git history: the label format and rules were fixed first (ADR-0040), the repos were chosen by reading code without running the analyzer, the labels were committed before the scorer existed, and the scoring rules were written down before the first run. After the first run, nothing was re-labeled or re-scored, even where a different rule would have turned a miss into a hit. An independent reviewer (Abhinav) checks a seeded random 20% of call sites. *Follow-up:* "What can the review not catch?" Call sites the labeler never labeled. Those surface as `unlabeled-site` false positives instead, which is why in-scope unlabeled predictions are counted against precision.

**2. Precision is 96.6% but recall is 20.3%. What does that tell you?**
The analyzer is rarely wrong but often silent. That's the intended failure mode ("fail visibly, never guess"), and the miss lists say exactly which code shapes to support next: path-taking helpers called from many places, and an axios instance whose `baseURL` is assigned after creation. It also says a 96.6% precision on 29 predictions is a small sample: one more wrong edge would move it by about 3 points.

**3. How does `pnpm eval --check` prove a report is reproducible when the report includes a date and a machine?**
The report is a pure function of the pinned inputs (repo SHAs, labels, analyzer code) plus a Run record. `--check` reads the Run record back, refuses if the analyzer, schema, eval code, labels, or lockfile differ from the commit it names, regenerates the report with the same Run record, and compares bytes. Line endings are pinned (`core.autocrlf=false` for checkouts, LF for `eval/results/**`) so Windows and Linux agree. *Follow-up:* "Why not just exclude the Run section from the comparison?" Then a report could claim a commit it wasn't produced from.

**4. Why is a call through `apiClient.get("/accounts")` labeled at the caller and not at the `fetch` inside `apiClient`?**
Because the route is decided at the caller; the `fetch` inside the helper serves every route. Labeling the inner `fetch` would make one site stand for dozens of different routes, and a tool that reports "unresolved" there would look half right. Defining the call site as "where the code fixes the route" is a property of the code, so it can be labeled without looking at the tool. The analyzer's one-level wrapper limit then shows up as false negatives, which is honest.

**5. Why is the review sample stratified per repo, and why write your own random generator?**
A pooled draw of 29 of 142 sites could skip the 8-site taxonomy repo entirely, leaving one labeler pass unchecked; per-repo ⌈20%⌉ guarantees coverage at the cost of one extra site. The generator (FNV-1a hash of `<date>/<owner>/<name>` → mulberry32 → Fisher–Yates) uses only 32-bit integer math, so anyone can regenerate the exact list on any platform from the committed labels and the issue date, and nobody can re-roll for an easier sample.
