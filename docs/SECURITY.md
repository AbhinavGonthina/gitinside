# Security

GitInside analyzes **untrusted code** submitted by anyone, and holds **private repo data** for signed-in users. Decisions: ADR-0007, ADR-0009, ADR-0014, ADR-0015; D5.8, D7.1–D7.3.

## 1. Assets

- **Private repo contents and their graphs** (installation-scoped).
- **Secrets:**
  - GitHub App private key and webhook secret.
  - OAuth client secret.
  - Neon connection string, the snapshot bucket's keys (an Oracle Customer Secret Key).
  - Job HMAC secret (`ENQUEUE_HMAC_SECRET`), session secret.
  - The worker's GitHub token (fine-grained, read-only access to public repositories only; for the rate limit).
  - No Google Cloud key exists: Vercel and the deploy reach Google keyless (Workload Identity Federation), and the worker's runtime account token, from Cloud Run's metadata server, can only read the worker's four secrets.
- **Users' GitHub identities and sessions.**
- **Availability** of the worker (Cloud Run) and the free-tier quotas, and the **Google billing account**: Cloud Run usage above the free allowance is billable once the trial ends (ADR-0111).

## 2. Threat model

| # | Threat | Vector | Mitigation |
|---|---|---|---|
| T1 | Code execution from an analyzed repo | `postinstall` scripts, config files that execute (`next.config.js`, `vite.config.ts`), `.npmrc` hooks | We never run `npm`/`pnpm`, scripts, or `require`/`import` repo files. The analyzer only reads text via the TS compiler API; a Vite config's dev proxy table is read from its syntax, and a `rewrite`'s regex is read character by character, never compiled (`devProxy.ts`, ADR-0204); `next.config`'s `basePath` and `rewrites` are read the same way, their path patterns segment by segment (`nextConfig.ts`, ADR-0206). The analysis child runs under Node's permission model (`apps/worker/src/runner.ts`, ADR-0059): it can't start processes or worker threads, load addons, read outside the app and the job's `src`, or write anything but its output file, and its environment is empty. It also can't use `process.binding`, the inspector, or WASI. On Cloud Run the worker's secrets are its own environment variables (from Secret Manager); the child's empty environment and its refused reads of `/proc` (the parent's `environ` included) keep them out of reach (`runner.test.ts`, ADR-0152). Each instance runs in Google's sandbox (gen2) and holds one job, so even a container escape reaches no other job. Test (`apps/worker/src/security.test.ts`, ADR-0076): the `fixtures/malicious/postinstall-script` repo (lifecycle scripts, `next.config.js`, `vite.config.ts`, a tsconfig plugin, `.npmrc` hooks, top-level code) goes through a whole job; its sentinel file never appears, and the only process started is the sandboxed analysis child. |
| T2 | Filesystem escape during extraction | `../` paths, absolute paths, symlinks, hard links in the tarball | A streaming tar extractor we parse ourselves (`apps/worker/src/extract.ts`, ADR-0058) writes only regular files and directories (links and special files are skipped and listed, so nothing can redirect a later write), fails the job on any absolute or `..` path, and checks every resolved path stays inside the job dir. Files are created exclusively (no overwrite). The analyzer also never follows a symlink it finds on disk. Tests for each, plus whole-job cases in the security suite (links aimed at a canary folder outside the job, every escape form aimed at real folders). |
| T3 | Resource exhaustion | zip bombs, huge files, millions of files, deep nesting, pathological TS (huge unions, recursion) | Limits (sized together so one job fits a 4 GiB Cloud Run instance whose `/tmp` is memory: `apps/worker/src/budget.ts`, ADR-0146): 400 MiB extracted (counted on the decompressed stream, so a gzip bomb stops early), 60,000 archive entries, 2 MB per file (skipped by the analyzer), 20k source files, 50 MB of source files together (`LIMIT_SOURCE_SIZE`, checked at the inventory before any parsing, so a repo that would run out of memory minutes in fails in seconds; ADR-0137), depth 64, child process with `--max-old-space-size` (2,560 MB, `LIMIT_MEMORY`), CPU/time limit (5 min wall clock, cut to what the attempt's 280 s leaves, killed with SIGKILL: `LIMIT_TIME` if it had at least its guaranteed 230 s, else the retriable `ANALYSIS_TIME_CUT`, ADR-0143; 1 vCPU per instance), one job per instance and at most 2 instances (the queue dispatches 2 at once). An instance that still ran out of memory would be killed by Cloud Run: the push gets no answer, so Cloud Tasks retries it, and maintenance fails a row left `running` (`JOB_INTERRUPTED`, ADR-0147). The security suite checks the file, source-size, size, entry, depth, and path limits at their production values on whole jobs (a 420 MiB zip bomb, 20,001 source files, 26 source files of 2 MiB, 60,001 entries). |
| T4 | Network abuse from the worker | an analyzer bug or a future plugin making requests; Cloud Run's metadata server, which hands out the runtime account's token | **The analysis child has no network, and that is the boundary** (ADR-0152). The worker fetches the tarball before forking (`apps/worker/src/github.ts`, ADR-0061: redirects followed by hand, only within the API or to `codeload.github.com`, and the GitHub token is never sent past the API host). A preloaded guard (`netguard.ts`) fails every socket, DNS, `fetch`, HTTP/2, and Unix-socket call in the child with `ERR_NETWORK_DISABLED`, the metadata server included, and the permission model closes Node's own ways around it (`process.binding`, the inspector, WASI, addons, child processes, worker threads). Tests: the sandbox probes in `runner.test.ts`, each shown to fail without the permission flags. **The worker process** has Cloud Run's ordinary outbound network. No allowlist outside the process is free there (Direct VPC egress reaches the internet only through Cloud NAT, and firewall rules by hostname need Cloud NGFW; both are billed), and the Oracle VM's DNS and iptables gateway (ADR-0075) left with `infra/oracle`. It runs only our code and calls `api.github.com`, `codeload.github.com`, the snapshot bucket's endpoint (built from a namespace and region that can't add a domain, ADR-0095), and Neon. **Residual risk:** code running in the worker process (an escape from the child through a Node or V8 bug, or a malicious dependency, T12) could send the worker's secrets anywhere. The metadata server's token adds nothing to them (the runtime account only reads those four secrets); each can be rotated, and the GitHub token reads only public repositories. |
| T5 | Secret leakage into graphs | `.env` values, hardcoded keys | The env detector reads key **names** and URL **schemes/hosts** only; values are discarded at parse time. Graph strings are never built from env values. One exception, for matching only (ADR-0202): from committed **example** env files (`.env.example`, `.sample`, `.template`; never `.env`, `.env.local`, `.env.production`, …), the route matcher takes the URL **path** of an API-named base's value (at most 4 plain segments, no host, credentials, query, or fragment) and tries it in front of the request's path. It stays inside the matcher: a match shows the route's own label from the server's code (its sites record the request's URL as written, without the path, ADR-0087's M6.11c amendment), and a miss shows the request's URL without it, so a path that is really a token never appears. Credentials are dropped from literal URL hosts, and source text shown on unresolved requests has string contents masked outside the URL path (ADR-0038). Test: `fake-secrets` fixture output contains none of its planted values (an `.env.example` path behind a request that matches nothing included), also after a whole job with fake secrets in the worker's own environment (security suite). |
| T6 | Private data exposure | a public cache key collision, missing access checks, shared links | Private snapshots live under `private/<installationId>/…` and are never served via CDN. The worker asks GitHub for each repo's visibility and refuses a private repo on a job without an installation (`REPO_NOT_PUBLIC`, ADR-0063), even when its token could read it. Every private view checks access (cache ≤ 60s). Private pages are `noindex`, and badges for private repos are link-only. Tests: user without access → 404 (not 403, to avoid confirming existence); revoked access → denied within 60s. |
| T7 | Stale data after uninstall | data retained after the user leaves | The `installation.deleted` / `installation_repositories.removed` webhook deletes snapshots, analyses, PR records, and access cache for those repos immediately. Tested. |
| T8 | Forged webhooks or forged jobs | attacker POSTs to `/api/github/webhook` or the worker's `POST /run` | GitHub HMAC (`X-Hub-Signature-256`) verified with constant-time comparison. The worker (`apps/worker/src/run.ts`, ADR-0143) is first behind Cloud Run: its ingress is `internal`, so the internet can't reach it, and only `gitinside-invoker`, whose OIDC tokens Cloud Tasks mints, may invoke it (`infra/gcp/`, applied in M5.17e). Each job body also carries the web app's HMAC-SHA256 over timestamp + method + path + raw body with a shared secret (current or, during a rollover, previous; ADR-0060), accepted for a day because a task can wait in the queue, checked before parsing or routing. Bodies over 16 KiB are refused unread; job IDs are derived from the body, so a replay is the same job, and a replay of a finished one does no work (ADR-0145). There is no queue server to reach: Cloud Tasks replaced BullMQ and Redis, and the old enqueue API is gone (M5.17c3). |
| T9 | Abuse / denial of wallet | spamming analyses to exhaust quotas; huge or busy repos re-analyzed per commit; bots spread over many addresses | Only a **new** analysis costs anything (a finished diagram, badge, or job already queued never wakes the worker), and each one passes, in order: the size refusals, the compute pause, the bot check when traffic looks automated, the per-repo limit, then the per-address limit (`apps/web/lib/analyze.ts`; check-on-view has its own per-repo limit instead of the last three). A refusal uses no rate-limit slot, row, or task and says why and when to retry. Dedupe: one job per `repo@sha` and analyzer version (ADR-0060), one task per queue entry, and a duplicate push for a finished job does no work (ADR-0145). Every figure is in **T9 in numbers** below, checked against the code by `apps/web/lib/abuseLimits.test.ts`. Object Storage, Neon, and Vercel are free plans that can't bill (D8.2); their use is alarmed at 80% and snapshots are evicted to fit. **Cloud Run can bill** once its trial ends (ADR-0111): the app pauses new analyses at 80% of the month's free compute by its own count (ADR-0156), the service can't grow past 2 instances × 300 s requests, and Google's spend cap and budget kill switch bound what the count misses (M5.17e, #3). **Residual risk:** someone with many addresses who passes Turnstile can, at the fastest (both instances busy), use the month's 80% in about 9.3 hours, after which new analyses pause until the next UTC month. That is a denial of service, not a bill; diagrams already made keep working. |
| T10 | XSS from repo content | file names, labels, code previews rendered in the UI | React escaping everywhere; Shiki output is rendered as tokens through React, never as HTML; no `dangerouslySetInnerHTML` with repo strings; strict CSP on `apps/web` (only two directives name another origin: `connect-src` names `raw.githubusercontent.com`, where the browser reads public code previews as text at the analyzed SHA, ≤ 2 MB counted while streaming, no cookies or redirects, no `.`/`..`/empty path segments, ADR-0115; `frame-src` names `challenges.cloudflare.com`, Turnstile's widget, loaded only when the server asks for the bot check, ADR-0157). Mermaid export escapes labels. The progress page's "Found so far" names (services, stores, hosts) travel child → worker → Postgres → web capped (8 names, 64 characters each) with control and format characters replaced, and are re-checked at every hop (`parseFoundFacts`, ADR-0135). |
| T11 | Overbroad GitHub permissions | App asking for more than needed | Permissions: Contents read, Metadata read, Pull requests read & write (comment), Checks read & write. No admin, no workflows, no write to contents. OAuth sign-in requests identity only. |
| T12 | Supply chain (our own dependencies) | malicious npm package in GitInside | Pinned versions, lockfile committed, `pnpm install --frozen-lockfile` in CI, minimal dependencies, Dependabot alerts on. |
| T13 | Autopilot loosening its own limits | an unattended run edits the loop script or permission settings | `.claude/settings.json` denies edits to `scripts/autopilot.*` and `.claude/settings*.json`. The loop denies force push, `gh repo delete/edit`. `main` is branch-protected (no force push or deletion). |

### T9 in numbers

The abuse limits as of M5.18f (#11). `apps/web/lib/abuseLimits.test.ts` checks each row except the last two against the code and `infra/gcp`, so a limit changed in one place only fails CI. Windows are fixed UTC hours unless a row says otherwise.

| Limit | Value | Where |
|---|---|---|

| Worker instances | at most 2, 0 when idle | `infra/gcp/service.json` |
| Each instance | 1 vCPU / 4 GiB, 1 job, 300 s per request | `infra/gcp/service.json`; CPU only during requests, no startup boost |

| Snapshot bucket | 20 GB; retention keeps the latest 5 per repo and evicts the oldest past 16 GB | `RETENTION_POLICY` (PR pins kept 30 days, ADR-0077) |
| Bucket requests | 50,000 a month | `store_requests` (ADR-0096); alarm only, the plan can't bill |
| Postgres storage | 1 GB | Neon's free plan as SPEC §5 states it; alarm only |
| New analyses per user, signed in | 30 per hour | SPEC §3; arrives with sign-in (M8) |
| Billing | spend cap around $1 if offered, a $1 monthly budget whose alert turns billing off, no Cloud NAT, load balancer, Memorystore, or static IP, images kept inside Artifact Registry's free storage | ADR-0111; the kill switch is `infra/gcp/budget.json` ⇒ `pubsub.json` ⇒ `killswitch.json` (ADR-0169: once the month's cost after credits reaches $1, the project's billing account is unlinked); applied by M5.17e2–e4 and verified in M5.13's smoke test (#3). Until then the trial account can't bill |

What these bound, worked out from the rows above:

- **The month's free compute** lasts 288,000 GB-s ÷ 4.295 GB ≈ 67,000 instance-seconds before the pause: about 216 jobs that each use the full 300 s plus 10 s of shutdown, or far more ordinary ones (cal.com took 27–77 s on a laptop, ADR-0111). With both instances busy that is about 9.3 hours of wall clock.
- **Without the app's own pause** (a counting bug), the service can still run at most 2 instances around the clock; ADR-0111 puts that ceiling at about $150–170 a month, which is why the spend cap and kill switch are required before the trial ends, not optional.
- **What the count misses:** time Google bills before our process starts (pulling and starting the image). The 20% margin covers it; M5.13 compares a day's count with Google's billing report.

## 3. Worker container

- Image `apps/worker/Dockerfile`, run on Cloud Run (ADR-0111). Cloud Run applies no compose-style hardening, so the image carries it itself (ADR-0150), and every CI run checks it by starting the image as Cloud Run does (`infra/gcp/check.mjs`: plain `docker run`, a non-default `PORT`, 1 vCPU / 4 GiB, `/tmp` in memory, no init). The service, queue, and IAM it runs under are reviewed config in `infra/gcp/` (ADR-0151), checked against the code by `apps/web/lib/gcpConfig.test.ts`. The Oracle stack (compose, egress gateway, Caddy, ADR-0074, ADR-0075) was removed in M5.17d2; this section was reviewed for Cloud Run in M5.17f (ADR-0152).
- Runs as a non-root user (`USER 1000:1000`, the base image's `node`). Nothing on the filesystem outside `/tmp` is writable by it: the app is root-owned, the `node` home and anything else uid/gid 1000 owned is handed to root, and no other path is world-writable (the CI check walks the whole filesystem as the worker). Job folders go under `/tmp/jobs` (in memory on Cloud Run). The app lives at `/app/apps/worker`, so the analysis child's read root `/app` holds code only; npm, npx, corepack, and yarn are removed. Cloud Run can't make the root read-only or `/tmp` `noexec`, so ownership is the control; nothing ever executes from a job folder anyway (T1).
- No capabilities for the worker's user (checked by the image check). One job per instance: 1 vCPU / 4 GiB, concurrency 1, at most 2 instances, a 300 s request timeout (`infra/gcp/service.json`).
- Each job (`apps/worker/src/job.ts`): tarball → `/tmp/jobs/<jobId>-<random>/src` → child process with resource limits → `architecture.json` → upload → the job dir is deleted (also deleted on failure). The worker sweeps `/tmp/jobs` at startup for folders a killed process left behind.
- Fact cache (`apps/worker/src/factcache.ts`, ADR-0178): the child reuses and stores per-service facts in `/tmp/cache`, which outlives jobs (not the instance). Public repos share `public/`; each GitHub App installation has `installations/<id>/`, deleted with the installation (M8.5); a private repo without an installation gets no cache. The permission model lets the child read and write only its job's folder (`--allow-fs-read`/`--allow-fs-write`, tested with a probe aimed at another installation's folder), so one tenant's facts never reach another's analysis. Accepted risk: a child that escaped the analyzer's parse-only code could write wrong facts into `public/` for later public jobs on that instance; that needs code execution in the child, which T1 already treats as the breach, and the facts carry no secrets. The cache's 64 MiB is part of the T3 memory budget.
- No queue runs beside the worker (Cloud Tasks pushes jobs to it, ADR-0114; Redis was removed in M5.17c3). The analysis child's environment is empty.
- Outbound (T4, ADR-0152): the analysis child has none (`netguard.ts` and the permission model). The worker process has Cloud Run's ordinary egress and calls only GitHub, the bucket, and Neon; no egress allowlist runs outside the process, since none is free on Cloud Run. Its secrets are environment variables from Secret Manager, out of the child's reach.
- Inbound: the service's ingress is `internal` (only Google services in the project, i.e. Cloud Tasks, on the `run.app` URL), and only `gitinside-invoker` may invoke it (no `allUsers`); every `/run` is then HMAC-checked (ADR-0143). It runs as its own account, `gitinside-worker`, which may only read its four secrets (`infra/gcp/iam.json`).

## 4. Secrets handling

- Never committed. `.env*` is gitignored. Example files (`.env.example`) contain names only.
- **Production:** Vercel environment variables (web) and Secret Manager for the worker, read only by its runtime account (`infra/gcp/iam.json`; deployed in M5.17e). The worker's GitHub token is a fine-grained token with read-only access to public repositories and no other permission, so a leaked one reads only what anyone can. No Google service-account key is ever created (keyless federation). Deploys come only from CI's `deploy` job on `main`: GitHub's OIDC token becomes `gitinside-deploy`, whose provider admits only this repository (by ID), `ci.yml` on `refs/heads/main`, from a push or a manual run; that account may push the image, replace the two services, and update the queue, but can't change who may invoke them (ADR-0170).
- Abhinav enters secrets himself. Autopilot never asks for secret values in issues, logs, or commits, and never prints them.
- Rotation: GitHub App keys and HMAC secrets can be rotated without downtime (two valid secrets during rollover).
