# Security

GitInside analyzes **untrusted code** submitted by anyone, and holds **private repo data** for signed-in users. Decisions: ADR-0007, ADR-0009, ADR-0014, ADR-0015; D5.8, D7.1–D7.3.

## 1. Assets

- **Private repo contents and their graphs** (installation-scoped).
- **Secrets:**
  - GitHub App private key and webhook secret.
  - OAuth client secret.
  - Neon connection string, the snapshot bucket's keys (an Oracle Customer Secret Key).
  - Enqueue HMAC secret, session secret.
- **Users' GitHub identities and sessions.**
- **Availability** of the worker (Cloud Run) and the free-tier quotas.

## 2. Threat model

| # | Threat | Vector | Mitigation |
|---|---|---|---|
| T1 | Code execution from an analyzed repo | `postinstall` scripts, config files that execute (`next.config.js`, `vite.config.ts`), `.npmrc` hooks | We never run `npm`/`pnpm`, scripts, or `require`/`import` repo files. The analyzer only reads text via the TS compiler API. The analysis child runs under Node's permission model (`apps/worker/src/runner.ts`, ADR-0059): it can't start processes or worker threads, load addons, read outside the app and the job's `src`, or write anything but its output file, and its environment is empty. Test (`apps/worker/src/security.test.ts`, ADR-0076): the `fixtures/malicious/postinstall-script` repo (lifecycle scripts, `next.config.js`, `vite.config.ts`, a tsconfig plugin, `.npmrc` hooks, top-level code) goes through a whole job; its sentinel file never appears, and the only process started is the sandboxed analysis child. |
| T2 | Filesystem escape during extraction | `../` paths, absolute paths, symlinks, hard links in the tarball | A streaming tar extractor we parse ourselves (`apps/worker/src/extract.ts`, ADR-0058) writes only regular files and directories (links and special files are skipped and listed, so nothing can redirect a later write), fails the job on any absolute or `..` path, and checks every resolved path stays inside the job dir. Files are created exclusively (no overwrite). The analyzer also never follows a symlink it finds on disk. Tests for each, plus whole-job cases in the security suite (links aimed at a canary folder outside the job, every escape form aimed at real folders). |
| T3 | Resource exhaustion | zip bombs, huge files, millions of files, deep nesting, pathological TS (huge unions, recursion) | Limits (sized together so one job fits a 4 GiB Cloud Run instance whose `/tmp` is memory: `apps/worker/src/budget.ts`, ADR-0146): 400 MiB extracted (counted on the decompressed stream, so a gzip bomb stops early), 60,000 archive entries, 2 MB per file (skipped by the analyzer), 20k source files, 50 MB of source files together (`LIMIT_SOURCE_SIZE`, checked at the inventory before any parsing, so a repo that would run out of memory minutes in fails in seconds; ADR-0137), depth 64, child process with `--max-old-space-size` (2,560 MB, `LIMIT_MEMORY`), CPU/time limit (5 min wall clock, killed with SIGKILL, `LIMIT_TIME`; CPU share capped by the container), at most 2 concurrent jobs. The security suite checks the file, source-size, size, entry, depth, and path limits at their production values on whole jobs (a 420 MiB zip bomb, 20,001 source files, 26 source files of 2 MiB, 60,001 entries). |
| T4 | Network abuse from the worker | an analyzer bug or a future plugin making requests | On Cloud Run the worker process has the platform's ordinary outbound network: the Oracle VM's egress allowlist (a DNS and iptables gateway, ADR-0075) was removed with `infra/oracle` in M5.17d2, and M5.17f reviews what replaces it. The worker itself only calls `api.github.com`, `codeload.github.com`, the snapshot bucket's Object Storage endpoint (built from a namespace and region that can't add a domain, ADR-0095), and Neon. The analysis child process has no network need; the worker fetches the tarball before forking (`apps/worker/src/github.ts`, ADR-0061: redirects followed by hand, only within the API or to `codeload.github.com`, and the GitHub token is never sent past the API host), and a preloaded guard (`netguard.ts`) fails every socket, DNS, and `fetch` call in the child with `ERR_NETWORK_DISABLED` (with the allowlist gone, this guard is the boundary for the child until M5.17f). |
| T5 | Secret leakage into graphs | `.env` values, hardcoded keys | The env detector reads key **names** and URL **schemes/hosts** only; values are discarded at parse time. Graph strings are never built from env values. Credentials are dropped from literal URL hosts, and source text shown on unresolved requests has string contents masked outside the URL path (ADR-0038). Test: `fake-secrets` fixture output contains none of its planted values, also after a whole job with fake secrets in the worker's own environment (security suite). |
| T6 | Private data exposure | a public cache key collision, missing access checks, shared links | Private snapshots live under `private/<installationId>/…` and are never served via CDN. The worker asks GitHub for each repo's visibility and refuses a private repo on a job without an installation (`REPO_NOT_PUBLIC`, ADR-0063), even when its token could read it. Every private view checks access (cache ≤ 60s). Private pages are `noindex`, and badges for private repos are link-only. Tests: user without access → 404 (not 403, to avoid confirming existence); revoked access → denied within 60s. |
| T7 | Stale data after uninstall | data retained after the user leaves | The `installation.deleted` / `installation_repositories.removed` webhook deletes snapshots, analyses, PR records, and access cache for those repos immediately. Tested. |
| T8 | Forged webhooks or forged jobs | attacker POSTs to `/api/github/webhook` or the worker's `POST /run` | GitHub HMAC (`X-Hub-Signature-256`) verified with constant-time comparison. The worker (`apps/worker/src/run.ts`, ADR-0143) is first behind Cloud Run IAM (only Cloud Tasks' invoker service account may call it, M5.17e), and each job body also carries the web app's HMAC-SHA256 over timestamp + method + path + raw body with a shared secret (current or, during a rollover, previous; ADR-0060), accepted for a day because a task can wait in the queue, checked before parsing or routing. Bodies over 16 KiB are refused unread; job IDs are derived from the body, so a replay is the same job, and a replay of a finished one does no work (ADR-0145). There is no queue server to reach: Cloud Tasks replaced BullMQ and Redis, and the old enqueue API is gone (M5.17c3). |
| T9 | Abuse / denial of wallet | spamming analyses to exhaust quotas | Per-IP and per-user rate limits (D8.4), dedupe by `repo@sha`, global concurrency 2, retention eviction, quota alarms at 80% (needs-abhinav issue). Nothing can incur charges (D8.2). |
| T10 | XSS from repo content | file names, labels, code previews rendered in the UI | React escaping everywhere; Shiki output is rendered as tokens through React, never as HTML; no `dangerouslySetInnerHTML` with repo strings; strict CSP on `apps/web` (only `connect-src` names another origin: `raw.githubusercontent.com`, where the browser reads public code previews as text at the analyzed SHA, ≤ 2 MB counted while streaming, no cookies or redirects, no `.`/`..`/empty path segments, ADR-0115). Mermaid export escapes labels. The progress page's "Found so far" names (services, stores, hosts) travel child → worker → Postgres → web capped (8 names, 64 characters each) with control and format characters replaced, and are re-checked at every hop (`parseFoundFacts`, ADR-0135). |
| T11 | Overbroad GitHub permissions | App asking for more than needed | Permissions: Contents read, Metadata read, Pull requests read & write (comment), Checks read & write. No admin, no workflows, no write to contents. OAuth sign-in requests identity only. |
| T12 | Supply chain (our own dependencies) | malicious npm package in GitInside | Pinned versions, lockfile committed, `pnpm install --frozen-lockfile` in CI, minimal dependencies, Dependabot alerts on. |
| T13 | Autopilot loosening its own limits | an unattended run edits the loop script or permission settings | `.claude/settings.json` denies edits to `scripts/autopilot.*` and `.claude/settings*.json`. The loop denies force push, `gh repo delete/edit`. `main` is branch-protected (no force push or deletion). |

## 3. Worker container

- Image `apps/worker/Dockerfile`, run on Cloud Run (ADR-0111). Cloud Run applies no compose-style hardening, so the image carries it itself (ADR-0150), and every CI run checks it by starting the image as Cloud Run does (`infra/gcp/check.mjs`: plain `docker run`, a non-default `PORT`, 1 vCPU / 4 GiB, `/tmp` in memory, no init). The service, queue, and IAM it runs under are reviewed config in `infra/gcp/` (ADR-0151), checked against the code by `apps/web/lib/gcpConfig.test.ts`. The Oracle stack (compose, egress gateway, Caddy, ADR-0074, ADR-0075) was removed in M5.17d2; M5.17f reviews this section for Cloud Run.
- Runs as a non-root user (`USER 1000:1000`, the base image's `node`). Nothing on the filesystem outside `/tmp` is writable by it: the app is root-owned, the `node` home and anything else uid/gid 1000 owned is handed to root, and no other path is world-writable (the CI check walks the whole filesystem as the worker). Job folders go under `/tmp/jobs` (in memory on Cloud Run). The app lives at `/app/apps/worker`, so the analysis child's read root `/app` holds code only; npm, npx, corepack, and yarn are removed. On the Oracle stack the root was also read-only, with a 1,200 MB `noexec,nosuid,nodev` tmpfs at `/tmp/jobs`.
- No capabilities for the worker's user (checked by the image check). One job per instance: 1 vCPU / 4 GiB, concurrency 1, at most 2 instances, a 300 s request timeout (`infra/gcp/service.json`).
- Each job (`apps/worker/src/job.ts`): tarball → `/tmp/jobs/<jobId>-<random>/src` → child process with resource limits → `architecture.json` → upload → the job dir is deleted (also deleted on failure). The worker sweeps `/tmp/jobs` at startup for folders a killed process left behind.
- No queue runs beside the worker (Cloud Tasks pushes jobs to it, ADR-0114; Redis was removed in M5.17c3). The analysis child's environment is empty.
- Inbound: the service's ingress is `internal` (only Google services in the project, i.e. Cloud Tasks, on the `run.app` URL), and only `gitinside-invoker` may invoke it (no `allUsers`); every `/run` is then HMAC-checked (ADR-0143). It runs as its own account, `gitinside-worker`, which may only read its four secrets (`infra/gcp/iam.json`).

## 4. Secrets handling

- Never committed. `.env*` is gitignored. Example files (`.env.example`) contain names only.
- **Production:** Vercel environment variables (web) and Secret Manager for the worker, read only by its runtime account (`infra/gcp/iam.json`; deployed in M5.17e).
- Abhinav enters secrets himself. Autopilot never asks for secret values in issues, logs, or commits, and never prints them.
- Rotation: GitHub App keys and HMAC secrets can be rotated without downtime (two valid secrets during rollover).
